Compiler implementation notes (dfcompiler 0.0.9alpha, spec 0.0.9)
=====================================================================

What this file is: the decisions the compiler makes where the spec leaves room, the way each part is built,
and the limits of this version. Compiler status.txt says what is done; this file says how, and what is missing.
Where a decision came from the spec the section is named; where I (Claude) chose, it is marked CHOICE.


1. Overall shape
-----------------
- dfparser (Lexer, Parser, Node) is shared with dfcompiler: same source files, compiled into both.
- dfcompiler reads one .df file, type checks it, writes a C file and calls clang (not found: PATH, DFLAT_CC, --cc).
  Folders (next to the source file): the C goes to .compilation/<name>.c, the executable to build.<target>/<name>[.exe]
  (build.win-x64, build.linux-x64 ...; build.custom for CL:). Both folders are created when missing and the files are overwritten.
- Options (all with two dashes, no short forms; an unknown option is an error): --output <file> (the executable, wherever the user
  wants), --target <target>, --emit-c (only the C file), --run (run the program), --cc <path>, --version, and "--" then the
  arguments of the program. (-o and -version of the earlier versions are gone.)
  Since 2026-10-18 the names are not case sensitive (--VERSION, --Emit-C work), as in "Compiler_Options.md", which is the list of the options of the compiler
  (the ones not built yet are described there). --run must be the very last option; the program arguments come after "--" (--run -- first second), and a
  "--" without --run, or anything but "--" after --run, is an error. Program.cs holds the usage text; the options and the .dsprj file are built as we go.
- Targets: win-x64, win-x32, linux-x64, linux-arm64, osx-x64, osx-arm64 (clang triples in Program.Targets), or CL:<text>: the text is
  split at the spaces and given to clang as it is (nothing else is added for the target: no -lm, no -D_CRT_SECURE_NO_WARNINGS).
  Without --target, or with the target of this machine, clang gets no target flag (as before). Any other known target adds
  --target=<triple>, -lm (not for Windows targets) and -D_CRT_SECURE_NO_WARNINGS (Windows targets). Whether clang can build for the
  target (headers, libraries, linker) is not checked: clang's own errors are shown. --run only runs a program built for this
  machine; for another target it says so and stops after building. The generated C is the same for every target (the differences
  are #ifdef _WIN32 blocks that the C compiler resolves), and the Linux and macOS parts of the runtime were never compiled yet.
- Output is one C file: the runtime (always), optional runtime parts (strings, dates, Unicode tables, only when used),
  the types, the tables of classes, the function prototypes, the bodies, main.
- Compiler version = spec version + "alpha" (0.0.9alpha).
- Nothing is freed to the system yet (strings, arrays, objects): see section 10.
- Source files: CodeGen/CodeGen.cs (core, statements, expressions), .Types, .Features (overloads, named arguments, definite
  assignment), .Errors (catch, throw, atEnd frames), .Switch (enums, switch), .Nulls (nullables, ?., enforce), .Tuples,
  .Stdlib, .Text (string/char/date tables), .DateTime, .Arrays, .Classes, .Traits, .Equality, .Exceptions, .Ownership, .Generics;
  Runtime.cs (always), RuntimeText.cs, RuntimeDate.cs, UnicodeTables.cs (optional parts).


2. Types and values
--------------------
- A type is a string in the compiler: "i32", "string", "arr<i32>", "Status" (enum), "Circle" (class), "i32?" (nullable),
  "(i32 id,string name)" (tuple), "*(...)" (several returned values).
- Unsuffixed integer literals have the native size CodeGen.NativeInt (i64, or i32 with a 32-bit cpu or --native-int 32); a literal that does not fit an i32
  takes i64 (spec 1.3). `int` is a type: Normalize maps it to NativeInt, as `uns` to NativeUns. The return type `int` of main gives an i32 exit code.
- Not available: i128/i256/u128/u256, r16/r128, dec, real, pointers, addr, vec/list/map/hmap/set/hset/dfoot, lambdas,
  imports, multiple files.
- Casts: out of range saturates; a float to integer cast truncates. (spec 3.5)
- `var`: for variables and for-loop items only; the type is the type of the value. Not allowed for fields.
- Strings (spec 4.4): a df_string is a pointer to the first allocation, NULL is "". The class is the low 4 bits of byte 0. Classes
  0-7: single block of 32 << class bytes (byte length in the high nibble of byte 0 and byte 1, chars in bytes 2-3, text at 4);
  11: literal, chars and bytes as two 32-bit words each at bytes 4 and 12, text at 20 (CString writes one static object per text,
  emitted before the program); 13: moved, pointer at byte 4 (read only, nothing moves yet). Every text ends with a 0. The runtime reads
  a string through df_view (pointer + byte length, type df_sv), df_str_len and df_str_chars; df_str_alloc / df_str_make build one in
  the smallest class. Until block strings exist, a string above 4091 bytes is a class 11 on the heap (bit 0x80 of byte 0: a literal
  of the program has it clear and is never freed).
- Ownership of strings (CodeGen.Strings.cs): a string local or parameter has a C flag o_<cname> (VarInfo.OwnFlag): true when it owns
  its string. Declarations and assignments set it from Expr.Fresh (StrNodeFresh: a call, +, an interpolation, a!, a literal are new;
  a name, a field, an item are borrowed); df_str_set frees the old string when owned. Declarations written 'string x' (and string
  parameters assigned in the body) get an implicit atEnd StrDrop, so every exit of the scope frees them. Fields (df_str_put, drop glue),
  items and tuple items (StrOwnedAs) always own: a borrowed value is copied. A function returns a string its caller owns (StrReturned:
  an owned local moves out, anything else is copied). Runtime functions never return their argument. A new string that is only read
  (operands, library and user arguments, conditions, receivers) goes through df_tmp; each statement that made some ends with
  df_tmp_drop(df_tm), the mark the function took when it started. Text builders use df_str_cat / df_str_catx (free the left part).
  DF_STR_TRACE (a define given to clang by hand) prints the strings alive at exit.
- Changes in place (spec 4.1, CodeGen.Strings.cs): the runtime works on a place (df_string* and the bool* of its flag; fields and
  items use df_str_owner). df_str_room makes room keeping the identity: a full allocation moves to a new one and the first allocation
  becomes class 13 (old class in the high nibble, for shrink); a literal or the empty string is never written, the place gets a new
  string. df_str_append (+=), df_str_set_char (text[pos] = c), df_str_clear, df_str_shrink; df_str_take puts the text of a new string
  (the result of s.trim()...) into the place and frees it. The compiler uses take for a changing method whose result is not used
  (EmitInPlaceStatement) or goes back to the same place (InPlaceAssign; SamePlace knows string b = a through VarInfo.AliasOf).
  StrPlace refuses const, parameters and loop variables (VarInfo.ReadOnlyString). Vec and list items are not places yet.
- Block strings (Runtime.cs, spec 4.4.4): df_sroot and df_sblock under #pragma pack(4) (layout checked by _Static_assert);
  df_str_make / df_str_concat / df_str_dup build one above 4091 bytes (df_bs_push*). Native: df_str_len, df_str_chars, df_str_fwrite
  (console), df_bs_char_at and df_str_set_char, df_str_append, df_str_splice_in -> df_bs_splice (insert, remove, replaceAt, prepend:
  seek from the cursor, the first or the last block; remove across blocks; insert in the block or split it; free an empty block; merge
  neighbours that fit; the cursor ends on the changed block), df_str_clear, df_str_become (a place takes a big new string: a block
  root takes its blocks, a smaller form points to it as class 13), df_str_shrink (repack, or back to a single block: the root becomes
  a class 1 when the text fits 59 bytes). Every other reader goes through df_view, which flattens a block string into a ring of 16
  copies (DF_FLAT_RING); a for loop over a string uses df_view_keep (its own copy, freed after the loop). The compiler calls
  df_str_splice_in / df_str_append directly for s.insert/remove/replaceAt/append/prepend on a place (DirectEdit).
- Strings in collections (step e): StrItemAs -> df_str_item(value, fresh) for every item stored (a new string in its smallest form is
  kept, anything else is copied by df_str_dup, which always gives the smallest form); item stores use df_str_put (the old item ends);
  DropListItem, EmitVecDropGlue (all the slots of the block) and EmitListDropGlue free string items; add(collection), copyFrom and
  fill copy every string; pop, ->c[i], takeAt and replace give the item (Fresh). StrGift: ->x on a string variable or field moves it
  (a borrowed one is copied); a parameter ->string owns its string (ParamSig.IsGift), which the vec and list library code uses.
  `text[i]` reads a character by position (IndexOutOfRangeException). Writing a character by index is an error (open in the spec).
- date is milliseconds since 1970 UTC (null = minimum i64); time is milliseconds since midnight (null = -1);
  clock and lapse follow the spec. date and time are nullable by default (`date?` is an error).


3. Standard library
--------------------
- Built into the compiler: Root.GetArgs, Console, Time (Now, Clock), Math / Math32 (constants PI, PI_HALF, E, SQRT2, R2D, D2R),
  Random (xoshiro256**, Seed, Int, Real, RealRange, Shuffle), string functions, char functions, date and time members.
- Call on a value: `s.Trim()`, `c.IsDigit()`, `d.addDays(1)`. Library functions take named arguments (caseSensitive: false) using the
  parameter names of the spec; `default` cannot be used as a name (it is a keyword).
- Characters are code points. All string indices (IndexOf, Substr, PadLeft ...) count characters, not bytes. IndexOf and
  LastIndexOf return -1 when not found.
- Case: ToUpper / ToLower map one character to one character (no special cases: the ß stays ß). Case-insensitive search compares
  lower(upper(c)) of both sides.
- Trim() removes white space, control and format characters. Trim(string c) treats c as a set of characters.
- Unicode data comes from the .NET database of the compiler and is written into the C file as range tables, only the tables used.
  No locale is used.
- Split with an empty separator gives one item (the whole string). Split keeps empty items.
- ToCStr: the array ends with a terminator (one byte for UTF8/ASCII/ISO88591, two for UTF16, four for UTF32). UTF16 and UTF32
  are little endian, the BE variants big endian. Characters that do not fit ASCII / ISO88591 become '?'. StringEncoding (and
  String.StringEncoding) is declared by the compiler when named.
- Program arguments: index 0 is the program name; on Windows they are read from the wide command line and converted to UTF-8.
  `main` forms: none, arr<string> args, string args...; return void or int (exit code). Having top-level code and main is an error.
- Random.Shuffle works on arrays and on string variables (the string is rebuilt and assigned back).
- Dates: all UTC. dayOfWeek is the enum DayOfWeek (Monday = 0); month/day/etc. are i32; a null date gives 0 for its parts
  (CHOICE). addMonths/addYears keep the day when it fits, otherwise the last day of the month. add* gives null when it overflows.
- date(string) and time(string) parse the default formats of section 9 and give null plus a silent InvalidDateTimeFormatException
  when invalid; time(i32) and (time)n give null plus a silent OutOfRangeCastException. parse(...) never raises.
- date - time and date + time give a date (3.3.2); time - time gives a date lapse in milliseconds. (3.4 says date - time is a lapse:
  contradiction in the spec, CHOICE: the 3.3.2 table and the changelog.)
- Date and time formats (8.4): d f F g h H k m M s t y z, and w q i r e j. CHOICES where the spec is short: k = hour 1..24;
  w = week of the year counting from January 1; z prints +0 / +00 / +00:00 (UTC); e = day of year, 3 wide, zero padded (doubled: space);
  doubled w and i pad to 2 with a space; j = 1 (Monday) to 7; quoted text in '...' or "..." and \ escape; a<20 a>20 a^20 align.
  A date-only letter used on a time is a compile error (when the format is a literal). Parsing with a format is strict and uses the
  same letters; two-digit years: 00-29 = 2000s, 30-99 = 1900s.
- Number formats (8.1, 8.2) and number parse are implemented for integers and reals (section 14). String formats (8.3) are NOT:
  `{x:spec}` on anything but numbers and date/time gives a warning and is ignored. tryParse is not implemented (it needs (&) parameters).
- Silent exceptions of library calls are raised only when a catch that can handle them exists in the same function (see 7).


4. Collections
---------------
- Only arr<T> exists: a pointer and a length, elements start zeroed. Literals need a declared type (`arr<T> a = [..]`, `arr a = [..]`);
  a literal is the right side of an assignment. `arr<T>[n]` creates; the declaration form `arr<T>[n] name` parses but is rejected.
- Supported: index read and write with a bounds check (IndexOutOfRangeException), .len, for-in, has, indexOf (maximum u64 when not
  found), fill, clear, reverse, printing as [a, b, c]. Not supported: sort, copyFrom, views and ranges, keys, add, insert.
- == between arrays compares identity; a null array has no pointer; `arr<T>?` is an error (arrays are nullable by default).
- Arrays do not own their objects (section 9).


5. Functions
-------------
- Overloading: exact type first, then the smallest widening in the same family; an integer literal prefers i64; ties are errors.
  Named arguments and defaults work for functions, methods and constructors.
- Variadic parameters (T name...): the extra arguments become an arr<T>; an existing array alone is passed as it is. Must be last.
- A function whose calls may raise is marked "failing": its callers check the error register. This is computed from the source
  (divisions, throw, index, calls) before generating code. In a program with classes it is deliberately wide: any member access
  on a variable (it may be null), any call by name that matches a method name, and any == / != when a class defines equality.
  A destructor that can fail makes every function failing.
- The first line of a function with one expression returns it (single-expression body).


6. Classes (spec 11.1)
-----------------------
- An object is a pointer to a C struct. The first member is the class descriptor (id, name, parent, vtable, print function,
  trait table, drop function). Fields follow, the parent's first (so an upcast is a pointer cast), then the fields of the traits the
  class adds, then the fields of the class. Objects are allocated zeroed; fields whose zero is not all-zero bits (date, time, enums,
  tuples ...) are set in the constructor.
- Names: a class cannot be named like a type, trait, enum, function or `Exception`. Words that cannot be names: step, alias, atEnd and
  the other keywords (e.g. a field called `step` does not parse).
- Constructors: ONLY the primary constructor (header parameters) or the default constructor. Secondary constructors, constructor chains,
  private constructors and constructor atEnd fragments give "feature not supported". Header parameters are private fields; a body
  declaration of the same name only sets its visibility (a different type is an error; an initializer gives a level 3 warning).
  Construction order: parent, traits (parent trait first), then the header parameters and the field initializers in order.
  An extended class cannot have header parameters in its parent (the child cannot pass arguments to the parent): CHOICE until decided.
  An object parameter in a header must be written ->T (the object moves into the field).
- Calling a constructor: a function with the name of the class. A function cannot be named like a class.
- Visibility: private (default), public, internal. internal behaves as public until namespaces exist. Private is checked at compile
  time: usable inside the class and in its subclasses (they see everything). Overriding functions take the visibility of the
  original, and writing one on an override is an error. Trait members follow spec 11.2 (see PRIVATE STATE IN TRAITS).
- Statics: fields, static const, functions. Stored in C globals; initialized at program start in dependency order (a static that reads
  another runs after it; a cycle is an error; dependencies are found in the initializer text, not through function calls).
  Statics are inherited (Child.create()); a static function cannot be overridden or redeclared with the same signature.
  The lazy-initialization option is not implemented. Statics are not tracked by ownership.
- Methods: all instance methods are virtual (a vtable per class); a call is direct when nothing overrides the function.
  `parent.f()` is a direct call. A function without a body is an error in a class (virtual and for traits only: decision of the user).
- Null: reading a field or calling a function on null (or on a destroyed object) raises NullPointerException. `this` is never null.
  `?.` works on objects. `==` on objects: see section 8. Objects cannot be converted to bool.
- Printing an object: `Name { a: v, b: v, c: v, ... }` (first three fields, one level; a nested object prints `Name{}`;
  no fields: `Name {}`; private fields are printed too). It uses the dynamic class.
- `x is Class` and `x is Class c` (c scoped to the block, only as the condition of if / if-then / else-if); a check that is always
  true (upward) is a level 2 warning. Downcast operators do not exist.
- Exceptions caused by classes inside a class body: nested types, secondary constructors, atEnd inside the body: errors.


7. Traits (spec 11.2) and exceptions (spec 15)
-----------------------------------------------
- A trait is registered like a class that is never created. A trait value is the object itself (void*). A call on a trait value finds
  the function in the table of the class of the object (one table per class and trait); a property is found by offset.
  Dispatch is always dynamic: `specific T` and `any T` are accepted and behave the same (specific is not enforced).
- Implementing: `override` is required for every function that answers a trait function, also for default bodies; a function
  inherited from the parent class counts; a missing implementation is an error; the return type must match.
- The same member in two traits: unqualified use is an error; TraitName.member inside the class calls the trait's own body (not the
  override of the class), x.TraitName.member outside sees the object as that trait.
- Not supported: trait constructors with parameters, a trait that redeclares a function of its
  parent trait, static members in traits, trait-typed `is` checks on non-objects.
- Exception classes: class E(fields) : Exception [, SilentException]. The object keeps the layout of the runtime exception record
  (after the class header), so the error register can hold it and a catch gets it back as the class. The constructor takes the message
  first (optional) and then the fields (optional, zero by default). Id = hash of the class name (>= 256). Message, Function, Id, Line are
  read-only members. A parent exception class with header fields cannot be extended yet. `Exception` is also a type (a variable can hold
  any exception; it can be tested with `is`). Catch variables have the type of the class they catch.
- SilentException is a trait the compiler declares when it is named. A silent exception that nothing in the same function can catch
  does nothing (execution goes on). A catch Exception never handles a silent exception; catch SilentException, its own
  type, a parent below Exception, and catch all do. Silent exceptions are not seen by catches in callers (limit).
- IDs 19, 20 and 24 are defined (IndexOutOfRange, ModifyingProtectedSource, InvalidDateTimeFormat); only some are raised by this version.
  IDs 21 to 23 (NaNUsedAsKey, InvalidMapKey, EmptyVectorAccess) were retired by the spec on 2026-10-20 and removed from the compiler; they are not reused.
- An unhandled exception prints its message and `Panic -1000`.


8. Equality (spec 11.1.3)
--------------------------
- Order for a == b with an object on the left: equals, then the operator `fun bool ==(V other)`, then identity. != is the negation.
- Null is handled before either function runs (they never receive null): a null side gives an identity comparison.
- `override fun bool equals(T other)` is written with override (Root.Class has equals). It is generic: the compiler makes one copy
  for each type T of the right operand. `T is type` is decided at compile time (the other branch is not emitted); `other` has the type T
  inside the copy (this is how "binding in generic checks" is solved: undecided in the spec, CHOICE). `other is Type` is a runtime
  check. Every path must return a value (checked on the text even if unused, and again for every copy).
- Which copy runs is chosen at run time by the class of the left operand, through one table per T (one entry per class).
  A trait-typed left operand compares by identity. The operator `==` is an ordinary virtual function.
- Warnings: level 2 when a class has both equals and the operator; level 3 when a later check can never run for a T because an
  earlier one already matched and returned.


9. Ownership (spec 12, 12.4, 14.2) - only the first part (4a)
-----------------------------------------------------------------
Owner or borrow is decided where a variable is declared:
- `T x = new object / result that moves / ->y` : x owns. `T x = y` (a variable, field, parameter): x borrows.
  `T x` without a value, `T x = null`: x owns. `T x _= y`: x is a weak reference.
- Fields own. Parameters borrow, unless written ->T x (the callee owns; the call writes ->y or gives a new object).
- A function that returns objects either always moves (a new object, ->x, or one of its own owner variables, which is moved out)
  or always borrows (a field, a parameter, another variable). The compiler classifies each function from its return statements (by
  names, then checks the real return statements) and every function that shares a virtual slot or answers a trait function must agree.
  The result of a call is a new object only for constructors and moving functions.
- Rules (errors): an owner cannot be assigned an object that something else owns (use ->x or a new object); a borrow cannot receive a
  new object; a weak reference is read only through enforce and assigned only with _=; `->` works on owners and on fields of an object
  the code owns (a field of a borrowed object cannot be moved out); `->this` is an error; `x is atEnd.` needs an owner;
  `->` on a basic value is ignored with a level 1 warning.
- Ending: when a scope ends (normal end, return, break, continue, jump, exception passing) its owners end, last declared first, after
  the written atEnd blocks. A loop body that declares objects is wrapped as a block so each pass ends its objects. A function's
  `} atEnd { }` runs as the final cleanup (after the written ones, before the objects). `atEnd of a, b { }` is a scope atEnd (the names
  are not used). A new value assigned to an owner ends the old object. A call used as a statement ends the object it returns.
- Ending an object: the destructor (the atEnd after the class) of the most derived class, the objects it owns, then the parent's
  destructor and objects; then the object is marked dead (its descriptor is replaced) and keeps its memory.
  A dead object: member access raises NullPointerException; enforce on a weak reference to it fails; ending it again is a Panic
  ("Double free", exit -1000). A destructor that throws propagates from the end of the scope like any exception.
- Not implemented: temporaries inside expressions (never ended), objects held by arrays and tuples (not owned, never ended), static
  fields, constructor atEnd fragments, atEnd after statements other than functions and classes (form 3, an error), reference counting,
  .clone(), x!, compile-time use-after-move, lifetimes (a borrow can outlive its owner; it then finds a dead object when used).
- Memory is never given back. Safety against use after end comes from the dead mark, not from freeing.


10. Errors and atEnd (spec 14.2, 15)
------------------------------------
- Exceptions use an error register (df_err): a failing function returns normally with it set; the caller jumps to its catch or
  returns. Catches handle everything above them in their block, in order; a catch with no type is `catch all` with a level 2 warning.
- Silent exceptions of the runtime (Overflow, OutOfRangeCast, InvalidCharacterCodePoint, 21 - 24) do not match `catch Exception`.
- The old standalone `atEnd { }` on a line of its own is still accepted as a scope atEnd (the spec removed that form).
  Trailing `} atEnd { }` is attached by the parser to the statement it follows; the compiler accepts it for functions and classes.
- An error raised by an atEnd block at the normal end of a scope keeps propagating through the earlier blocks; an error raised while
  another exception is passing is a Panic.
- Loop bodies: legacy atEnd blocks in a loop run once after the loop (only if the body ran); objects end every pass.


11. Parser changes made with the compiler
------------------------------------------
- T name... (variadic after the name), arr<T>[n] as an expression and as a declaration, `static`, trailing atEnd, atEnd of,
  `f is atEnd.` (statement only; the dot ends the statement even at the end of a line), `fun bool ==(V o)` (`!=` is rejected).
- Reserved words that surprised me: step, alias, atEnd, static, default.


12. Summary of the main limits
-------------------------------
- Generics: see "Generics" below (functions, classes, traits, value parameters, placeholders, type switch are built; collections are not).
- No collections other than arr, lambdas, pointers, references, imports, namespaces (the line is a comment).
- Classes: primary constructors only; no parent constructor arguments; no secondary constructors.
- Ownership: single owner and weak references only; no reference counting, clone or copy; borrows are not lifetime checked.
- Library: no string formatting, no tryParse, no files.
- Memory is never freed.


13. Generics (spec 11.3) - phase 7a
------------------------------------
STATE (2026-10-17): built and tested. dfcompiler/tests/generics.df compiles and runs with the expected output; the 30 older tests
give exactly the same output as the compiler before 7a (checked by building the previous commit and comparing). The error cases
(constraint not met, bare generic class, no inference, set used as a type, two types for one parameter, too many type arguments,
copy limit reached) give clear messages. Two fixes were needed after the first build: a header parameter written ->Item is a gift
only when the type is an object (for a number it is a plain copy, so Box<i32> works); the test uses "Item rest..." (the variadic
mark goes after the name) and "return" for a body with several statements.
(Rule from the user: never build without explicit approval.)

Where the code is
- dfparser/Parser.cs: inline constraints and 'where' can be mixed (the old "not both" error is gone); "Generic Name { ... }" is
  parsed to a GenericSet node (ParseGenericSet); "Stack<i32>.member" is accepted in TryParseGenericArgs (a '>' followed by '.').
- dfcompiler/CodeGen/CodeGen.Generics.cs: everything generic (templates, sets, constraints, inference, copies, limits, Compile()).
- Small changes in: CodeGen.cs (Generate calls RegisterGenerics before DeclareClasses, CheckClassInstances after RegisterClasses,
  generic functions go to RegisterGenericFun; Path() and Call() understand GenericRef; the emission loop works on a snapshot;
  FunSig has InstanceDepth / InstanceChain; "ResolvedType" is a type node kind), CodeGen.Types.cs (ResolveType: ResolvedType,
  generic class use, a set used as a value type is an error), CodeGen.Classes.cs (no more "Generic classes" error, names that clash
  with sets, display names in printing and in the class descriptor, IsParts accepts ResolvedType), CodeGen.Errors.cs (failing
  analysis knows generic names), CodeGen.Ownership.cs (CallMoves and ObjectTypeOf know generic calls), Program.cs (uses
  CodeGen.Compile; Version is 0.0.9alpha).
- dfcompiler/tests/generics.df: the test program (the errors it should give are listed in comments at the end).

How it works
- A generic function or class is a template (a tree). A use with concrete type arguments copies the tree, replaces every use of a
  type parameter by a "ResolvedType" node (its text is the type string) and registers the copy as an ordinary function or class with
  a mangled name: min<u8> -> min__u8, Stack<i32> -> class Stack__i32. A class copy prints as Stack<i32> (displayNames). Nothing
  generic reaches the C code.
- Functions: copies are made while the program is compiled, when a call is compiled (InstantiateForCall -> InstantiateFun). A copy
  is registered in funs, marked as able to fail (so callers always check the error register: wide on purpose, like section 5),
  classified for ownership (Classify), and put in the pending list that Assemble compiles (the same list the equals copies use).
  Any call to a generic name also makes the caller able to fail (FindFailingFunctions).
- Classes: a copy must exist before the classes are declared, but the compiler only finds out which copies it needs while compiling.
  So: when a type Stack<i32> is resolved and its copy does not exist, ClassInstanceName adds it to the seeds and throws
  NeedInstanceException; CodeGen.Compile() catches it and compiles the whole program again from a fresh clone of the tree (the seeds
  survive between attempts; RegisterGenerics turns each seed into a class node before DeclareClasses). A program with N generic class
  copies is compiled up to N + 1 times. The tree is cloned for every attempt because AddPrelude changes it.
  NeedInstanceException is not a CompileException on purpose, so the "catch (CompileException)" blocks do not swallow it.
- Type arguments are inferred from the arguments only (not from the return type or from the target). The declared type of each
  parameter is matched with the type of the argument: T, arr<T>, tuples, Stack<T>, T... (variadic), named arguments. If one
  parameter gets two types, the wider one is taken when the other converts to it, otherwise it is an error. Written type arguments
  may be fewer than the parameters; the rest is inferred. A parameter that cannot be inferred is an error that says to write it.
- A set used as the type of a parameter (Numeric first, Numeric second): that parameter gets a type parameter of its own (named
  _first), constrained by the set. So average(Numeric a, Numeric b) is one copy per combination actually called.
- Constraints: a trait, a class or a set, joined with && (all must hold). Checked when a function copy is made, and for class copies
  after all classes are registered (CheckClassInstances), because classes are not known earlier. A class member of a set accepts
  its subclasses; a trait member accepts every implementer. Inline and 'where' constraints can be mixed: the same constraint twice is
  an L1 warning; a different one in 'where' on a parameter that already has inline ones is an error (join it with &&).
- Sets: "Generic Name { types }" at the top level, uppercase name, members are types, classes, traits or other sets. A set used where
  a value type is expected is an error (it only names alternatives). Predefined: Signed, Unsigned, Integers, Reals, Numeric, Strings,
  but only with the types this compiler has (no i128/i256/u128/u256/r16/r128/dec/int/uns/real yet).
- Limits of 11.3.12: MaxCopies = 16 copies per generic, MaxChainDepth = 16 for copies made by copies (functions: the chain is
  printed) and for the nesting of type arguments (classes). They are properties of CodeGen; there is no command line option yet
  (the names of the options are an open item in the spec). The limit for library collections (64) does not exist yet (no collections).
  The message follows the spec: "Generic X defined in line N was used with more than 16 instances in function F".
- Static members: one copy per instance, because each instance is a class of its own (Stack<i32>.Bump() and Stack<string>.Bump()
  do not share anything).
- T? in generic code is an error when the type parameter is replaced (spec 11.3.8); nullable types are listed in sets instead.

CHOICES where I (Claude) decided and the spec does not say, and limits of this version
- The body of a generic is NOT checked at the definition (the spec says it is: the Rust model). It is checked in every copy, so an
  error appears with the first type that reaches it, and a generic that is never used is never checked at all.
- Supported: generic functions at the top level and generic classes at the top level. NOT supported (error "feature not supported"):
  generic methods, a class implementing a generic trait twice, a trait with both <T> and placeholders, a generic parent (class A<T> : B<T>), 
  'where' on a type expression (only Source.Item is built),
  Box<Dog> -> Box<Animal> conversion. These are phase 7b.
- Value parameters (11.3.3, built 2026-10-18): <u64 Width, bool On> on classes and functions. The type is an integer or bool (char, reals and dec give
  "feature not supported"). A value argument is kept as the string "#12" / "#-3" / "#true" next to the type names, so it is part of the mangled
  name (Grid___4_3_i32 style) and of the copy limits. A written argument is a number, true/false or + * << of numbers (saturating, unsigned, EvalConstant);
  it must fit the type. In a copy the parameter name becomes the literal: as a value (Name node -> Int/Bool/Neg) and as a type argument (Type node ->
  ValueArg), so arr<Cell>[Width * Height] and Grid<N, 2, i32> inside another generic work. A function infers a value parameter only through a
  generic class argument (Grid<N, 3, i32> g); otherwise it is written: sizeOf<3>(0). A local variable with the name of a value parameter is replaced too.
- 'where' on a class header (built 2026-10-18): the parser reads it after the bases; ReadTypeParams already handled the entries. 'where' on a class
  without type parameters is an error.
- Type switch (value is ? { Numeric: a, char, string: b, default: c }), built 2026-10-18: node TypeSwitch (subject + Arm like a switch expression, labels
  are types). TypeSwitch() in CodeGen.Generics.cs takes the static type of the subject and compiles ONLY the first matching arm (a set, a class with
  its subclasses, a trait, or a type); no match and no default is an error, checked in each copy (not at the definition). The L2 warning is only for a
  repeated label or a case after default (a case already covered through a set is not detected).
- Generic traits (C1, built 2026-10-18): a trait with <Item> is a GenericClass (IsTrait) and is copied like a generic class: RegisterGenerics puts a
  Trait node named Container__string in the program, ClassInstanceName makes the name (restart through the seeds). RegisterClasses turns Container<string>
  in a class header into the copy; a trait copy as a constraint (Source : Container<i32>) is resolved with the arguments of the copy
  (CheckConstraints/Satisfies). Two copies of one generic trait on a class: "feature not supported yet". Parent generic traits: not in the language.
- Placeholders (C2, built 2026-10-18): a trait with 'placeholder Item' is a GenericClass with HasPlaceholders whose Params are the placeholders; the class header
  'Sequence with (Item is u32)' gives the arguments and the copy Sequence__u32 is made like any generic trait copy (Item? in it stays as it is for
  string and classes, SubstituteTypes allowNullable). The bare trait name is only a constraint: Satisfies = the class implements a copy of it. 'where Source.Item : C'
  is stored in TypeParam.PlaceholderConstraints and checked in CheckConstraints with PlaceholderValue (the type the class fixed). Inside the generic
  body Source is the concrete class, so items.Next() is an ordinary call. A sequence of string cannot end with null (a null string is empty).
- Conversion of a value to a set member (D, built 2026-10-18): only in a constructor call of a generic class, Box<Num>(x): GenericRefClass(reference, args, scope)
  evaluates the arguments that mention the parameter (ChooseSetArgs, PatternPairs on the PrimaryCtor), then ChooseSetMember applies the order of 11.3.9: the
  exact type, the same macrotype that holds it (Assignable, leftmost), any member it converts to (Assignable); classes: exact, nearest parent, then
  members left to right (traits too). Not built: a set in an explicit generic function call f<Num>(x), a declared variable with a set argument (error),
  secondary constructors as the source of the value. Fixed 2026-10-18: 'var f = Foo(n)' with n a variable of the same scope failed with "unknown name 'n'" when the scope had implicit drops: HoistDeclarations
  typed the vars in the parent scope. It now types them in a scope that holds the variables declared before (TypeForHoist, with a dummy exception label
  because the frame is not open yet); test varobjects.
- Type arguments of a class are always written (Box<i32>(5)); a constructor call does not infer them.
- A generic function cannot have the name of another function (no overloading between generic and plain ones).
- The "unconstrained T is move-only" rule of 11.3.11 is not checked at the definition. ->Item on an object moves it, on a number it
  copies (a constructor header that takes ->Item works for both).
- Whether a call of a generic function gives a new object (moves) is guessed from the returns of the template (TemplateReturnsMoves);
  the copy is then classified for real. If both disagree, the usual ownership errors can appear.
- The L1 warning "-> on a basic value" is repeated for each copy that has a number there (open item in the spec, 99).
- A generic function copy is always "failing" (see above); this only costs extra checks, not correctness.
- Nothing from section 99 of the spec is implemented (the user said it is for later): sets inside a class, a variable declared with a
  set as type argument, conversion of borrowed generic values and collections, 'where' on class and trait headers, nullable
  edge cases in sets, '->' warning inside generic code, names of the compiler options for the limits, the exported intermediate form.
- Default type arguments, specialization and T? are not in the language (11.3.13), so they give errors.

- Index checks: IndexOutOfRangeException in every build (the Debug / Release rule of 6.1 needs the --debug / --release options, not built).
- Known limits: see the NOT yet list in CompilerStatus.txt (7c).

14. Number formatting and parsing (spec 8.1, 8.2, 9) - integers and reals
--------------------------------------------------------------------------
STATE (2026-10-17): built and tested with dfcompiler/tests/numformat.df (every line of the test has its expected text in a comment) and
the 30 older tests (same output as before). Silent exceptions of parse were checked with catches in the same function.
NOT done: tryParse (needs (&) parameters), dec, string formats (8.3), formats in {x:spec} for anything but numbers, dates and times.

Where the code is
- dfcompiler/RuntimeNumber.cs: the C runtime, added to the program only when it uses a number format or parse (chunk "numfmt", which
  also brings the "text" chunk: UTF-8 helpers and the string builder).
- dfcompiler/CodeGen/CodeGen.NumFormat.cs: toStr(format) and {x:format} for numbers (NumberFormat), the compile-time check of literal
  formats (NumberFormatProblem for a spec, CheckParseFormat for a parse format), and the registration of T.parse (AddNumberStdlib).
- Small edits: CodeGen.DateTime.cs (FormatCall and FormattedHole send numbers to NumberFormat), CodeGen.Stdlib.cs (SilentCall takes
  several exception names; parse formats written as literals are checked), CodeGen.Text.cs (the new chunk), CodeGen.cs (warning text).

How it works
- Formatting: df_nf_parse reads the spec into a df_nf struct (the same grammar is repeated in C# in NumberFormatProblem, only to
  report errors at compile time; if you change the grammar, change both). A number becomes decimal digits (digs, no leading or
  trailing zeros, value = 0.digs * 10^dp): integers from the magnitude, reals from the shortest round-trip digits (no D size) or from
  all the exact digits of the double (D size given, so rounding is right: 2.5 is a true tie, 0.1 is not). Then df_nf_round applies the
  mode (u half up = away from zero, b banker's, c toward +infinity, f toward -infinity, t truncate), then layout.
- A spec that does not parse at run time gives the default text of the value (a literal spec is a compile error instead).
- Parsing: df_parse_<type>(text, default), _f(text, default, format), _fmt(text, format); one set per integer type and r32, r64.
  No format: skips everything up to the first digit (or ".digit"), a '-' right before it is the sign, reads digits, an optional
  ".digits", for reals an exponent; NaN, INF and the infinity sign are read by reals only. With a format: prefix, placeholders
  (alternatives tried in order, the first that matches the whole text wins), suffix; nothing is skipped except fill characters
  when a width, fill or alignment is given. Any invalid format gives the default.
- Out of range saturates and leaves a silent OutOfRangeCastException; a minus on an unsigned type gives 0 and a silent
  OverflowException. A parse call raises only the one a catch of the same function can handle (SilentCall tests the note).

CHOICES where the spec is short or unclear
- Option letters are case-insensitive except h / H after b. Separators and fill characters can be any character that is not an
  ASCII letter (a digit is allowed as fill: f0). Anything else in a spec is an error (spaces too).
- D: optional symbol (any non-letter non-digit; l = locale = '.'), size digits (0 alone = no decimals, 0n = exactly n, n = up to n),
  then an optional rounding mode letter u b c f t. So after the size, f / b / t are read as modes: to follow D with a fill or a
  base, put another option in between (w10f0D2 is fine, D2f0 is floor then an error). Integers accept D too (5 with D02 is 5.00).
- Sign: S or S- negatives only (default); S+ always (zero too); St- / St+ the sign at the left edge of the width; S() negatives in
  parentheses. With the default the sign sits next to the digits, so the fill comes before it (000-42).
- Width counts characters; the default alignment of numbers is to the right; a^ puts the extra fill on the right. a. aligns the
  decimal symbol by adding the missing decimal places on the right (it only has an effect with D size, not fixed).
- Grouping g<sep><size>[<size><sep>...]: sizes are one digit (1 to 9); the separator after each group is the one written with it;
  the last group size repeats; a trailing r groups from the left (1234567 with g_3r is 123_456_7); gL is ',' and 3. Grouping applies
  to the integer digits (and to the digits of the other bases).
- Other bases: bh / bH / bb / bo / b64 show the raw bits (negative numbers by their width, reals by their IEEE bits); there is no
  sign; zero prints 0 (A in b64); b64 uses A-Z a-z 0-9 + / without padding.
- Scientific e[lit]0n: the text in lit is printed before the exponent; '+' inside lit marks where the exponent sign goes and makes it
  always shown, '-' marks the place with the sign only on negatives; no marker = at the end of lit, negatives only; \\ escapes. A
  negative exponent always gets '-'. 0n pads the exponent digits with zeros (after the sign), #n with spaces (after the sign too).
  Plain e = e[e+]D6a<. Without D, 6 decimals (up to). Zero prints 0. The mantissa has one digit before the decimal symbol.
- Rounding to zero never leaves a minus sign (-0.004 with D2 is 0).
- NaN, the infinity sign and null (a nullable without a value) take width, fill and alignment; the infinity sign takes the sign.
- A real with a format is printed in plain digits, never as 1E+20 (the format-less toStr() is unchanged).
- parse: the format of the spec example "{S}{S()}" reads both -10 and (10) as -10. Group separators are accepted between digits
  without checking the group sizes. A scientific format needs its text and exponent digits exactly. Hex and the other bases read the
  raw bits (ffffffd6 as an i32 is -42). A format with no placeholder, two groups of static text, or an invalid spec is an error at
  compile time when it is a literal, otherwise the default is returned.
- parse signature: parse(text, default = 0, format = none), also parse(text, format) as a named form (text:, default:, format:).
  A second argument that is a string is the format.

Root.IO.File (spec 17.6.3 to 17.6.6)
STATE (2026-10-17): built and tested with dfcompiler/tests/files.df (a scratch folder in the temp directory, removed at the end).

  modes follow the table of 17.6.4; an I/O failure while writing is NoMoreResourcesException (CHOICE: the usual cause is a full disk).

tryParse and the order of interpolation (2026-10-17)
- Interpolation: with two or more holes each hole goes into a temporary first, so they run left to right (C leaves the order of
  function arguments open; clang on Windows went right to left). One hole, or only text, is generated as before.
- T.tryParse(text, (&)result[, format]) for integers, reals, date and time (TryParseCall): the library takes the address of a plain
  variable (the call must write (&), the type must match exactly, not const; named arguments text, result, format). It is NOT the
  general reference parameter: your own functions still cannot take (&) parameters. The variable counts as assigned afterwards.
  CHOICE: a number that does not fit the type is a failure (false, variable unchanged, no silent exception), as in C# TryParse;
  parse still saturates. Negative text for an unsigned type is a failure too. date and time: the null result is the failure.


String formats, spec 8.3 (2026-10-17)
- {text:spec} and text.toStr(spec) for strings (CodeGen.StrFormat.cs checks literal specs at compile time; RuntimeStringFormat.cs, chunk
  "strfmt", does the work and brings the "text" chunk and the Unicode table of white space). A spec that is not valid at run time leaves
  the text as it is (like numbers give the default text). A null string is "" and is padded like any other.
- Order of the options (CHOICE, the spec only lists them): trim (s, sl, sr), case (cU cL cS cT), quote (q), truncate (t), then width, fill
  and alignment. Default alignment is left. Options may come in any order and may repeat (the last wins); letters are case-insensitive.
- w<n> counts characters (code points); wc<n> counts display columns: 0 for combining marks and zero-width characters, 2 for the main
  East Asian wide and emoji ranges (an approximation of East Asian Width, CHOICE), 1 for the rest. A width never cuts the text.
- t<'marker'> keeps the start, t>'marker' keeps the end; the marker counts in the width and is written between single quotes (\' and \
  stand for themselves); it needs a width; a marker wider than the width is cut to the width. Text that already fits is left alone.
- cS (sentence) capitalizes only the first letter and lowers the rest (CHOICE: no capital after a full stop); cT (title) capitalizes the
  first letter after every white space and lowers the rest.
- q writes a Dflat string literal: \" \ \n \r \t \0, other control characters as \u{HEX}; braces are not escaped.
- A fill character cannot be a letter (a digit can); in wc mode a fill of width 0 is ignored.


Array sort, sortUnstable and copyFrom, spec 6.6 (2026-10-17)
- arr.sort() / sort(SortDirection.ASC | DESC) is a stable merge sort (a temporary buffer); sortUnstable is a heap sort (no extra
  memory) (RuntimeSort.cs, chunk "sort"). SortDirection { ASC, DESC } is declared when the program names it (AddPrelude).
- Default order (CHOICE where the spec is short): numbers, char and enums (by value) as numbers; bool false before true; strings by
  code point (a byte comparison of the UTF-8, so "Apple" < "apple"); date, time null first (the null is the minimum value); a real NaN
  last. Descending reverses the order but keeps equal items in their original order (stable). Objects and tuples have no default order yet.
- sort(lambda) is "Lambdas not supported yet" (no lambdas).
- copyFrom(dstIndex, source, srcIndex, count) and copyFrom(dstIndex, source, range) (a..b, a..=b, ..b, a..): a range that does not fit
  either array, or a negative index, raises IndexOutOfRangeException (not detected at compile time yet; the spec wants a compile error
  when it can be seen); the same array as source and destination is a compile error when both are the same variable, otherwise
  ModifyingProtectedSourceException at run time. dstIndex may be the length (count 0). Arrays of objects are refused (items would be cloned).


Reference parameters, spec 13.1 (2026-10-17)
- &T x is a read-only reference, (&)T x a writable one. In C both are pointers (const T* and T*) named p_x; the body sees the variable as
  (*p_x), so reads, writes, +=, ++, array methods and passing it on all work unchanged. A read-only reference is const in the body.
- The call: &T takes any value, no marker (a variable by its address, other values through a temporary, so literals and expressions
  work); (&)T needs (&)x in the call and takes a variable, a field (obj.f, this field), a tuple field or an array item (a[i], with
  its bounds check); the type must be exactly the parameter's type; a const variable is refused; the variable counts as assigned
  afterwards. A (&) on a plain parameter, or a missing (&), is a compile error. A writable reference cannot have a default value.
- Overloads: the (&) in the call is ignored for the choice of the function (the type of x counts). A reference parameter and a copy
  parameter of the same type are the same signature.
- Objects: a reference to an object (&Item o, (&)Item o) is the object pointer itself. (&)Item o still requires (&)o in the call. It does
  NOT yet let the function replace the caller's object (CHOICE: ownership of the variable is not touched); it is a writable borrow
  for changing fields and calling functions.
- Not done: reference parameters on constructors (error), volatile &T (error), variadic references (the parser refuses), references stored
  in variables or returned (the spec has none), compile-time proof that the reference does not outlive the variable.


EXCEPTIONS: THE MODEL (final design, 2026-10-17; NOT BUILT YET; to be merged into the language specification, section 15)
=========================================================================================================================
Status: this is what the compiler will do. Today (0.0.9alpha) non-silent exceptions use a global error register (df_err) and silent ones a
one-slot note (df_silent_desc) that only a catch of the same function can see. Everything below replaces that. The syntax of the language
does not change.

1. Principles
- An exception is a value that a function returns next to its result, as in Rust: one slot for the result, one for the exception. There is no
  unwinding and no global error register. After a call, the caller looks at the exception slot: it handles the exception, returns it to its own
  caller, or (for a silent exception nobody observes) does not even look.
- A silent exception is an exception with a flag. It is created, passed back and checked exactly like any other exception, but only where
  somebody observes it (rule 5). Where nobody does, ALL the code for it is removed: no trapping, no exception record, no passing back.
- atEnd blocks and destructors are not changed. They run on the normal path and on the exception path as they do now.

2. Which catch observes an exception
- A catch handles an exception when the exception is of the class the catch names or of any subclass of it. This is the same rule for silent and
  non-silent exceptions.
- Exception is the root of all exceptions: "catch Exception e" (and the bare "catch e", which means the same) is the sinkhole and handles every
  exception that is not silent: it does NOT handle silent exceptions (spec 15.1, 15.4, 15.8.2).
- SilentException is meant to be a trait that every silent exception class implements. "catch SilentException e" handles every silent exception and
  no other. The definition of the trait is still open (it is declared by the compiler today).
- "catch all" handles everything, as it does today. A catch for a parent class handles all the silent children of that class too.
- Catches of a function are tried in the order written; the first that matches handles the exception.

3. Kinds of function (decided by the compiler; there is no safe keyword)
- PURE: can raise nothing at all.                            Signature: the result only.
- SAFE: no non-silent exception can leave it, and the silent exceptions it can emit are not observed by the call (see 5 and 6).
                                                             Signature: the result only. Callers never check it.
- FAILING: a non-silent exception can leave it, or a silent one that the call observes can.
                                                             Signature: the result and the exception (see 4).
- A function can raise when it contains a throw, an operation that raises (integer / and %, array and string indexing, access to a null
  object ...), or a call to a function that can raise.
- A non-silent exception that is fully handled inside the function and cannot get out of it counts as not emitted by the function. Every point
  of the function that can raise it must be covered by a catch that handles it (rule 2), and the catch bodies must not raise a non-silent
  exception themselves (no throw of one, no call that can raise one that escapes). Example, a SAFE function:
      fun i64 safeDivide(i64 a, i64 b) {
        return a / b
        catch DivisionByZeroException { return 1 }
      }
  The division raises DivisionByZeroException, which is not silent, but the catch covers it and the body of the catch cannot raise: nothing
  leaves the function, so callers do not check it. Without the catch, or with a catch for another class, the function is FAILING.
- Virtual functions and trait functions: a slot is SAFE only if all its implementations are SAFE (one FAILING override makes the slot FAILING).
  PURE needs the same: all implementations.

4. How a FAILING function returns (the Rust model)
- Two slots: the result and the exception. The exception slot is a pointer to the exception record, null when there is none.
- A function without a result (void) returns only the exception slot. Several results or a tuple are one result slot.
- Call site: call, then "if the exception slot is not null": run the matching catch of this function; if there is none, return the exception to our
  own caller (this function is FAILING), after the atEnd blocks of the scopes left have run. An exception that nobody handles reaches the top of the
  program: Panic, as today.
- Non-silent exceptions go up the call chain to the first matching catch, as today.

5. Silent exceptions: who observes them
- A silent exception of class X emitted by function F is observed by a call statement of F's caller when that statement is covered by a catch of the
  caller that handles X (rule 2). "Emitted by F" means: raised by one of F's own operations (for example the + that overflows), thrown by an explicit
  throw in F, or declared by a library function that F calls directly (rule 8). It is NOT what F's own callees emit (rule 6).
- If no catch of the caller handles X, the call returns as if nothing had happened (spec 15.4: execution continues) and nothing is generated for X.
- A catch in the function that contains the emitting operation itself handles the exception as an ordinary local exception (same rule, the function
  being its own caller).
- Example, a function that can only overflow silently is SAFE for callers that do not catch it:
      fun i64 add(i64 a, i64 b) { a + b }

6. Silent exceptions never go up on their own
- If F calls G and G emits a silent exception that F does not observe (no catch of F handles it), the exception is ignored in F. F's caller does not see
  G's exception, even if F's caller has a matching catch.
- To send it up, F catches it and throws it again, explicitly:   catch OverflowException e { throw e }
  The new throw is F's own emission, so F's caller observes it (when it has a matching catch), as rule 5 says.
- Example:
      fun i64 mul(i64 a, i64 b) { a * b }                   // can overflow: silent
      fun i64 add3(i64 a, i64 b, i64 c) { mul(a, b) + c }   // no catch: the overflow of mul is ignored here
      fun i64 use() {
        return add3(1, 2, 3)
        catch OverflowException { return -1 }               // sees only the overflow of the + in add3, never the one of mul
      }

7. Variants (how the silent code is stripped) [BUILT AS A RUN-TIME MASK: see EXCEPTIONS STAGE 2 at the end]
- A function that can emit silent exceptions is compiled once for every MASK its call sites ask for. The mask of a call site is the set of silent
  exception classes, among those the called function can emit, that are handled by the catches covering that call statement in the caller.
  A call outside any catch has the empty mask. A catch SilentException or a catch all covers every silent class the function can emit; a catch Exception does not.
- Empty mask: every silent path is removed from that version. If the function can raise nothing else, that version is SAFE (plain signature).
- Non-empty mask: the silent classes in the mask are treated like any other exception in that version, which is then FAILING.
- Masks do not flow down: the mask of the calls a function makes comes from that function's own catches (rule 6).
- Virtual and trait calls: every implementation of a slot is compiled with the union of the masks of all the call sites of that slot.
- The number of versions stays small: a mask can only contain silent classes that the function can emit and that some catch of the program handles.

8. Library functions: black boxes with declared exceptions
- The compiler does not look inside a library function (today they are C code of the runtime; later some will be written in Dflat). What it needs is the
  list of exceptions each function may raise, silent and non-silent. That list is in the standard library specification (Libraries/StdandardLibrary/dflat-stdlib.md): every
  function is listed with the exceptions it may throw. The compiler keeps the same list in its library tables.
- A function that lists nothing (for example Math.sqrt) is PURE. A function that lists non-silent exceptions makes its caller FAILING (unless the caller handles
  them all). A listed silent exception is observed through the mask of the call like any other (rule 5).
- The C code of the runtime reports an exception in a temporary slot between its return and the wrapper that the compiler generates at the call site; the
  wrapper moves it into the exception slot. The temporary slot is never visible to the program and is empty between statements.
- When a library function is rewritten in Dflat, it follows the rules above and must propagate what its specification says it propagates: an exception
  declared for the function is emitted by the function itself, or caught and thrown again explicitly (rule 6). A helper that throws for its caller is not enough.
  File and FileStream are written in Dflat today and must be changed this way (their silent exceptions, for example FileAccessException, must be emitted by the
  public function the user calls).

9. What does not change
- The syntax: throw, catch, catch all, catch by class, rethrow, exception classes, Panic and exit codes.
- atEnd blocks, destructors and scopes: same order, same guarantees.

10. Open points
- The exact definition of the SilentException trait.
- Whether library functions without a declared list in Libraries/StdandardLibrary/dflat-stdlib.md (only the IO section lists "raised by" today) need to be completed before the model is built.
- (closed) Spec 15.4: a catch of Exception does NOT handle silent exceptions. The compiler follows it since 2026-10-17.

11. Plan and tests (for when it is built)
- Stage 1: the two-slot return for FAILING functions (replaces df_err), the PURE / SAFE / FAILING analysis (including fully handled exceptions).
  Non-silent behaviour must not change: all existing tests must give the same output.
- Stage 2: masks and variants, the silent rules, the library tables with their declared exceptions, File and FileStream moved to explicit re-throws.
- Tests: safeDivide (called from code that does not check it); the mul / add3 / use example, with and without the catch in use; add with and without a catch;
  a silent exception class thrown by a user function; re-throw with "throw e"; catch Exception and catch SilentException observing silent exceptions; a virtual slot
  with a SAFE and a FAILING override; a trait call; a generic function used with and without a catch; every library call that raises silently.


EXCEPTIONS STAGE 1: BUILT (2026-10-17)
=======================================
Built: rules 2, 3, 4 and 8 of the model above (pure / safe / failing functions, the result + exception return, fully handled exceptions).
Not built: rules 5 to 7 (silent exceptions seen by callers, masks and variants, library declarations): silent exceptions still behave as
before (raised only where a catch of the same function handles them).

How it works in the generated C
- Every function has its own locals df_err and df_err_thrown (CodeGen.Errors.cs, FunctionContext); the catch, dispatch and atEnd code is the old
  code working on these locals. The global df_err is gone.
- A FAILING function returns its result and its exception: a struct df_resN { value; err } (CodeGen.ExcFlow.cs, ResultPair), or just the exception
  (df_exception*) when it has no result. Constructors return the object with the exception the same way. A PURE or SAFE function returns its result only.
- A call to a failing function: PairCheck looks at .err, moves it into df_err and jumps to the handler of the scope (UserCallCode).
- The C runtime and the destructors cannot return a pair: they leave the exception in df_pending (Runtime.cs, df_raise). The code generated around the
  call (CheckRaise, RaiseJump) moves it into df_err at once. df_pending is empty between statements.
- A function whose analysis says "nothing leaves" but that reaches its fail label anyway panics there (an internal error, never silent).
- main: an exception that reaches the top is a panic, as before (df_panic_unhandled(exception)). Static initializers do the same at program start.

The analysis (CodeGen.Leaks.cs, FindFailingFunctions)
- For every function: its raise points (integer / and %, indexing, null object access, throw, ==/!= on objects) and its calls, each with the catches
  that cover it (a statement is covered by the catches written after it in the same block and in the blocks around it). A fixpoint over the call graph gives
  the set of exception ids that can leave each function: the raise points and the callee sets that no covering catch handles. A function with a non-empty
  set is FAILING; the others are PURE or SAFE.
- A catch handles an exception of its class and its subclasses; catch Exception and catch all handle every non-silent exception. A catch body only lets out
  what it throws (any other error in a catch body is a panic, as before). A throw of a catch variable (throw ex) lets out the class of that catch.
- Conservative choices (sound, they only make a function FAILING when it could be safe): a / or % counts even on reals (no types at this stage); a throw
  of a variable that is not a catch variable lets out "any exception"; calls to generic functions and constructors of generic classes let out "any exception"
  (their copies are made later); the copies of equals; == and != between objects when the program has equals or the operator; functions of classes and
  traits with the same name and parameters share what they let out (they can be called through one pointer); one failing destructor makes every function
  FAILING (as before).
- Silent exceptions: a throw of a silent exception is not counted (it never leaves a function today).

Tests: tests/safety.df and tests/safety2.df (outputs in their comments; the C signatures can be read with --emit-c: pure and safe functions have plain
signatures, failing ones df_resN). The 31 older tests give exactly the output of the compiler before this change.


EXCEPTIONS STAGE 2: BUILT (2026-10-17)
=======================================
Built: rules 2, 4, 5 and 6 of the model (which catch observes an exception, silent exceptions observed only by the caller that catches them, no
leaking, explicit re-throw). Rule 7 (variants) is built in another way, see "The observed mask". Rule 8 (library declarations) is not built.

RULE 7 (variants) IS BUILT AS A RUN-TIME MASK (the specification 15.8.7 now describes this): one compiled version and a mask passed at run time instead of one version per mask. Reason: variants cannot give the right behaviour for
virtual and trait calls (one override would have to be compiled for the union of the masks of all the callers, and would stop at a silent throw
for a caller that ignores it; the spec says an ignored silent exception lets the function go on). A mask passed at run time gives exactly the
rules of 4 to 6 for every kind of call and needs no copies of the functions. What it does not do: it does not remove the code of a silent
exception per call chain; it removes it per program (a kind that no catch of the program handles has no code at all) and the C compiler removes
the test when it sees a constant mask.

The observed mask (SUPERSEDED on 2026-10-19: see "EXCEPTIONS STEP 1" below; the hidden df_obs parameter is gone, the live kinds and ObservedMask stay)
- LIVE silent kinds: the silent exception classes (the standard silent ones and the silent exception classes of the program) that at least one catch of the
  program handles (CatchHandles with silent = true: its own class, a parent, Exception, the SilentException trait, catch all). Each live kind has a bit
  (silentBit, 64 at most; more is a compile error).
- EMITTERS (maskFuns): the functions that contain a throw of a live silent exception that no catch of the function itself handles, or a re-throw of a catch
  variable that may hold a silent exception (throw e). Constructors, init functions, static initializers, destructors, == operators and generic copies
  of equals are never emitters (a silent throw there is only seen by the catches of the same function, as before). Functions of classes and traits
  with the same name and parameters are all emitters or none (they are called through one pointer).
- An emitter takes one more parameter, the hidden "uint64_t df_obs", and returns its exception like every FAILING function. The call site passes the
  kinds that the catches around the call handle (ObservedMask), and nothing else: the mask of a call is built from the catches of the caller only, so a
  silent exception never goes through a function that does not catch it (rule 5). main is called with 0.
- A throw of a silent exception inside an emitter: if a catch of the same function handles it, it is an ordinary local raise; else it is raised only if the
  bit of its kind is in df_obs ("if (df_obs & bit) { raise }"), otherwise the throw does nothing and the function goes on. In a function that is not an
  emitter the throw does nothing unless a local catch handles it. A re-throw (throw e in a catch body) checks the bit of the exception at run time
  (df_obs_bit, generated).
- The catches of a block do not observe what their own bodies throw (SilentCaught skips the catches of the block whose body we are in).
- The analysis of what leaves a function (CodeGen.Leaks.cs) is not changed by this: the silent exceptions are tracked apart (FunFlow.Silent).

Library functions
- The natives of the C runtime (parse, date(string), (time)n ...) keep their silent exceptions as before: a catch of the function that makes the call observes
  them (SilentCall), which is rule 5 with the native as the emitter. They are not yet declared per function as rule 8 asks.
- File and FileStream (written in Dflat) now throw their silent exceptions themselves in the function the user calls (FileAccessException, DirectoryNotEmptyException,
  FileNameAlreadyExistsException, SeekBeforeBeginException); File.check only throws what is not silent and gives back the silent id. The wrappers (delete, copyTo,
  moveTo, createDirectory of the object) catch the silent exceptions of the static functions and throw them again.

FIXED (2026-10-17): catch Exception does NOT handle silent exceptions, as the specification says (15.1, 15.4, 15.8.2). CatchHandles
(CodeGen.Leaks.cs) returns false for the target Exception when the exception is silent and df_exc_is (Runtime.cs) keeps its exclusion; a silent exception is handled by a
catch of its own class, of a parent class below Exception, of the SilentException trait, or by catch all. tests/silent.df and tests/exceptions.df are back to the original
rule; tests/silentmodel.df has sink (catch Exception does not observe) and a parent class below Exception (Family / Cousin).

Not done: arithmetic overflow and the other silent operations of the language (casts, + - *) do not emit exceptions at all yet (they wrap or saturate), so no
user function can be a silent emitter except by an explicit throw; silent exceptions from constructors, field initializers and destructors.

Tests: tests/silentmodel.df (the rules with user exception classes: ignored, observed, not leaking, re-thrown, catch Exception / SilentException / all,
virtual and trait calls, non-silent exceptions unchanged), tests/silentfiles.df (the library), tests/silent.df and tests/exceptions.df (two lines changed
back to the original rule after the fix). The other 29 old tests give the output of the compiler before stage 1.


EXCEPTIONS STEP 1: BUILT (2026-10-19), following the rewritten spec 15
=======================================================================
- A silent exception thrown by a function leaves it like any exception: the function returns (zero value, error) at the throw. There is no
  hidden mask parameter any more (TakesMask, maskFuns and the df_obs argument were removed).
- FunSig.CanEmitSilent says where a silent throw can leave: not in constructors, init functions, static initializers, destructors, == operators, generic
  equals copies and the entry point (main, including the top-level statements). There a silent throw is seen only by a catch of the same function
  (SilentCaught) and otherwise does nothing and the code goes on (SilentThrowCondition returns null). This is the constructor rule of 15.7.6.
- Leak analysis: the set of what leaves a function has a special member SilentLeak (-3): an uncovered silent throw (or a rethrow of a catch variable that
  may be silent) in a function that CanEmitSilent. It makes the function failing (it returns the pair) but is never passed on to callers: a silent
  exception goes one level only. Virtual and trait groups share it like any other member.
- The call site (PairCheck): if the returned error is silent and no catch around the call handles it (SilentIgnored: bit test with ObservedMask,
  or simply "silent" when no catch of the program handles any silent kind), the error is dropped and the call goes on with the value the function
  returned. Otherwise it goes to the handler as before.
- RELEASE OF THE RECORDS (built 2026-10-19, spec 15.1 and 15.7.5): df_exc_release (Runtime.cs) frees the message, the function text and the record (an exception
  object of the program is dropped first, so its destructor runs). Who releases: the catch that handled it, when its body ends (normal end, or return / break /
  continue / jump out of it, through the CaughtVar of the catch frame in EmitReturnUnwind / EmitUnwindTo); a catch body that throws a DIFFERENT exception
  releases the original (cbexit compares df_err with the caught pointer; throw ex of the same record does not release); a silent exception ignored at a call
  site (PairCheck). ReturnPassesAtEnd is true inside a catch body so a plain return does not skip the release. Panics do no cleanup. ex.Message / ex.Function
  now copy the text (df_str_dup_cstr). A catch variable cannot be stored, returned, put in a list/tuple or moved with -> (CheckCatchVariableStays: compile error).
  Leak check: run a program with the environment variable DF_EXC_COUNT=1: it prints "exceptions alive at exit: N" (df_exc_live), 0 expected (test exceptionrelease).
  NOT done: static records for silent exceptions without fields (they are still allocated and released like any other).
- SILENT OPERATIONS OF THE LANGUAGE (step 2, built 2026-10-19, spec 15.4): the overflow of integer + - * (also -x of a signed, ++ and --, and the compound
  assignments, which go through BinaryOp) and a cast to an integer that does not fit are raised only where SilentCaught says a catch of the same
  function handles them (OverflowException / OutOfRangeCastException, SilentException, catch all; catch Exception does not). Then the code is
  CheckedArithmetic (__builtin_add/sub/mul_overflow, df_raise + RaiseJump) or SilentCall(df_satc_<type>_<src>, ...) (the checked casts of Runtime.cs leave a note
  when the value does not fit). With no such catch the code is exactly what it was (wraps / saturates, nothing created). They never leave the function.
  NOT done: (char)n with an invalid code point (InvalidCharacterCodePointException; the U+0000 fallback itself is not built), the exceptions of collections.
- ATEND HAS NO ERROR PART (step 3, built 2026-10-19, spec 15.7.6): a non-silent exception not handled inside an atEnd block is a Panic (-1000, message first),
  whether or not another exception is passing through (EmitAtEnd: OuterHandler is always the panic label). The leak analysis ignores what an atEnd block raises (it does
  not leave the function). A destructor (the atEnd of a class) follows the same rule: its fail label panics, it is never a failing function, and the old rule "a
  destructor that can raise makes every function failing" is gone. A silent throw inside an atEnd block is seen only by a catch inside the block (SilentCaught stops at
  the atEnd frame, SilentThrowCondition returns null there), otherwise it does nothing. Tests: atendpanic, atendhandled.
- CONSTRUCTORS (step 4, built 2026-10-19, spec 15.7.6): a constructor whose init functions (field initializers) can raise returns (object, error); when it raises the
  half-built object is dropped (df_drop: the objects its fields already hold end) and the caller gets (null, error). A silent exception raised by a call in a field
  initializer is ignored by the init function (it never leaves a constructor). Only primary constructors exist (secondary ones are "feature not supported"), and a
  class body cannot have atEnd yet, so "the atEnd blocks registered so far run" has nothing to run today. Test: ctorfail.
- Not done yet: silent operations of
  the language (overflow, saturating casts) as local-only exceptions (step 2), and the atEnd panic rule (step 3). 64 live silent kinds is still the limit
  of ObservedMask.
- Tests changed because a silent throw now returns: silentmodel and bitfields (third()). New: silentreturn.

LISTS list<T> (built 2026-10-22, compiler 0.0.15alpha, spec 6.8.3; CodeGen.List.cs and the class `list` of VecPrelude)
=====================================================================================================================
- Same approach as vec: a generic class `list<T>` written in Dflat (VecPrelude) with the hot paths emitted as C. The singly linked list is stored in two arrays: `items`
  (slot n holds the item of node n) and `links` (the slot of the next node, UINT64_MAX at the end); the list keeps first, last, count, used, a chain of free slots and a
  version. A removed node goes to the free chain and is reused; growing doubles the two arrays (add is amortized O(1)). So the nodes are slots, not separate allocations:
  the observable cost table of the spec holds (c[i] O(n) walk, add O(1), insert / removeAt O(1) at the ends, reverse relinks).
- Glue: c[i] / c[i] = v / += walk the links (ListIndex, ListIndexAssign), the for loop walks them once, the literal (ListLiteral), a bare `list x = [..]` (InferListType), printing
  (ListStrFunction), sort / sortUnstable (the items go to a temporary array, the arrays' sort orders it, they go back in the same nodes: not the relinking of the spec), swap
  (the class methods exchange / replace, same rule as the arrays), ->list[i] (takeAt: the item leaves and the node goes away), the drop of the list (EmitListDropGlue: a loop over
  the nodes, so a long list does not recurse, then the two blocks are freed). The class has add, insert, takeAt, removeAt, indexOf, has, remove, removeAll, clear, fill(value),
  fill(count, value), reverse, exchange, replace and getIterator. There is no capacity, resize, truncate or pop (compile error "has no function").
- The ownership rules and the ModifyingIteratedCollectionException check are those of vec. getIterator() copies the items into an array first (a snapshot, O(n)) and gives an
  arrIterator; the node pointer cursor of the spec needs pointers.
- Not done yet: add(collection), copyFrom, views l[a..b], l!, sort by relinking nodes, the iterator with a node cursor, .sizeof.
- Replaced on 2026-10-24 (compiler 0.0.17alpha): the nodes are separate allocations and the version is a counter of open iterators, see LISTS WITH NODES below.

  The prelude now has Collection<Item> { get_len, has, clear } and IndexCollection<Item> : Collection<Item> { getIterator }; vec implements has and clear as methods

ARRAYS ALIGNED WITH THE SPEC 0.0.13 (built 2026-10-22, compiler 0.0.13alpha)
==========================================================================
- `uns` is a type: Normalize maps it to CodeGen.NativeUns (u64, or u32 when the target is 32 bits; Program passes the bits of the target to CodeGen.Compile). The arrays
  used uint64_t lengths in C until 0.0.16alpha (see UNS LENGTHS AND INDEXES below). `int` is a type too since the native size cleanup (see NATIVE SIZE AND CPU below);
  `real` is not.

THE PREPROCESSOR AND THE OPTIONS (built 2026-10-21, compiler 0.0.12alpha, spec 19.1)
==================================================================================
- Preprocessor.cs (dfparser, shared with dfcompiler through the csproj): runs before the lexer on the source text. Lines starting with ## at the first column are
  directives (define if elseif else endif region endregion emiterror emitwarning); directives and the lines of a removed block become empty lines (a \r is kept),
  so the line numbers do not change. A '#' in the text of a directive is an error. Conditions: operands are variables, numbers (with kb mb gb), true / false,
  words or "texts"; ==, != on any value, < <= > >= only on numbers; && and || have the same precedence, from left to right; ! only on a bool variable; the right
  side of a comparison is a word unless it names a variable (then its value); a word that is not in the list of values of the left variable (os == windoes) is an error.
  ##define takes a value or a condition. Errors: unknown variable, an order comparison on a word, ##elseif / ##else after ##else, ##endif alone, ##if without
  ##endif, a name that is predefined or equals a value of a predefined variable or true / false, a redefinition of a project variable.
  A variable defined in the source can be defined again; the ones of the project file (CompilerVar) and the predefined ones cannot.
  ##region / ##endregion only fold (unmatched: level 3 warning). The Lexer does not know #region any more.
- PpVariables.cs: the predefined variables from the os, the cpu and the native size that Program.cs resolves (see NATIVE SIZE AND CPU below; real=64
  until --native-real is built; ram 4gb; exceptions on; build debug by default; coptlev, coptmode; version = LanguageVersion of Program.cs and
  version.major / minor / build). A custom CL: target uses the variables of this machine.
- Program.cs: Version 0.0.12alpha and LanguageVersion 0.0.12 (the version of the spec it was built for; --version prints both). Options added: --coptlev 0-3
  (-O<n>), --coptmode size|speed (size = -Os), --debug / --release (only the variable `build` for now). The input can be a .df file, a .dsprj file or a folder with one
  .dsprj. Settings: command line over the project file over the defaults (DFLAT_CC for the compiler). ReadProject: `key = value`, ; comments, paths relative to the
  project, keys not case sensitive: source / root, output (a file), target, cc, emit-c, coptlev, coptmode, build and CompilerVar=name=value (true, false, a number or a
  word without spaces; one line per variable); run and version are not allowed; any other key is "not built yet".
- Tests: preprocessor (host independent conditions), errors/pp_*. The project file was tested by hand (the runner has no way to pass a project): CompilerVar,
  precedence of the command line, an unknown key, a predefined variable, a repeated variable and a ##define of a project variable.
- Not done: --native-int / --native-real / --native-addr (int uns real are fixed), bits and ram for custom architectures, --no-exceptions (exceptions is always on),
  --force-lib, --libc, --c-std, --cachealign, --suppresswarning, --lazy-statics, the output as a folder, `name` and `include` in the project file.

LISTS WITH NODES AND THE COUNTER OF OPEN ITERATORS (built 2026-10-24, compiler 0.0.17alpha, spec 0.0.14: 6.4, 6.6, 6.8.3; points 29 and 4 of the collections discussion)
=================================================================================================================================================================
- A list node is a C struct per list type, struct df_ln_<type> { next; value; } (ListNode, emitted after the types of the program: listNodeTypes in Assemble), allocated with
  df_alloc one by one. The list keeps first, last, count and iterators; a null next ends the list. In VecPrelude the fields first and last are declared u64, and EmitStruct gives

- The class list<T> of VecPrelude keeps the rules (checkUnlocked, the index checks with their exceptions, the ->T parameters, the overloads) and calls node_ members on this:

  is an error). The receiver is moved (a variable or field is left null; an arr is left empty), the items move without copying the objects, the original ends. arr to vec

  removeAt(range), copyFrom, transformTo). Allowed while iterated: c[i] = v, swap, replace, fill(value), clear(). Debug: catchable; Release: panic (df_raise).
- clear() (spec 6.6): every item gets its default value and the size is kept, on arr, vec and list; the objects held end (the arr clear now drops them too).
- Program.LanguageVersion is 0.0.14 (the spec this build follows; --version and the preprocessor variable version).
- The parser no longer warns "read as a generic call" for transformTo<arr>() (arr counts as a type in that check only).
- Tests: listnodes (new), errors/list_add_objects_copy, list_copyfrom_objects, list_transform_item_type, list_node_member; list, listown, vec, vecown and vecspec changed for

PARENT AND CHILD OBJECTS (built 2026-10-24, compiler 0.0.19alpha, spec 12.5)
=============================================================================

- RegisterParentParam (CodeGen.Classes.cs): the parameter must be & or (&) (a reference) to a class (a trait: not supported), no default, one per class. It becomes a
  field (FromParam, IsParentRef, ReadOnlyRef for &) that the class does not own (OwnedObjectFields skips it) and that only the constructor sets (an assignment or a move
  elsewhere: "is the reference to the parent: only the constructor sets it"). The child gets the hidden field df_slot (uns: its position + 1 in the list of its parent,

  fields are not printed by the default toStr. as parent on a plain function is an error.

  only by the object itself (receiver self, in the class or a subclass) and through the parent reference of the class being compiled (ParentReceiver: self->m_x or (self)->m_x); through a read-only parent (&) only asparent, unrestricted and
  static functions; a field assignment through it is an error (ClassLValue). One visibility per function; asparent and unrestricted on fields are errors.

  of the slot)), adds the class to adoptedClasses and gives a level 2 warning. The drop of a parent calls df_kids_release (it nulls the references of its adopted children
  and frees the list); the drop of an adopted child takes it out of the list (df_kids_remove: the last entry moves into its place, its slot is updated) and does not run

- UsageOfDestroyedObjectException: ID 48 (spec 15.3), not silent, catchable in Debug and Release.
- Tests: parents (a read-only and a writable parent, a child never moved, an orphan adopted child, adopted children that end before their parent), errors/parent_twice,

NATIVE SIZE AND CPU (2026-10-25)

- Tests: equality.df uses T is int (a literal is an int now), preprocessor.df tests cpu == arm64 and int == bits. Options tested by hand (sparc, foo, --native-int 16,

STDLIB 0.0.10: PROCESSES, SLEEP, CONSOLE, PATHS (built 2026-10-25, compiler 0.0.21alpha)
=========================================================================================
- Root.exit, Root.Console.read / clear, Root.Time.sleep are rows of the Stdlib table (CodeGen.Stdlib.cs); their C is in the base runtime (Runtime.cs):
  df_exit (exit(), so atexit runs; atEnd and destructors do not), df_console_read, df_console_clear, df_time_sleep.
- A nullable result of a library function: the C function returns an int64_t, negative for null, and StdCall wraps it in the df_opt_ struct (char? read()).
- Console.read: Windows _kbhit / _getwch (two-code keys give null, Enter '\r' becomes '\n'). Unix: the first read() puts the terminal in raw mode (no ICANON,
  no ECHO, VMIN 0) and leaves it so; readLine, atexit, df_panic (df_panic_hook) and SIGINT / SIGTERM / SIGHUP / SIGQUIT give it back. An escape sequence is
  skipped (null), Esc alone is 0x1B. Not a terminal: getc, -1 at the end.
- Console.clear: Windows console API on the whole buffer (nothing when the output is not a console); Unix ESC[H ESC[2J only when isatty.
- sleep: the lapse becomes nanoseconds (date 1 ms, clock 0.1 ns rounded up, years and overflow about 146 years). Windows: a high resolution waitable timer
  (CREATE_WAITABLE_TIMER_HIGH_RESOLUTION, Windows 10 1803), else Sleep rounded up; Unix nanosleep, again after EINTR.
- Number to lapse (spec 3.4): Assignable(lapse, any number) is true and Convert calls df_lapse_from_ms (integers) or df_lapse_from_ms_real (reals); ArgCost
  gives a literal for a lapse parameter the cost 3.
- Root.IO.getCurrentDir / setCurrentDir / getFullPath / getRelativePath: static functions of the File prelude class (IoPrelude); Call sends Root.IO.<name> to
  File.<name> (LibraryStaticPath, also for Root.ExecProcess.run / exec). Mentioning one of the names adds the File prelude. C side in RuntimeIO.cs
  (df_io_current_dir, df_io_set_current_dir, df_io_full_path, df_io_relative_path); segments compared without case on Windows; different drives give the full "to".
  A side effect: File.getFullPath etc. also work.

  clock and lapse.
- put: a full chain without extension splits when the next bit of the scrambled hash separates its entries (with the new one); at the depth of
  the directory the directory doubles first (and the buckets with an extension are tried again: df_ht_unstick); otherwise an extension is added
  (the bucket is marked stuck when every entry has the same scrambled hash). The split takes every entry of the chain out and puts it back into the
  bucket or its new sibling (df_ht_place adds extensions when a side has more than 16). The depth of the directory stops at 48 (28 with a 32-bit uns).
- remove (df_ht_tidy): empty extensions leave the chain, the last two links merge at 14 entries or fewer, two siblings without extensions merge at 8
  or fewer, then df_ht_shrink (1 or 2 bits, a recount pass, an unstick). removeAll marks (df_ht_mark) and then builds the table again once
  (df_ht_sweep). clear frees everything (an empty hmap allocates nothing until its next add).
- The walk (df_ht_cur: directory index, block, slot) jumps 2^(d - L) directory entries after each chain. The loop for (k, v) in m and printing use it.
- Tests: hmap (every member, the nullable and wide nullable keys, reals, enums, bool, 20000 random adds and removals checked against arrays, the
  counter of open iterators); also run with --native-int 32 and --release; a stress run of 1000000 operations on 200000 keys was checked by hand.
  errors/hmap_object_key, errors/hmap_object_value (they were hmap_string_key and hmap_string_value before step 2).

HMAP STEP 2: STRINGS (2026-10-27, spec 6.8.5.1, compiler 0.0.31alpha)
- A string key slot is a df_ht_skey (RuntimeHmap.cs): the full hash (uint64_t) and a pointer in a union of 8 bytes, so 16 bytes on every target; the
  shape has df_ht_skey_hash (the stored hash) and df_ht_skey_eq (the hashes, then df_str_eq), and kp true. HmapKeySlot builds it from df_hash_str
  of the key (a borrow of the caller's string, for a lookup); MapSlot, for a new key, copies the key (df_str_dup) and builds a second slot with the
  hash already computed, which goes into the table. MapRemove takes the key slot out (df_ht_remove with a df_ht_skey) and frees its string;
  DropEntry frees it in clear, the drop and removeAll. CursorKey gives the hmap's own string (a borrow, as in map).
- A string value is the 64-byte slot of map (DF_BT_SVAL, df_bt_sval_*): HmapShape needs the chunk "map" for it. The slot moves with its entry
  (memcpy in splits, merges and the rebuild of removeAll), as in a leaf of map, so the read rule of map applies unchanged (MapBorrowMark).
- Tests: hmapstrings (keys longer than 16 and than 112 bytes, "" as a key, a value of more than 59 bytes, ->m[k] of a string, removeAll, +=
  on a string value, 12000 random adds and removals of string keys checked against arrays); also run with --native-int 32 and --release, and with
  DF_STR_TRACE (no string left alive beyond the 1 of an empty program, in hmap and hmapstrings).

HMAP STEP 4: .keys AND .values (2026-10-27, spec 6.5, 6.6, compiler 0.0.32alpha)
- HmapPrelude has the views hmapKeys<K, V> and hmapValues<K, V> (the same as mapKeys and mapValues: children of their hmap, a read-only reference

HMAP STEP 5: CAPACITY (2026-10-27, spec 6.8.5.1, 6.6, compiler 0.0.33alpha)
- hmap has get_capacity, reserve(uns wanted) and bool shrinkToFit() (HmapPrelude) over tree_capacity, tree_reserve, tree_shrinkToFit (MapTreeMember);
  reserve and shrinkToFit check the counter of open iterators (spec 6.4).
- df_ht_capacity: 11 << d (DF_HT_FILL, the average entries of a bucket), 0 before the first add. df_ht_reserve(t, wanted): the depth D that gives
  ceil(wanted / 11) buckets; the directory doubles up to D, then every bucket is split down to D (the room is made now, and the removals
  that follow do not shrink the directory at once, since every bucket is as deep as it). df_ht_fit: the chains are compacted (df_ht_compact),
  two siblings merge when they fit in one bucket (16, not the 8 of a removal), the directory shrinks one bit at a time while C(d) = 0 (no limit of 2),
  again until nothing changes; an empty hmap frees everything; false when nothing changed. The sibling merge and the shrink are shared with the
  removal (df_ht_merge_sibling, df_ht_mergeable, df_ht_shrink_by).
- hmap<K, V>[n] (ArrayNew, HmapNewWithCapacity): an empty hmap, then df_ht_reserve(n). hmap<K, V>[n] name (= []) is rewritten by RewriteSizedArrays
  like vec<T>[n] name (any other initializer is a compile error).
- Test hmapcapacity (also with --native-int 32). Note: after many removals shrinkToFit can return false, because the removals already merged and
  shrank the table (the test shows it).

RESERVE AS A TOTAL AND HMAP STEP 6 (2026-10-27, spec 6.6, 6.3, compiler 0.0.34alpha)
- reserve(n) on vec (VecPrelude) and on hmap (df_ht_reserve) makes room for n items in all: the capacity becomes at least n, and nothing changes
  when it already is (was: n more than the length). The room stays until a shrink (shrinkToFit, and on hmap the merges of the removals). Tests vec
  and hmapcapacity check that a smaller reserve changes nothing. (The internal VecReserve of add(collection) still grows by what it adds.)
- hmap h = [k: v] (ResolveDeclType, InferMapType with hashed): the key and value types come from the literal, as for map; var h = [k: v] stays a
  map (spec 6.3). ObjectTypeOf counts a bare hmap with a literal as a new object.
- Tests hmapliterals (the program of mapliterals with hmap: the same output, in the order of the table), errors/hmaplit_duplicate,
  errors/hmap_sized_literal.
