Compiler version 0.0.189 alpha for version 0.0.40 of the specs 2026/11/20

Changes from the previous version -----------------------
- .dfc (spec 15.8): each binary line ends with the SHA-256 of the binary (binary <target> <file> <size> <sha-256>); a binary that does not match is a compile error for a program, and a library build replaces such a file; test errors/lib_dfc_checksum
- Compiled libraries, step 5 point d: test projects/libids (the exception class of a library caught by the program, thrown by the program, caught by the library itself after the program gave the ids, beside an exception of the program). STEP 5 COMPLETE: item 15 (compiled libraries) complete; left: the sha-256 of the binaries of a .dfc
- Compiled libraries, step 5 point c (spec 15.8): the equals(T) of the class of an object (==, keys of maps and sets) is found through its record, the class then its parents, no longer through the number of the class, so the ids given by the program to its libraries are never used as indexes. Not yet: equals(T) of a class of a compiled library (not in the .dfi: such objects compare by identity in the program)
- Compiled libraries, step 5 point b (spec 15.8): at start, before any library starts, the program gives the ids of the classes and exceptions of its compiled libraries after its own (ids -> df_libids_<name> of each .dfi, in the order of include=); the public exception classes of a library are in its .dfi (class X : Exception) with their descriptor exported: a program creates, throws and catches them, and the library catches its own with the ids the program gave
- Compiled libraries, step 5 point a (spec 15.8): in a library build the class records and exception descriptors are writable, and df_libids_<name>(next) (ids -> in the .dfi) writes the ids the program gives, from next on, returning the next free one; the generated code reads the id of an exception class from its descriptor (catch, is, the silent bits), so the program can renumber them; descriptors are named like the records (df_desc_<namespace>__<Name>). The program does not call df_libids yet (point b)
- A library binary no longer holds the folders of the machine that built it (llvm-lib / llvm-ar get the object without its path)
- Compiled libraries, step 4 point 3: tests of the .dfc: libraries/packed (built for win-x32 then win-x64 into one .dfc; a library test folder can list extra-targets.txt), projects/packedapp (a program that links a .dfc), errors lib_two_interfaces and lib_dfc_no_target; run-tests.ps1 reads a .dfc as text (header and interface, sizes masked). STEP 4 COMPLETE
- Compiled libraries, step 4 point 2 (spec 15.8): a program uses a library folder that holds a .dfc: the interface is read from it, the binary of the target is taken out into .compilation/libs/<name>/<target>/ and linked; a .dfc without the target is a compile error that names the targets it holds; a folder with both a .dfi and a .dfc (or two of them) is a compile error
- Compiled libraries, step 4 point 1 (spec 15.8): --embed-binaries (embed-binaries=true in the .dsprj) builds a library into one <name>.dfc: the interface, then the table of the targets, then their binaries; a build for another target adds it to the .dfi or .dfc and keeps the others when the compiler and the interface are the same (level 2 warning when they are dropped); level 2 warning when the folder holds both forms; the interface is written only once the binary is built. Not yet: a program that uses a .dfc (point 2)
- Compiled libraries, step 3 point 6 (spec 15.8): an included library folder without a .dfi is a compile error (a program no longer compiles a library from source); the copies of the stdlib generics a library lists (vec<string>) are made by the program; the binary is checked before the version. Tests: run-tests.ps1 builds every library that a project includes before the tests run, masks the compiler versions in the errors; projects/libclasses (functions, enums, bitfields, classes, a replaced method, variables, an exception from a library); errors lib_no_dfi, lib_old_version, lib_no_binary; global_program_in_lib and ns_inside_root are now library builds that fail. STEP 3 COMPLETE

- Fix: an overlap of namespaces in a library build names the library
- Compiled libraries, step 3 point 5 (spec 15.8): the program starts its compiled libraries (atLibStart of the .dfi: df_libstart_<name>) before its own globals, statics and code, in the order of include=, and ends them (atEnd: df_libend_<name>) after it has ended, in the reverse order; methods of a global of a library are called on its name (Numbers.take())

Not yet: functions whose signature names a class of the library (point 3)

- Compiled libraries, step 2 point 5 (spec 15.8, 19): a project whose root file is lib.df (or --force-lib) builds a static library: <name>.dfi in the folder of the library and <libpath or that folder>/<target>/<name>.lib (lib<name>.a elsewhere), made with llvm-lib / llvm-ar. A project without source= takes the first of program.df, main.df, lib.df of its folder (spec 19); name= is read from the project file
- Compiled libraries, step 2 point 4 (spec 15.8): the interface of a library (.dfi): the DFI block (compiler, library, namespace, runtime chunks, stdlib parts), then its public declarations under their namespaces, each with its C symbol (->) and error when it returns an error part; a class gives its record, its C layout for the target (layout-<target>:), its public fields, constructors and methods; public globals with their lock, public variables, atLibStart and atEnd. Written for now with DFLAT_EMIT_DFI=<library> during a program build (the library build is point 5)
- Compiled libraries, step 2 point 3 (spec 15.8): the stdlib written in Dflat (its functions, the copies of its generics, the records of its classes, File and the streams included) goes with the runtime: static in a program alone, defined by the program (exported) or only declared by a compiled library (imported); lambdas and pure helpers stay in each unit. The full suite passes in the exported form
- Fix: the division and the remainder of a calculation between i64 and u64 (128 bits) no longer need a helper of the C compiler that is not linked on Windows
- Compiled libraries, step 2 points 1-2 (spec 15.8): the generated C names that separately built units share are stable: result types and tuples are named after their types, overloads after their parameter types (not their position), class records after the full namespace and the name of the class (df_cls_libs__fun__counters__Sequence)
- Top-level variables of the root file (spec 14.1): the functions, classes and methods of that file see them (only that file); each gets its value when its line runs, zero or null before; a function can write them (a new object or string ends the old one); they end after the top-level code, in reverse order
- A result of i64 with u64 going to var or a string becomes an i64, saturated, with a level 1 warning (spec 3.5.1; it was a compile error)
- Fix: a static field of an object or a string is written as a field (a new value ends the old one, a lent string is copied) and ends at program end, in reverse order, so the atEnd of its object runs
- Libraries (spec 16, 15.8): a fully qualified name of a library namespace in the code needs import lib in that file too; library variables can hold objects, strings and arrays (a new value ends the old one, they end after the library's globals, in reverse order); fix: a library variable without a value no longer crashes the compiler
- A library with no name defined (no .dsprj, or no name= in it) takes the last part of its root namespace as its name, with a level 1 warning (spec 16)
- Automatic conversions of numbers (spec 3.5.1): integers go to any integer type without a cast (a value that does not fit saturates, silent OutOfRangeCastException; a constant that does not fit is an error), char to integer, integer to real, r64 to r32 (silent PrecisionLostException 57, beyond the range +-infinity); mixed integer arithmetic is done in a signed type wide enough for both (i64 with u64 in 128 bits) and integer comparisons are exact; automatic conversions do not choose between overloads; the range and items of a for convert to the loop variable, real to integer included (spec 10); level 3 warning when a value can change

- Library start and end (spec 15.8, 14.2 form 6): atLibStart { } in lib.df runs at program start, after the library's globals and before the program's; the top-level atEnd { } of lib.df runs after the program's globals end, then the library's globals end; libraries end in reverse order
