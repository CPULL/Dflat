# 13. Functions

```
fun u64 fib(u64 n) { ... }
fun log(string msg) { }                        // void
fun i32, string getUser() { return 1, "a" }    // multiple values
fun (i32 v, string n) getPair() { return (1, "a") }   // tuple
fun u64 getVal() { c }                         // single expression returns
```

## 13.1 Parameters

The markers say what happens to the value: who owns it and whether it can be written. Three rules:

- The common case has no marker: a plain parameter lends read-only.
- One marker has one meaning, and the call repeats the marker of the definition, so the reader of the call sees what happens.
- `&` always means "you may write". It combines with the other markers (`&@`, `&%`, `&*`).

| Need | Lifecycle | Definition | Call |
|---|---|---|---|
| lend, read-only | stays the caller's; the function cannot write or free it | `f(Dog d)` | `f(x)` |
| lend, read/write | stays the caller's; the function can write it and replace it | `f(&Dog d)` | `f(&x)` |
| give | the function owns it and frees it | `f(->Dog d)` | `f(->x)` |
| give a copy | the function owns the copy; the caller keeps its own | `f(->Dog d)` | `f(x!)` |
| share | both use it; the last user frees it (12.7) | `f(@Dog d)` | `f(@x)` |
| share, read/write | as above, and the function can write it, holding the lock (12.7) | `f(&@Dog d)` | `f(&@x)` |
| weak | may be gone; checked with `enforce` (12.7) | `f(%Dog d)` | `f(%x)` |
| weak, read/write | as above; through `enforce` it writes, holding the lock (12.7) | `f(&%Dog d)` | `f(&%x)` |
| raw pointer | low level, no guarantees (12.1) | `f(*byte p)` | `f(*x)` |
| raw pointer, writable | low level, no guarantees (12.1) | `f(&*byte p)` | `f(&*x)` |

An example for each:

```
fun show(Dog d) { log(d.name) }            // reads only
show(rex)

fun rename(&Dog d) { d.name = "Max" }      // writes the caller's object
rename(&rex)

fun bool tryParse(string text, &i32 result) { ... }
i32 value
tryParse("12", &value)                     // writes the caller's variable

fun adopt(->Dog d) { kennel.add(->d) }     // takes the ownership
adopt(->rex)                               // rex is null afterwards
adopt(rex!)                                // gives a copy; rex stays

fun keep(@Dog d) { team.add(@d) }          // one more user
keep(@shared)
keep(->shared)                             // gives the caller's usage: count unchanged, shared is null

fun train(&@Dog d) { enforce d { d.level++ } }
train(&@shared)                            // shared is a &@Dog

fun watch(%Dog d) { enforce d { log(d.name) } else { log("gone") } }
watch(%shared)                             // from a counted or a weak variable

fun heal(&%Dog d) { enforce d { d.health = 100 } }
heal(&%shared)                             // from a &@Dog or a &%Dog

u8 level = 5
fun u8 peek(*u8 p) { p[] }                 // reads through the pointer
peek(*level)

fun clear(&*u8 p) { p[] = 0 }              // writes through the pointer
clear(&*level)
```

- Native data (integers, reals, chars, bools, enums, pointers): a plain parameter lends read-only, so the function cannot change the caller's value. The compiler may pass a copy instead, in a register or on the stack; the function cannot tell the difference. A `volatile` parameter is never copied (12.3): `fun wait(volatile clock now)`.
- Objects, strings, collections and arrays: a plain parameter is a borrow (12): no copy is made.
- `&` lends read/write: the function can change the object, and it can also replace the caller's value with a new one (`result = 42`, `data = [1, 2]`). There are no separate output parameters.
- When the function replaces the value, the old one ends (its `atEnd` runs) and the caller's variable owns the new one. So `&x` names what owns its value: a variable that owns it, a field, an item of an array, or a `&` parameter passed on. `&x` on a variable that only borrows (`Dog view = rex`, a plain parameter) is a compile error. A string that borrows its text gets a copy of its own before the call.
- `&this` is a compile error: the function could replace the object while its method runs.
- `x!` gives a copy: it fits a `->` parameter; to a plain parameter it lends a temporary copy, which ends with the statement (12).
- `->` on a native value is a plain copy with a level 1 warning (12.4).
- A counted argument is accepted only by `@` and `&@` parameters, and a weak one only by `%` and `&%` parameters; `f(Dog d)` and `f(&Dog d)` with a counted argument are compile errors (12.7). A `&@T` argument can go to an `@T` parameter (`f(@x)`, read-only; it shares the object or the value cell, except a `&@string`, which is copied, 12.7); an `@T` argument to a `&@T` parameter is a compile error. `@x` on a plain `x` makes it counted and `x` is lost (12.7).
- Function types and lambda captures use the same markers (13.3).
- A mismatched call is a compile error, a missing or different marker included (`rename(rex)`, `adopt(rex)`, `keep(shared)`).
- A new object, the result of a call and `null` need no marker, as for `->` (12.4): `keep(Dog("Fido"))`, `pack.add(make())`. A collection literal and `c[i] = x` are not calls: `list<@Dog> pack = [rex]` takes a usage of `rex` without `@`.
- Defaults anywhere; named arguments when needed (`hello(age: 27)`).
- Positional arguments stay in the order of the parameters; named arguments can be written in any position.

### 13.1.1 Return values

A result uses the markers of the parameters, with the same meaning. The caller receives what the marker says.

| Need | Lifecycle | Definition |
|---|---|---|
| lend, read-only | the caller reads it while the lender lives | `fun Dog first()` |
| lend, read/write | the caller writes it in place while the lender lives | `fun &Dog at(uns i)` |
| give | the caller owns it and frees it | `fun ->Dog make()` |
| share | the caller becomes one more user (12.7) | `fun @Dog shared()` |
| share, read/write | as above, and the caller can write it, holding the lock (12.7) | `fun &@Dog shared()` |
| weak | may be gone; the caller checks it with `enforce` (12.7) | `fun %Dog cached()` |
| raw pointer | low level, no guarantees (12.1) | `fun *string getVersion()` |
| raw pointer, writable | low level, no guarantees (12.1) | `fun &*byte{4096} buffer()` |

An example for each:

```
class Kennel {
  list<Dog> dogs
  @Dog boss
  %Dog lastSeen

  public fun Dog first() { dogs[0] }              // lends an item of this kennel
  public fun &Dog at(uns i) { dogs[i] }           // the caller can change the item in place
  public fun ->Dog adoptFirst() { ->dogs[0] }     // the item leaves the list: the caller owns it
  public fun @Dog leader() { boss }               // the caller becomes a user of boss
  public fun %Dog recent() { lastSeen }           // another weak reference
}

fun ->Dog make() { Dog("Rex") }                   // a new object: the caller owns it
fun &@Dog makeShared() { @Dog("Bob") }            // a new read/write counted object
fun *string getVersion() { *"1.2.3" }             // static data: no copy, valid for the whole program

Dog d = kennel.first()                            // d borrows from kennel
kennel.at(0).name = "Max"                         // writes the item in the list
Dog mine = make()                                 // mine owns the new dog
@Dog lead = kennel.leader()
%Dog seen = kennel.recent()
```

- A lent result (plain or `&`) can come only from something that lives after the return: the object of the method (`this` and its fields), a parameter that was itself lent to the function, or static data (`const`, literals, static fields). Called on a global from outside, a plain lent result is copied at the call and a `&T` one is a compile error (18.3). The lend follows the rules of 12: while the caller holds it, the lender cannot be released, moved or given away.
- The compiler checks borrows inside a function, by the order of the statements: until the last use of a local that borrows an object or an array (`Dog view = rex`, `Dog d = k.leader()`, `Dog f = pack[0]`), what it borrows from (`rex`; the receiver `k` and the lent arguments of the call; `pack`) cannot be assigned, ended with `is atEnd.`, moved with `->` or passed as `&`, and its fields cannot be written (`k.boss = x`, `k.visits++`, `k.dogs[0] = x`), as in Rust. After the last use it can. Strings are not locked: they keep their identity when changed in place, and a borrow sees the change (4.1, 4.4).
- A `&T` result lends what the function can write: `this` and its fields, an item of them, a `&` parameter, or the `&T` result of another call; never a global (18.3). A plain (read-only) parameter, a `const` or a new value (`fun &Dog f() { Dog("x") }`, which is `->`) is a compile error; a result cannot be both `->` and `&`.
- While a local borrows from an object (`Dog d = k.leader()`), only the `unrestricted` and static methods of that object can be called until the last use of `d` (an `unrestricted` method does not change it, 1.6.2); while an item of a collection is borrowed (`Dog d = c[i]`, `tryGet`), the members that change the collection are compile errors too.
- A local that borrows (from a place, or from a plain or `&T` result) is read-only when it is declared plain, also when the source lends read/write (no error, no warning); `&Dog d = ...` declares a read/write borrow and needs a source that lends read/write (a `&T` result, an item or a field the code can write). A local that owns (a new object, `->x`, a `->T` result) is not affected.

```
Dog g = Dog("rex")            // owns: everything allowed
Dog d = kennel.leader()       // a read-only borrow
&Dog w = kennel.at(0)         // a read/write borrow
Dog v = kennel.at(0)          // a read/write lend kept read-only: allowed
```

- `&T` results of values (numbers, `bool`, `char`, enums, `string`, structs): the function returns the address of the place, with the same sources as above. `&T x = f()` lends the place read/write; a plain `T x = f()` copies the value; the call itself can be assigned (`f() = v`, `f() += v`, `f()++`). The lender is locked until the last use of `x`, as for objects; the lend cannot be stored in a field or a collection, nor returned except as another `&T` result.

```
class Board {
  i32 score
  string title
  public fun &i32 scoreRef() { score }
  public fun &string titleRef() { title }
}
&i32 s = board.scoreRef()
s += 10                       // writes board.score
board.scoreRef()++
&string t = board.titleRef()
t += "!"                      // writes board.title in place
```

- A lend from a read/write counted object (`&@T`, 12.7) is valid only inside an `enforce` that holds its lock, and cannot leave that block: the writes through it are under the lock, which `enforce` releases on every way out, exceptions included (7.2.5). There is no lock for each operation: a plain object has one owner, so only a counted one can be reached by two tasks.
- A lent result of a local of the function is a compile error: the local ends at the return. The error points to `->` (`fun Dog make() { Dog("a") }` asks for `fun ->Dog make()`).
- Native data (numbers, `bool`, `char`, enums) are values: a plain result is the value itself and it can come from a local (`fun u64 fib(u64 n)`). `->` on such a result is ignored, with a level 1 warning.
- `->`: a local is given by `return x` with no marker, because it ends anyway; a field is given with `->` (`return ->field`, the field becomes null, 12.4). Strings, arrays and collections built in the function need `->` too (`fun ->string greet() { $"Hi {name}" }`).
- A tuple result or several results follow the rule of each item: `fun (&Item value, bool isValid) writableNext()`, `fun ->arr<Dog>, uns pack()`.
- Several results can hold counted values, each with its own marker (12.7): `fun @Dog, i32 pick()`, kept by counted targets (`@Dog a, i32 n = pick()`); a plain target for a counted result is a compile error; a result nobody keeps (`pick()`, `_, n = pick()`) releases its usage. A counted target can also take an object the function gives (`@Dog a, i32 n = make()` with `fun ->Dog, i32 make()`): it starts counting it. A read/write counted result among several results (`fun &@i32, bool scoreCell()`) gives a read/write usage, as `fun &@T`; a read-only usage is a compile error there, and a `@string` target of a `&@string` result gets a compact copy. An extern function takes and gives plain values only: a counted parameter or result there is a compile error (15.9).
- Accessors (11.1.4): the default `R` lends the stored field, so reading a property makes no copy; an `R` that computes a new object or string gives it, and the reader owns the result (12.4).

## 13.2 Overloading

- Functions can share a name when the number, the order or the types of their parameters differ; the return type alone doesn't count.
- A call that matches more than one function is a compile error, including when default values make it ambiguous (`f(i32 a, i32 b = 0)` and `f(i32 a)` with `f(5)`).
- Literals: the native-size signed type wins (`i64` on 64-bit), even over an exact `i32`.
- Variables: exact type, then smallest same-family widening; other families are not candidates; still tied → compile error.
- Conversion to `string` always ranks last: with `f(i32)`, `f(u64)` and `f(string)`, `f(33)` picks `f(i32)` on 32-bit and `f(u64)` on 64-bit, never `f(string)`.

## 13.3 Lambdas

A lambda is a function with captures. Every rule that applies to functions (13.1 parameter modes, 13.2 overloading, return values) applies to lambdas.

```
(i32 a, string b; &c, ->d, e!) { ... }
```

- Parameters come before the `;`. Their types are always written; they cannot be inferred.
- Captures come after the `;`. The `;` and the list are omitted when the lambda has no explicit captures.
- A single expression body returns its value, as for functions.
- A lambda is called like a function, `f(3)`, also where it is written: `(i32 a) { Root.Console.log(a) }(42)` prints 42.

### 13.3.1 Capture modes

| Form | Meaning |
|---|---|
| `a` (unlisted) | Read-only borrow. Automatic; never written in the list. The lambda cannot modify `a` or anything reachable through it. |
| `&a` | Read/write borrow. |
| `->a` | Ownership moves into the lambda; the lambda is the new owner and the outer `a` is null. For a counted `a`, its usage moves into the lambda and the count does not change (as `f(->rc)`, 12.7). |
| `a!` | A copy is made and stored in the lambda. |
| `@a` | The lambda holds its own usage of the counted `a`, read-only: +1 when the lambda is created, -1 when it ends. |
| `&@a` | The same for a read/write `&@T` `a`. A write inside the body needs `enforce a`, which takes the lock then (7.2), not at the capture. |
| `%a` | A weak reference to the counted `a`: only the count of weak references changes, so the object can end while the lambda lives. The body reaches it through `enforce a`. |
| `&%a` | A weak reference to a read/write `&@T` `a` (12.7). |

- Constants and enums need no listing and give no warning (their value is fixed).
- Modifying an outer variable that is not listed `&` is a compile error.
- A counted object used without being listed is a compile error that asks for `@a` or `%a`: a counted object cannot be borrowed (12.7).
- Inside the body the captures are used as any other variable, with everything that is legal on them: a copy can always be made; ownership can be passed on only when the lambda owns the object (`->a`, `a!`).
- There is no `this` in a lambda. Inside a method the fields are captured by their bare names, like locals (`(; &val)`, `val!`). Under the hood a field capture borrows the object, so the lambda cannot be stored past the object (13.3.4).
- A property (11.1.4) used in a lambda is read through its accessors each time the lambda runs: unlisted it is read-only, `&prop` lets the lambda assign it (through `W:`), `prop!` copies the value read when the lambda is created. `->prop` is a compile error. The reference to the parent (12.5) is read-only: it is used unlisted (its functions are called as in the class) or copied with `parent!`.
- A counted field or a weak field is captured as a counted variable is: `@field`, `&@field`, `%field`, `&%field`.

### 13.3.2 Function types

```
fun(i32)               // returns void, takes one i32
string(char, char)     // returns string, takes two chars
string(&MyObj)         // returns string, takes a writable MyObj
```

- Form: `<return type | fun>(<parameter type>, ...)`. The parameter modes of 13.1 are part of the type: `string(&MyObj)`, `fun(->Dog)`, `fun(@Dog)`.
- Captures are not part of a function type. A parameter, field or variable of type `fun(i32)` accepts any lambda with that call signature, whatever it captures, provided the lifetime rules are satisfied.
- The user of a lambda does not see or care about its captures. A parameter that the caller of the lambda must see is a real parameter (`&`, `->` marked at the call), not a capture.
- Function types are nullable by default: a variable, field or parameter of a function type that holds no function is null. Calling it raises `UnassignedFunctionCallException`, a child of `NullPointerException` (15.3), so a null lambda can be told apart from a null object.

```
fun test() {
  i32(string) aFunction
  if false then aFunction = (string s) { s.len }
  aFunction("I am going to crash")    // UnassignedFunctionCallException
}
```

### 13.3.3 Lambdas as values

A lambda is a pointer to a function with a bit of context. Without captures it is a plain function pointer; with captures its context holds them and is shared like a counted object.

```
string readOnlyBorrow = "readOnlyBorrow"
fun(i32) f1 = (i32 a) { c.log(a + readOnlyBorrow) }    // an implicit capture: f1 has a context
fun(i32) f2 = f1                                       // the same lambda
fun(i32) f3 = f1!                                      // a copy
```

- `f2 = f1`: the same lambda and the same context, with one more usage. The holders share the state of the `a!` and `->a` captures, and that state stays between calls.
- `f3 = f1!`: a new context. The owned captures (`a!`, `->a`) are cloned, the borrows point to the same variable, the counted captures add a usage, the weak ones stay weak. Without captures `f1!` is the same as `f1`.
- `f1!` on a lambda with a `&` capture is a compile error: two writable borrows of one variable. `f2 = f1` is allowed (one context, one borrow).

### 13.3.4 Lifetime rules

- An unlisted (read-only) capture and a `&` capture are borrows. They cannot outlive the captured variable, so a lambda holding one cannot be stored or returned unless the compiler can prove the variable lives long enough (the check of borrow lifetimes, point 83 and Phase 4c).
- While a lambda with a `&a` capture lives, the outer code cannot use `a`, until the last use of the lambda.
- To store or return a lambda, its captures are owned or counted: `a!`, `->a`, `@a`, `&@a`, `%a`, `&%a`.
- Rust model: the lifetime of borrows is checked at compile time.

### 13.3.5 Implementation

- A value of a function type is a pair `{ code, context }`. A lambda without captures has a null context. The code receives the context as a hidden first parameter: a call is `f.code(f.context, args)`. A null `code` raises `UnassignedFunctionCallException`.
- For each lambda expression the compiler writes two pieces of code: the creation code, where the lambda is written (once: it takes the borrows, makes the copies, does the moves, adds the usages), and the end code, when the last holder of the context lets it go (once: it ends the owned values and gives back the usages and the weak references). A call only passes the context.
- A lambda that does not escape (given to a call, not stored and not returned) has its context on the stack, with no allocation and no count. A lambda that is stored or returned has its context on the heap, with a count. The code written by the user is the same.

### 13.3.6 What is built (compiler 0.0.95)

- Function types for local variables, parameters and results, null by default; a call of a null one raises `UnassignedFunctionCallException`. A result of a function type is written with the keyword form: `fun ->fun i32(i32) adder(i32 n)` (the form `i32(i32)` reads as the name of the function there).
- Lambdas with typed parameters, called where they are written, kept in a variable declared with the function type (`var` is a compile error), passed to a parameter and returned. The result type comes from the function type expected there; without one the lambda returns nothing.
- Captures: unlisted (read-only borrow), `&a` of numbers, `bool`, `char`, dates, objects, strings and arrays (a string or an array needs the variable that owns it, as a `&` argument does), `a!` of those values, `string?` and function values (objects are cloned, 12.6), `->a` of strings, objects, arrays, function values and counted objects, `@a`, `&@a`, `%a`, `&%a`. Inside a method the fields are captured by their bare names, with the same forms; a borrowed field borrows the object. Properties and the parent as in 13.3.1.
- Borrows (13.3.4), until the lifetime of borrows is checked: a lambda with a borrowed capture (unlisted or `&`), and a function-type parameter, can be called, passed to a call or kept in a new local; assigning it to an existing variable or returning it is a compile error.
- Every context is on the heap with a count (the stack form of 13.3.5 is not built).
- Function values in fields of classes (`public fun(i32) onClick`), in `arr`, `vec` and `list`, and in tuples (also several results: `fun fun(), i32 make()`). A field, an item or a tuple keeps only a function value that does not borrow (a lambda whose captures are copies or moves, a function): a borrowing lambda put there is a compile error. Each holder has a usage; the usage ends when the field, the item or the tuple is replaced or ends. Called as `obj.onClick(3)`, `onClick(3)` inside the class, `handlers[0](3)`, `t.f(3)`. A class prints a function field as its type, or `null`.
- Function values as values of `map` and `hmap` (`map<string, fun(i32)>`, called `m["a"](3)`) and as fields of structs (`struct Button { string label, fun(i32) onClick }`, called `b.onClick(3)`), with the same rule: only values that do not borrow, one usage for each entry or struct, ended when the value is replaced or removed or when its holder ends. A copy of the map (`clone`, `add(other)`) or of the struct copies the function values with `!`. They print as their type, or `null`. Function values are compared only with `null`: the members of a map that look for a value (`has`, `remove`, `removeAll`, `keyOf`) are a compile error on such a map.
- Parameter modes in function types: `fun(&Dog)`, `fun(->Dog)`, `fun(@Dog)`, `fun(&@Dog)`, `fun(%Dog)`, `fun(&%Dog)`, `fun(&i32)`. The lambda declares the same modes (`(&Dog d) { ... }`) and a call through the function value writes the markers of 13.1 (`rename(&rex)`, `keep(->max)`, `share(@c)`).
- `f1!` of a lambda with a `&` capture (also through a variable that holds it) is a compile error (13.3.3).
- While a lambda with a `&a` capture is kept in a local, the code after it in the same block cannot use `a` (read it, write it, capture it again) until the last use of that local or of a local that shares the lambda (`fun() g = f`).
- `f1!` (13.3.3): a new context with what the lambda owns cloned (strings copied, objects and arrays cloned, function values copied with `!` too); the captures it borrows stay borrowed. A clone of an object copies its function fields with `!`.
- Exceptions: a lambda lets its exceptions out as a function does (15), to the code that called it; a silent one is ignored there unless a catch handles it. Every lambda returns its exception (a call through a function value cannot know which lambda it reaches). In `sort` the first exception stops the comparisons (the sort finishes in an unspecified order) and is raised after the sort; in `filter`, `map` and `reduce` it stops the loop, what was built so far ends, and it is raised.
- Not built yet: function types as keys of maps and as items of sets (they have no order and no hash), `&a` of the other types (`string?`, tuples, structs, function values), and markers on a parameter of a function type itself (`&fun(i32) f`). `sort` with a lambda and the functional members (6.6) are built.

### 13.3.7 Examples

```
char z = 'z'
() { Root.Console.log(z) }          // z: read-only borrow

A a = A()
() { a.val++ }                      // compile error: not listed &
(; &a) { a.val++ }                  // explicit mutable borrow
(; ->a) { ... }                     // the lambda owns a
(; a!) { ... }                      // the lambda owns a copy of a

@Dog d = @Dog()
() { d.bark() }                     // compile error: list @d or %d
(; @d) { d.bark() }                 // the lambda holds a usage of d
(; %d) { enforce d { d.bark() } }   // weak: d may be gone

(i32 a) { Root.Console.log(a) }(42) // prints 42

// accepted by fun(i32):
(i32 x) { }
(i32 x; &a) { }
(i32 x; ->a) { }
(i32 x; a!) { }
```

## 13.4 Variadic parameters

```
fun logAll(string level, string messages...) {
  for string message in messages { r.Console.log($"{level}: {message}") }
}
logAll("info", "started", "ready")
```

- `T name...` accepts any number of `T` arguments, none included. It is the last parameter, and a function has at most one; it has no default value and cannot be named in the call.
- Inside the function `name` is a read-only `arr<T>`: it is read (`name[i]`, `name.len`, `for`) and never changed. There are no `->T name...`, `@T name...` or `&T name...` forms: the arguments are always lent read-only (objects: only their `unrestricted` methods).
- `T` is a basic type, a class or a struct; a collection (`arr`, `vec`, `list`, maps, sets, views) is a compile error.
- An existing `arr<T>` or `vec<T>`, or a view of one, given as the only argument in the variadic place is lent as the whole variadic part, with no copy: `logAll("info", msgs)`, `logAll("info", msgs[1..])`. A `list` is not accepted there (the error points to `transformTo<arr>()`). Items and a collection cannot be mixed in one call.
- When a call matches a variadic and a non-variadic overload, the non-variadic one wins.
