# 16 Namespaces, imports, aliases

```
namespace clinic.planning         // one per file, no braces
namespace local                   // name from the folder path
import Root                       // a namespace: all its public names (Console, Math, Random ...)
import Root.Console               // one declaration: only the name Console
import gfx, Root.Math             // several paths, separated by commas
alias Root as r
alias Root.Console as console
alias u8 as byte8
```

- The root file declares its namespace explicitly; `local` = root namespace + folder path. In a multi-file compilation a root file without a namespace line is a compile error; a single-file compilation does not need one.
- The root file: a file compiled on its own (given directly, or named by `source=` in a project file) is the root whatever its name; this is a single-file compilation. A program of several files has `main.df` or `program.df` as its root file, and a library has `lib.df`, at the top of its folder. A `source=` that names one of these files makes a multi-file compilation; any other name makes a single-file compilation.
- Only the root file can have top-level code (when `main()` is not needed). Every other file has only declarations (classes, traits, enums, functions, constants, aliases); top-level code or a `main` there is a compile error.
- Every other file must be in the namespace of its folder: the root namespace plus the folder path from the root. It can be written in full or as `local`; any other namespace is a compile error. So no file can add a class to a namespace outside its own folder (for example a program cannot add `gfx.MyContext` to a library) and reach its protected members.
- Namespaces are case-insensitive, and so is the match with the folder names (`Gfx/` is `gfx`). The folders of a namespace use the ASCII rule below.
- `import` takes the full path of what it brings in; a bare name is not enough. The path ends at a namespace or at one declaration (16.2).
- Where an import is looked for: the stdlib (`Root`), the folders of the program, and the libraries listed with `include=` in the project file (Compiler_Options.md). Each library is a root folder whose root file declares its root namespace. The import goes to the root whose namespace starts its path, then down the folders of the rest of the path.
- What is compiled: the root file, what it reaches through imports and, in a multi-file compilation, the other `.df` files of the folder of the root file (without an import). A single-file compilation ignores the other files of its folder. Any other `.df` file is ignored.
- Two roots with the same namespace, or a root whose namespace is inside the namespace of another root, are a compile error. The stdlib counts as a root: no library can declare a namespace inside `Root`, because `internal` members are visible to the sub-namespaces (1.6.1).
- A single-file compilation can import only its own subfolders and the stdlib; `include=` lines of its project file are ignored with a warning (until compiled libraries exist).
- Folder names used for `local` namespaces must be ASCII letters, digits and `_` only, no exceptions; any other folder is ignored by the build (level 3 warning). Two folders whose names differ only by case are a compile error.
- `alias <original> as <new>`; aliases are pure aliases (interchangeable with the original). They can also go to members and functions: `alias Root.Console as c` and `alias Root.Console.log as log`

## 16.1 Names and visibility

Namespaces are almost transparent: a name is qualified only when two namespaces give the same name.

```
namespace a.b.c
class A { }                    // no keyword: only a.b.c
internal class B { }           // a.b.c and its sub-namespaces
public class C { }             // everyone
class Z { A a = A() }          // valid: same namespace

namespace a.b.c.d
class D { A a = A() }          // error: A has no keyword
class D { B b = B() }          // valid: internal, seen by the sub-namespaces
class D { C c = C() }          // valid

namespace x.y.z
class X { C c = C() }          // valid only with import a.b.c
class X { a.b.c.C c = C() }    // valid: fully qualified, no import needed
```

- Visibility of the top-level declarations (classes, traits, structs, enums, functions, constants): no keyword = only their own namespace; `internal` = the namespace and its sub-namespaces; `public` = everyone. There is no `private` keyword.
- An unqualified name is looked for in this order: the own namespace (it always wins), the enclosing namespaces (nearest first, `internal` and `public` names), the imported namespaces (`public` names). The same name in two imported namespaces is a compile error that asks for the qualified name.
- A fully qualified name (`a.b.c.C`, `a.b.c.make()`, `a.b.c.Color.Red`) needs no import: the compiler loads its namespace. It follows the same visibility: `public`, or `internal` from the namespace and its sub-namespaces.
- The standard library is a namespace like the others: without an import its names are written in full (`Root.Console.log(...)`); `import Root` lets a file use the names directly inside `Root` (`Console.log(...)`, `Math.sqrt(...)`), `import Root.IO` the names of `Root.IO` (`File(...)`), `import Root.Console` only the name `Console`. A name of the program with the same spelling wins.
- An alias of a namespace qualifies as well: `alias a.b.c as abc`, then `abc.C()`.
- `a.b.c.C c = C()`: a bare constructor call takes the namespace of the declared type.
- Members marked `internal` (1.6.1) are seen by the code of the namespace of their class and of its sub-namespaces.
- The qualified name of a class is its namespace plus its name (`a.b.c.C`): it is the name of its hash (6.2.1). A program without a namespace uses `Root.`. Printing an object shows the name as written (`C { ... }`).

## 16.2 Imports

```
import Root                 // the namespace Root: Console, Math, Random, Date ... by their bare names
import Root.IO              // the namespace Root.IO: File, Stream, FileStream ...
import Root.Console         // the class Console only: Console.log(...); Math is still Root.Math
import gfx.Context          // the class Context of the library gfx only

Console.log("hi")           // with import Root or import Root.Console
Root.Console.log("hi")      // always valid, with or without an import
```

- The path of an import ends at a namespace or at one declaration of a namespace (a class, a trait, a struct, an enum, a set, a function or a constant).
- A namespace brings in all its `public` names (`internal` ones too from the namespace and its sub-namespaces, 16.1). It does not bring in the names of its sub-namespaces: `import Root` gives `Console`, not `File`, which needs `import Root.IO`.
- A declaration brings in only its own name. Its members are reached through it, as usual: `import Root.Console` gives `Console.log(...)`, `Console.Color.Red`, not a bare `log(...)`. To use a member without its class, use an alias (`alias Root.Console.log as log`).
- The visibility of the declaration applies: importing a name that is not `public` (or `internal` from the namespace and its sub-namespaces) is a compile error.
- A path that is both a namespace and a declaration cannot exist: a namespace and a declaration of its parent namespace cannot have the same name (compile error at the declaration).
- Importing the same name twice (`import Root` and `import Root.Console`) is allowed and changes nothing. The same name from two different namespaces is the compile error of 16.1, also when one of them is imported as a single name.
- The search order of 16.1 does not change: a name imported alone is an imported name, after the own namespace and the enclosing ones.

### 16.2.1 What goes into the executable

- An import gives names; it adds no code. A program that imports `Root` and uses only `Console.log` has the same executable as one that writes `Root.Console.log` without imports.
- Only what the program uses goes into the executable: the classes, the methods and the functions it calls (directly or through what it calls), of the program, of its libraries and of the standard library. A class that is never used adds nothing; a method of a used class that is never called adds nothing.
- A method that can be reached through dispatch is kept: when a class is used, the methods that replace a method it calls through a parent or a trait stay in the executable even if the program never names them.
- The same holds for the generic copies (11.3): only the copies the program uses are made.
