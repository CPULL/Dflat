# 20 Multitasking (Root.Tasks)

Everything here is preliminary, syntax included.
V 0.0.7 2026/11/23

## 20.0 Usage
Multitasking is not included by default in DFlat programs.

An `import Root.Tasks` is required: the full namespace path, as every import (16). Namespaces are case-insensitive, so `import root.tasks` is the same.

The multitasking runtime is in the program only with this import: without it the runtime has no thread support and no cost for it. A library built with `import Root.Tasks` brings it into the program that links it; a library built without it cannot be linked by a program that has it (15.8).

## 20.1 Execution units

- Three kinds: **Process**, **Task**, **Thread**. Weight: process > task > thread. They are independent kinds (">" means heavier, no containment).
- **Task**: a class that runs on its own. Any class can become a task by implementing `taskRun()`.
- **Thread**: a function (lambdas too) that runs on its own.
- Functions can be defined anywhere, not only in classes (implicit main object).
- Process, Task and Thread share a trait/superclass (**Runnable**) with common properties and methods, including:

```
fun ReturnType wait()
```

- A thread started directly belongs to the task that starts it (or the implicit main task).
- **All Runnables use deferred start**: creation puts the runnable in `Ready` status, then `.start()` begins execution.
- `wait` collects the next value the runnable hands out with one of the `return` forms (below, and section 20.2).

### Task

The `Task()` constructor takes the class itself followed by its constructor parameters. The object is built inside the task's memory space; the parameters cross the boundary with the normal passing modes (section 20.12). Then `taskRun()` starts after `.start()` is called.

`Task()` has two named parameters of its own, `timeout` and `linked`, written with the normal named arguments (13):

```
Task t = Task(MyTask, 123, "blah", timeout: 3600000, linked: false)
t.start(timeout: 5000)
```

- The named arguments `timeout:` and `linked:` inside `Task(...)` always belong to `Task`, never to the constructor of the class. A class with its own parameters named `timeout` or `linked` gets them positionally.
- `timeout` (milliseconds as an integer, or a `lapse`) is the maximum time a value of the task waits to be handed over on the side of the task: a blocking `return` or `return!` that nobody collects drops the value when it runs out (below).
- It can be written in the constructor and in `start(timeout: ...)`. The latest wins: constructor < `start`.
- The waiter has only the timeout of its `wait` (20.2.8).
- `linked` (`bool`, default `true`):
  - `true`: the task is a child of the runnable that creates it, and gets the soft kill (section 20.10) when its parent ends.
  - `false`: the task is a child of the main program, and ends when the main program ends (section 20.10).



```
class MyTask {
  public i32 val
  internal string txt
  arr<u64> data[256]

  fun taskRun() {
    data.fill(val)
    ...
  }
  fun method1() { ... }
  fun method2() { ... }
}

Task task = Task(MyTask, 123, "blah")   // Ready: object built inside the task
task.start()                            // Running: taskRun() begins
wait task timeout 5000                  // waits up to 5000 ms
```



- After `Task(MyTask, ...)` the creator holds only the handle. The object belongs to the task: `method1()` and `method2()` are the task's own code.
- The constructor of the class runs at `Task(...)`. An exception it raises goes to the creator, there, as for any constructor.
- `start()` gives the handle itself: on a new task it is given (`Task t = Task(MyTask).start()`), on a handle that is in a variable it is lent (`Task b = a.start()`: `b` is a borrow of `a`). A task has one owner.
- A handle cannot be cloned: `t!` is a compile error.
- A task cannot be started more than once from the same handle: a second `start()` raises `TaskAlreadyStartedException`, a real exception, not a silent one.
- `taskRun()` can also be called directly, as a normal method of a normal object, without `start()`. Then every execution of `return!` or `return?` raises `ReturnOutsideATaskException`.
- The methods of the task can be called through the handle (`ticker.stop()` in the sketch below): the public ones and the `unrestricted` ones, and also the internal ones from the same namespace.
- Fields are never reached through the handle, public ones included: only methods and properties (their accessors are methods).
- A call through the handle runs inside the task, at its next checkpoint (a `wait`, an `enforce`, a `return` of any kind: section 20.8), never on the caller's side.
  - Only the checkpoints of `taskRun()` serve the calls. A checkpoint inside a call that is being served only does its own job: calls never nest.
  - The arguments and the result cross with the normal passing modes (section 20.12), as the constructor parameters do.
  - A method that returns nothing is posted and the caller goes on: `ticker.stop()`.
  - A method that returns a value is waited for: `var n = wait ticker.getCount() timeout 500`.
  - A call on a task that is not running (not started yet, or ended) raises `CalledANotRunningTaskException`, a regular exception.
  - An exception that leaves a called method goes to the caller that waits for its value. When nobody waits for it (a posted call), the task becomes `Failed`.
  - A task in a loop with no checkpoint never serves its calls (the warning of section 20.8).
- `wait task` collect the next produced item from the task, returned by `return` (task waits for the waiter to collect, then ends), `return!` (task waits for the waiter to collect), or `return?` (task does not wait and continue also if nobody is waiting right now.)
- `wait` on a task that is no more running returns a zero or null value (also composite) and produces a silent `TaskAlreadyTerminatedException`.
- `wait` on a task that was not started: the timeout of the `wait`, then a zero or null result and a silent `TaskWasNotStartedException`.
- A task is still an object: when it goes out of scope and is no more running, it is removed like any other object. It does not matter if the result was collected or not.
- No leaks: when the task has ended, nobody is waiting and nobody references its handle anymore, it terminates and all its memory is released.
- A task that is running remains alive, also when its handle goes out of scope. It ends with its parent (`linked`) or at the end of the main program, as in section 20.10.


Sketch of a task that returns many times: `return` sits inside the loop of `taskRun()`, and a public method is there to stop it.

```
class MyTask(i32 delay) {
  bool alive = true
  u64 count = 0
  fun u64 taskRun() {
    while alive {
      Root.Time.wait(delay)
      count++
      return? count
    }
  }
  public fun stop() {
    alive = false
  }
}

Task ticker = Task(MyTask, 100).start()
var n = wait ticker timeout 5000   // the next count
ticker.stop()
```

- `return` in `taskRun()` ends the task.
- When `taskRun()` ends without a `return` and it is not void, it is a `return 0` or `return null`: it waits to be collected, as `return val`. An exception comes only when the task is waited again after it has terminated.
- Three forms of `return`:
  - `return val`: wait until somebody collects the value, then exit the task/thread. When the timeout runs out first, the value is dropped and the task ends.
  - `return! val`: block and wait until somebody reads the value, then continues. When the timeout runs out first, the value is dropped and the task continues.
  - `return? val`: post the value to whoever is reading (if anybody is) and continue without waiting (it is an `async return`).
- A task that ends because its value was not collected is `Completed`. No exception on the task side: the exceptions are only on the receiver side.
- An exception that leaves `taskRun()` ends the task as `Failed`, and the waiter gets it as the extra error value (section 20.2).
- A void `taskRun()`: `wait task` waits for the end of the task and gives no value.

### Thread

The function comes first, its arguments follow. They are taken when the thread is created.

```
fun lapse runThis(u32 time = 1234) { ... }

Thread tr1 = Thread(runThis)          // Ready, default arguments
Thread tr2 = Thread(runThis, 567)     // Ready
tr1.start()                           // Running
tr2.start()                           // Running

var res1 = wait tr1 timeout 5000     // what runThis returned
var res2 = wait tr2 timeout 5000
```

- A thread is a simple function that is run in parallel. Threads do not have a `taskRun()` method.
- A thread is a function of its parent runnable, run in parallel: it has access to whatever the parent gives.
- A thread cannot live without a task: it needs the parent context to use data.
- Threads are as lightweight as possible: the compiler does not check what a thread reads and writes of its task. The code is thread safe, or it uses `mutex` and `enforce` (20.13); otherwise the result is not guaranteed.
- The handle of a thread never leaves its task: it cannot be given, lent to another task or returned outside of it. Only the parent waits on it.
- A thread cannot wait on a task of its parent, which owns it (20.2.6).
- The three forms of `return` work in a thread function as in `taskRun()`: a thread can hand out many values.
- A thread cannot start another thread: only a task (or the main program) starts threads. `Thread(...)` written in a function that runs as a thread is a compile error; where the compiler cannot see it (a handle given to the thread), `start()` raises `ThreadStartedByAThreadException`, a real exception.
- `Thread()` takes the named argument `timeout` (milliseconds as an integer, or a `lapse`), after the arguments of the function: `Thread(runThis, 567, timeout: 5000)`. It bounds the blocking `return` and `return!` of the thread, as for a task (the waiter may be gone): when it runs out the value is dropped, `return` ends the thread, `return!` continues. The order is the one of the task: constructor < `start`. The waiter has only the timeout of its `wait` (20.2.8).
- When its task ends, for any reason, the threads still running get the soft kill (20.10). The task does not wait for them.

```
fun u64 aThread(u32 d) {
  while d > 0 {
     wait 1000 // 1 sec
     return? d
  }
}

Thread t = Thread(aThread, 10).start()
```

The handle can be written with its result type: `Thread<lapse>` for `runThis`, `Thread<u64>` for `aThread` (sections 20.9 and 20.15).

## 20.2 Wait

There is one keyword, `wait`, for everything that is waited for.

A task has many things that can happen: events from the UI, signals from the parent, messages from other processes, streams that complete to receive data. Each of them is a **waitable**: something that is ready to be processed. "Waitable" is not a trait: it is only the name of the group of items a `wait` can wait for.

A `wait` lists all the waitables that can arrive and gives the code to execute for each one. It is the dispatch point of the task, in place of callbacks: mailboxes and streams do not call code when something arrives, they are waited on.

The first time a wait is reached, its runnable is registered with all its waitables. Subsequent executions reuse the existing registrations until the containing scope ends; only a branch whose variable now holds a different object (a new promise, or a previous one set to null) registers again (20.2.4).

`wait` is a keyword only when a target follows it on the same line (`wait t`, `wait on t`, `wait 250`), or when it stands alone on its line followed by `on` branches. Elsewhere it stays a name: `wait(...)` is a call, and a variable named `wait` can be used, also as the value of a `timeout` (`enforce timeout wait player.bump(2)`). `wait 250` waits a fixed time (20.8); a bare `wait` with no `on` branch after it is the checkpoint of 20.8.

### 20.2.1 Form

One waitable: `on` is optional.

```
wait t as res { use(res) } timeout 1000 { log("no result") }
wait on t as res { use(res) } timeout 1000 { log("no result") }

var res = wait t timeout 500 { 0 }                       // as an expression: 0 when the time runs out
```

A wait on a single variable with no code to execute skips the braces:

```
wait go timeout 1000                                     // a signal: waits for it, nothing to run
var n = wait ticker timeout 5000                         // the next value of the task; zero or null when the time runs out
```

Several waitables: `wait` alone on its line, one `on` branch for each waitable on the lines after it (the next-line rule of `atEnd`, 14.2).

```
Signal s1 = Signal(SignalMode.Single, "S1")
Signal s2 = Signal(SignalMode.Single, "S2")
Signal sj1 = Signal(SignalMode.Broadcast, "SJ1")
Signal sj2 = Signal(SignalMode.Broadcast, "SJ2")
Token jobs = Token("jobs")

Event<Size> resize = Event("resize")

Task t = Task(MyTask, 123).start()

MailBox msgbox1 = PostOffice.find("MsGbOx1")
MessageStream msgStream = msgbox1.getStream()

wait
  on s1 {
    // s1 is a signal and has no data
  }
  on s2 {
    // ...
  }
  on sj1, sj2 as sj {
    if sj == sj1 { ... }
  }
  on jobs {
    // a token of jobs was consumed: do one job
  }
  on resize as ev {
    // process the new size in ev
  }
  on t as taskRes {
    // process taskRes from t
  }
  on msgbox1 as msg {
    // a message msg arrived on mailbox msgbox1
  }
  on msgStream as data {
    // data received from the mailbox stream msgStream
  }
  timeout 5000 {
    // nothing arrived for 5 seconds: send a keepalive
  }
```

In a loop, with an async read and the catches:

```
Signal stop = Signal(SignalMode.Single, "stop")
Token tick = Token("tick")
Event<Size> resize = Event("gfx.window.ui.resize")
Task t = Task(MyTask, 123).start()
MailBox msgbox1 = PostOffice.find("MsGbOx1")
promise<i32> reading = myStream.readAsync(&buff, 4096)

#again#
wait
  on stop { return }
  on tick { count++ }
  on resize as size { layout(size.w, size.h) }
  on t as res { use(res) }
  on msgbox1 as msg { handle(msg) }
  on reading as bytesread {
    process(buff, bytesread)
    reading = myStream.readAsync(&buff, 4096)
  }
  catch ChannelClosedException on msgbox1 { msgbox1 = null }
  catch StreamException ex on reading { report(ex.message) }
  catch Exception ex { report(ex.message) }
  timeout 2000 { sendKeepAlive() }
jump #again#
```

One waitable with its catch:

```
wait reading as bytesread { ... } catch StreamException ex { ... } timeout 1500 { /* do this if timed out */ }
```

- `as name` names what the waitable gives: the data of an event, the value of a task, the message, the result of the operation (`bytesread`).
- Several signals in one branch: `on s1, s2 as s { if s == s1 ... }`; `s` is the `Signal` that fired (20.3).
- An event with its filter: `on resize from window1 as size { }`.
- The clauses after the branches are those of `enforce` (7.2.3): `catch E [ex] [on x]`, `atEnd`, `default`, plus the mandatory `timeout`.
- The `timeout` clause comes after the `on` branches, before or after the catches.
- A branch names only variables and objects whose type is a waitable. A call is not allowed (`on stream.readAsync(...)`, `on t.getCount()`): the call makes its promise first, and the `wait` waits on the promise.

### 20.2.2 What can be waited on

- `Signal`, signal groups (20.3)
- `Token` (20.3.2)
- `Event<T>` (20.4)
- `Task` and `Thread`: the next value they hand out (20.1)
- `MailBox`, `MessageStream` (21.3)
- `promise<T>`: what an async operation gives back (`stream.readAsync(...)`). It fires once; a new operation gives a new promise. The word `promise` is reserved; its behavior is not defined yet (20.18): it can fire as soon as enough data arrived, at a timeout, or as soon as some data arrived.

### 20.2.3 One waitable for each run

- Each run of the `wait` executes one block, then the code after the `wait` goes on. A loop around it (a label and `jump`, `while`) waits again.
- When several waitables are ready together, the branches take turns: the `wait` keeps track of the last branch that ran, and the next run tries first the branch after it, then the ones after that, wrapping back to the first. The first run starts from the first branch in written order.
- The `wait` is a checkpoint (20.8): in `taskRun()` the calls through the handle are served while it waits, and the cancel signal is seen.
- A target that becomes null (`msgbox1 = null`) is ignored by the next runs of the `wait`. What to do with a waitable that failed is up to the developer.
- A task or a thread that has ended and has nothing left to give is ignored by the next runs of the `wait`, as a target that is null.

### 20.2.4 Registration

- The `wait` enables all the items it is waiting for to actually receive the events, the first time it is processed. They remain enabled to receive signals, events, etc. until the scope containing the `wait` ends.
- The registration belongs to the runnable, not to the `wait`: a runnable is registered once for each waitable, whatever the number of its waits that name it. It starts with the first `wait` that names it and ends when the last scope that contains such a `wait` ends.
- It is the same for a `wait` on one waitable and for a `wait` on several, with or without a block: after `wait go timeout 1000` has timed out, the runnable remains registered for `go` until the scope ends.
- Branches on the same event with different `from` are different waitables: one for each sender.
- A waitable that is not a variable or a field (`wait Task(X).start() timeout 500`) is registered only while it is waited for.
- For a `wait` in the body of a loop, the scope is the one that contains the loop: the items remain enabled from one turn of the loop to the next.
- Waitables that arrive while the code runs outside the `wait` (a block, or the code of the loop) are kept: the next `wait` of the runnable that names them, the same one or another, gets them.
- When the registration ends, what is pending for it disappears, except what its source keeps: an ExclusiveSafe send goes back to its counter, a static event stays in its queue. A token is never set aside for a `wait`: it stays in the count of its `Token` until a `wait` consumes it.
- An event, a token and a message belong to their owner, the one that registered the source: `Event.register` (20.4.3), `Token.register` (20.3.2), `postOffice.register` (21.2). When a waiter ends, they stay for the others; when the owner ends, they disappear. A task that gives its last value with `return val` ends after the value is collected: until then, and for the instant after it, the names it registered are still taken.
- An Exclusive signal has the runnable as its listener until the registration ends; a send stays there until it is processed. The waits of one runnable never conflict with each other on it.

### 20.2.5 Arrivals while a block runs

- Another waitable is kept, without penalties: one arrival for each waitable.
- The same waitable as the one being processed:
  - a token: in the count of its `Token`;
  - a static event: queued, following its `keep` and `fullMode` (20.4.4);
  - a volatile event: one is kept; a newer one replaces it (the last one wins);
  - a task or a thread handing out a value with `return` or `return!`: kept (the task waits to be collected, up to its own timeout, 20.1);
  - any other one (Broadcast, Single, Exclusive signals, `return?`): abandoned for this runnable; another waiter can receive it.
- A runnable that is not waiting loses its turn for an event, never the event: the next waiter receives it at once, and this runnable receives it later, if it is still there (20.4.5).

### 20.2.6 Who can wait on a task

- Only the owner of the handle waits on a task. When the handle is lent with `&`, the borrower waits and the owner cannot until the lend ends. A plain lend does not give the right to wait: a `wait` takes a value away from the task.
- One borrower at a time: a second lend of the same handle to another runnable, while the first one lasts, is a compile error.
- A `wait` on an `@Task` or a `%Task` is a compile error. A `Task` that is a global is waited on only inside its lock.
- The threads follow the rules of 20.1: only the parent waits on them.
- The place on the task belongs to its owner (or borrower), not to a `wait`: all its waits share it, and the one that runs takes the next value. A `wait t` inside a block of a `wait` that has `on t` takes the value after the one of the block.
- A `wait` by a runnable that is neither the owner nor the borrower is a compile error where the compiler sees it; otherwise it raises `WaitingOnANotOwnedTaskException`.
- To tell many runnables that a task has ended, the task sends a Broadcast signal.

```
wait
  on t as header {
    var body = wait t timeout 500    // the value after the header
    use(header, body)
  }
  on stop { alive = false }
  timeout 1000 { }
```

### 20.2.7 Exceptions

- A waitable can fail while it is waited for: a channel destroyed, a stream error, a failed promise, a task that ended with an exception.
- An exception that leaves the function or `taskRun()` reaches the waiter, and the runnable ends as `Failed`. It goes to one `wait` only; the later waits get the silent `TaskAlreadyTerminatedException`.
- As all exceptions, it follows the Rust `Result` model: `wait` gives the actual return values plus an extra error value with the exception, if any.
- The catches follow the rules of `enforce` (7.2.3), read from top to bottom, the first that matches handles the exception:
  - `catch E on x` runs only when the waitable `x` fails;
  - a catch without `on` runs when no more specific catch that matches comes before it.
- An exception raised by the code of a branch block does not come from its waitable: `catch E on x` does not take it, a catch without `on` does.

### 20.2.8 Timeout

- The `wait` has one timeout, and it is mandatory: `timeout <t> { ... }` (the braces can be skipped on a wait on a single variable, 20.2.1). A `wait` without it is a compile error. It forces the programmer to always be intentional about how long to wait.
- A timeout is in milliseconds (an integer) or a `lapse`.
- The timeout is idle time: it runs out when no waitable is ready for that long. Each run of the `wait` starts it again.
- When it runs out, the `timeout` block is executed.
- A wait does not time out once the data of a waitable started to arrive (a stream, a message): at each arrival, also if not completed, the timeout starts again.
- As an expression, the value of the `timeout` block is the result when the time runs out, following the rule of the clauses of 7.2.6: `var res = wait t timeout 1000 { 123 }`. `enforce wait ... default` is not needed any more.
- The waitables have no timeout of their own for the receiver. These go away: the timeout of `Signal(...)` and of a signal group, `Event(name, timeout:)`, the registration timeout used by the waiters, the timeout of `start()` and of the constructor of a task used by `wait t`, the timeout embedded in a mailbox.
- These stay, because they are not waits on a waitable: the timeout of a task or a thread on its own `return` / `return!`, the registration timeout of an event used by `BlockSender`, `kill(timeout)`, the timeouts of `mutex` and `semaphore`.

### 20.2.9 Open points

- Async streams: the protection of a buffer from data races while the operation is pending (the buffer stays its owner's; the promise cannot reach it).
- `promise<T>`: when it fires.
- The timeout of a wait: a timed OS wait or a runtime timer.
- A task or a thread with no timeout of its own: how long its blocking `return` / `return!` waits to be collected.

## 20.3 Signals

Communication has three levels, all important: **signals** (a bare go, section 20.3), **events** (a well defined payload, inside one process, section 20.4) and **messages** (variable data, also between processes and machines, chapter 21).

- What a signal is for: "I need to wait for a go, I do not care about anything else".
- A signal is only an alert. It can be shared by many waiters or belong to one. It is sent, consumed and then gone. Underneath it is little more than a counter.
- Generic system with one uniform interface in the language. Each source (OS, window, runnable, user code) defines its own signals and decides how they are intercepted per OS.
- A signal has no payload and may have no sender. It is a bare notification. Messages are a separate thing and carry content.
- A signal is identified by an unsigned number or by a string. The two are separate namespaces: `Signal(20000)` and `Signal("myapp.go")` never meet.
- Numbers below 4096 are reserved. `KnownSignals` gives names to them. `Signal(n)` with such a number raises `ReservedSignalException`.
- Number 666 is reserved as the cancellation signal (no OS uses it).
- Mode is set at signal creation, and never changed when sending, because waiters with different modes cannot live together. The mode is optional. Default is **Single**. For immediate creation and send (`Signal.send(SignalMode.Broadcast, "bump")`) the signal is first created and then immediately sent.
- Polymorphic constructors: strings for custom ones and uns for numeric ones, where the first 4096 are reserved and listed in the enum `KnownSignals`.
- Also used as cancellation signals.
- Signal modes:
  - **Broadcast**: any number of listeners, all notified. Lost if nobody is waiting.
  - **Exclusive**: only one listener allowed (a second listener is an error: its `wait` raises `ExclusiveSignalBusyException`). Lost if nobody is waiting.
  - **Single**: any number of listeners, one woken per fire (FIFO). Lost if nobody is waiting.
  - **ExclusiveSafe**: one receiver, as Exclusive, and never lost: it is kept until the next checkpoint of the receiver (20.8). The mode of the pre-registered kill signals (`KnownSignals.Cancel`). Open: whether a program can make its own ExclusiveSafe signals.
- Combined wait: first signal to fire wins, only for wait. The result is the `Signal` that fired, null when the time runs out.
- `==` between two signals compares the signals, not the objects: `Signal("a") == Signal("a")` is true.
- The registry of the signals is global: one for the whole process. An entry exists as soon as either side uses its name, and it has no owner; the same name with a different mode is an error (`SignalModeMismatchException`).
- A few names are pre-registered: the signals of the soft kill (20.10), `KnownSignals.Cancel` (666) first.

### 20.3.1 Signals sent to a runnable

A signal by itself has no target. To reach one runnable, it is sent to it with the method of the Runnable trait (20.9):

```
Task t = Task(MyTask, 123).start()
t.signal(Signal("myapp.reload"))
t.signal(Signal(KnownSignals.Cancel))     // what kill() does (20.10)
```

- The signal goes into the queue of the runnable, as the calls through the handle (20.1).
- The runnable checks its signals at every checkpoint (20.8): a wait of any kind, an enforce, a return of any kind.
- What happens there depends on the mode of the signal:
  - Broadcast, Single, Exclusive: it counts only if the runnable is waiting on that signal at that moment; otherwise it is lost.
  - ExclusiveSafe (the kill signals): it is never lost. At its next checkpoint the runnable starts ending: its `atEnd` blocks run and the `enforce` scopes unwind (20.10).

Life of a signal: created, waited for (the subscription), sent.

```
Signal wakeMeUp = Signal("wakemeup")
...
wait wakeMeUp timeout 5000     // the subscription
...
wakeMeUp.send()                // the emit
```

```
Signal wrs = Signal("Window.resize")
Signal pkill = Signal("Process.Kill")
Signal existing = Signal.tryGet(SignalMode.Exclusive, "named.signal") // returns null if such signal was not registered.
```

Constructor syntax: mode first (optional, defaults to Single), then name/number.

```
enum SignalMode { Broadcast, Exclusive, Single, ExclusiveSafe }

Signal go     = Signal("myapp.go")                          // default Single
Signal job    = Signal(SignalMode.Single, 20000)            // explicit mode, number
Signal done   = Signal(SignalMode.Broadcast, "myapp.done")  // explicit mode, string
Signal kill   = Signal(KnownSignals.Kill)
Signal cancel = Signal(KnownSignals.Cancel)                 // 666

go.send()
wait go timeout 1000
Signal.send("myapp.go")              // static, no mode, defaults to SignalMode.Single
Signal.send(SignalMode.Broadcast, "blah")
SignalGroup anyExclusive = Signal.group(SignalMode.Exclusive, 12356, "bump")
```

```
SignalGroup anySingle = Signal.group(35678, "bump", 77777, "foo")
Signal res = wait anySingle timeout 5000      // null: none of them fired

Signal s1 = Signal("first")
Signal s2 = Signal("second")
SignalGroup sg = SignalGroup(s1, s2)
wait on sg as fired {
  if fired == s1 { ... }
} timeout 5000
```

A `SignalGroup` holds signals only, never tokens, and keeps which signals they are, not the objects. `number` and `name` of a `Signal` say what it was made with (`number` is null when it was a name, `name` is empty when it was a number).

Signals and SignalGroups are waitables (20.2): they have no timeout of their own, the timeout is the one of the `wait`. A SignalGroup cannot be sent.

### 20.3.2 Token

A `Token` counts what has been produced and not consumed yet: `produce()` adds one, each `wait` consumes one. A token goes to one waiter only, and it is never lost.

```
// the owner
Token jobs = Token.register("myapp.jobs")

// anybody else
Token jobs = Token("myapp.jobs")

jobs.produce()                    // one token more
jobs.produce(12)                  // twelve more

wait jobs timeout 500             // consumes one
wait jobs timeout 0               // consumes one if there is any, without waiting

while alive {
  wait
    on jobs { work() }            // each run consumes one
    on stop { alive = false }
    timeout 1000 { }
}
```

- `Token.register(name)` makes the token and returns it; `Token(name)` finds it. Any runnable can produce and any runnable can consume.
- The names follow the rule of the events (20.4.1). There are no numbers.
- The owner is the runnable that calls `Token.register`. When it ends, the count disappears and the name can be registered again. A second `register` of a name that is registered raises `TokenAlreadyRegisteredException`.
- A name that is not registered gives no error: `produce` and the waits on it are skipped. When it is registered, they start to work.
- `produce(n)` takes an `uns`; `produce(0)` does nothing. The tokens wake the waiters in order (FIFO), one token for each.
- A `wait` consumes one token, always. The wait is the only way to consume.
- `jobs.count` (read-only, `uns`) is the number of tokens there now: one already handed to a runnable that is inside its `wait` is not counted; `jobs.name` is the full name.
- A `Token` gives no value: `on jobs` takes no `as`. It cannot be in a `SignalGroup`, and `t.signal(...)` (20.3.1) does not take it: a runnable that receives work registers a `Token` of its own.
- A semaphore (20.14) has a fixed number of permits, each one given back at the end of its block; a token is made by `produce` and is gone once consumed.

## 20.4 Events

An event is a signal with data: a struct, given by the sender to the receivers, inside one process. The syntax follows the one of the signals (20.3).

### 20.4.1 Names

- An event is identified by a string name, never by a number. The registry is one for the whole process.
- A name with a dot is a full name and is used as it is: `"gfx.window.ui.resize"`.
- A name without a dot gets the namespace of the file in front: in `namespace a.b.c`, `Event<Size>("nosize")` is the event `"a.b.c.nosize"`. In a file without a namespace the name is used as it is.
- `name` gives the full name: `nosize.name == "a.b.c.nosize"`.

### 20.4.2 Data

- Each event carries a struct, its data, written as the type argument: `Event<Size>`.
- In the block that receives it, the data is the plain struct, with its fields. The compiler adds there, and only there, the members of the propagation (20.4.5): `processed`, `setProcessed()`, `stopPropagation()`. A copy of the data taken out of the block is a plain struct, without them.
- A struct used as the data of an event cannot have a member with one of those names: `events.df(19): setProcessed is a reserved word for structures used as event data.`
- The data is read-only for the receivers.
- The fields of the data cross the tasks (20.12): numbers, strings, enums, structs of them, `Sender<T>` (20.4.6). Plain objects, weak references, reference count, and arrays are not allowed.

### 20.4.3 Sender and receivers

The sender registers the event; the receivers find it. A receiver cannot create an event.

```
struct Size { Sender<Window> window, u32 w, u32 h }

// sender
Event<Size> resize = Event.register("gfx.window.ui.resize")
resize.send(Size(myid, 256, 128))     // in a method of Window

// receiver
namespace a.b.c
Event<Size> resize = Event("gfx.window.ui.resize")
wait on resize as newsize timeout 200 { ... }
Event<Size> nosize = Event("nosize")    // a.b.c.nosize
```

- `Event.register(name, mode, timeout, keep:, fullMode:)` makes the event when the type of the structure can be inferred. The registrator sets its mode (20.4.4): `Event<Size> resize = Event.register("gfx.window.ui.resize")`
- `Event.register(name, struct, mode, timeout, keep:, fullMode:)` makes the event without requiring to assign to a fully qualified variable: `var resize = Event.register("gfx.window.ui.resize", Size)`
- The owner of the event is the runnable that calls `Event.register`. When it ends, what is in the queue disappears (a block that is processing an event ends normally) and the name is no more registered: it can be registered again.
- `Event(name)` finds an event that is registered.
- A name that is not registered yet gives no error: the waits and the sends on it are skipped. When the name is registered later, they start to work.
- The struct is checked at run time against the one of the registration: the same name with another struct raises `DuplicateEventNameWithDataMismatchException`.
- Events are waitables (20.2): the receivers have only the timeout of the `wait`.
- The `timeout` of the registration is how long a send waits for room in a full `BlockSender` queue (20.4.4). It is not used by the receivers. It is written only with `fullMode: EventQueueFullMode.BlockSender`, and there it is required (compile error otherwise).

### 20.4.4 Modes

```
enum EventMode { Volatile, Static }
enum EventQueueFullMode { DiscardNewest, DiscardOldest, BlockSender }

Event<Size> resize = Event.register("gfx.window.ui.resize", EventMode.Static, keep: 4, fullMode: EventQueueFullMode.DiscardOldest)
Event<Size> moves = Event.register("gfx.window.ui.move", EventMode.Static, timeout: 1000, keep: 4, fullMode: EventQueueFullMode.BlockSender)
```

- **Volatile**: an event that nobody is registered for is lost.
- **Static**: an event that nobody is registered for stays, for the next waiter. `keep:` is how many the queue holds; `fullMode:` says what a send does when it is full: the new event is discarded, the oldest one is discarded, or the sender waits (up to the `timeout` of the registration).
- When the queue is full, the oldest event that some runnable has already processed leaves first, for the runnables that have not had it yet too. `fullMode` applies only when there is no such event.
- `DiscardOldest` always takes out the oldest event, also when a waiter has it in its block now: that block ends normally, then the event is gone and no other waiter receives it.
- How a static event is kept (one, a queue, a small queue that blocks or discards) is still to be evaluated: the syntax above is preliminary.

### 20.4.5 Propagation

- When several runnables wait for the same event, they receive it in sequence, one after the other (FIFO). One that is registered but not waiting now loses its turn and receives the event later, when it waits again.
- `processed` is read in the receiving block; only `setProcessed()` changes it.
- `stopPropagation()` blocks the event: the next waiters do not receive it at all.
- An event stays until it is consumed (every runnable registered for it is done with it, or `stopPropagation()` is called), its owner ends, or its queue is full (20.4.4).


### 20.4.6 The sender of an event

- A field of type `Sender<T>` says who sent the event. It holds the id of an object of the class `T` (or of a subclass), not a reference to it: the receiver identifies the sender, it never reaches it through the event. Any valid field name is accepted: `Sender<Window> window`, `Sender<Button> sender`.
- Every object of a class named in a `Sender<T>` has a unique id: a `u64` from one counter of the process, given when the object is made. An id is never used again, also after its object has ended. The other classes have no id and pay nothing.
- The sender fills the field, as every other field of the struct:
  - `myid`: the id of the object the method runs on. It is written only as the value of a `Sender<T>` field, in a method of `T` or of a subclass; anywhere else (another class, a function with no object) it is a compile error.
  - any instance of `T`: its id is stored, `Size(window2, 256, 128)`.
- A struct has at most one `Sender<T>` field: with two, `from` would not know which one to compare (compile error).
- `wait on ev from x as data { }` receives only the events whose sender is `x`: the ids are compared, nothing is reached. An event of another sender is not taken: it stays for the other waiters, in the same order.
- To use the sender, the receiver uses its own reference to it (`window1` above), with its own rules.

```
wait on resize from window1 as newsize timeout 200 { ... }
```

### 20.4.7 Receiving

- An event is received with the `wait` of 20.2: `wait on ev [from x] as data { ... } timeout t { ... }`. The data is reached through `data` inside the block.
- Several events in one wait are several branches (20.2.1): `on resize from window1 as newsize1 { ... }`, `on resize from window2 as newsize2 { ... }`.

## 20.5 Farm (data-parallel construct)

- Name: **farm**. Blocking call: starts N threads and waits for them.
- **Split**: a function (or code inline in the block) that takes the farm params and returns one param tuple per thread. Splits can be uneven (0-15, 15-39, 39-46). No automatic split.
- **Join**: same contract, takes the array of thread results and returns the farm result.
- Without a Join the return type is `arr<threadreturntype>`. Farm is void if the thread function returns nothing (e.g. Mandelbrot writing its screen band in place).
- Farm is thread-level parallelism. SIMD is separate.

```
fun sum(arr<i32> data) {
  i32 total = 0
  for var item in data {
    total += item
  }
  return total
}

arr<i32> buff = ...
var res = farm(4, sum, buff)
```

Block form:

```
res = farm(4, thrfn, params) {
  Split: fun paramstuple(params) { code for the split }
  Join:  fun farmresult(arr<thrresult> results) { ... }
}
```

## 20.6 Pipe (stage-parallel construct)

- Each stage is a plain function that defines its input and output. Input and output types can be completely different.
- The pipe partitions the data, feeds the stages and collects the results. It is pull-based: the split runs each time the first stage needs more data.
- The pipe is the main task, its stages run in threads.
- Join is incremental (init, one call per result, end).
- Stateful stages (e.g. a P-frame needs the previous frame) must see data in order.

First skeleton:

```
fun <outStream1> PipableStage1(<inputParams>)
fun <outStream2> PipableStage2(<outStream1>)
fun <outStream3> PipableStage3(<outStream2>)
fun <Result>     PipableStage4(<outStream3>)
Result res = pipe(PipableStage1, PipableStage2, PipableStage3, PipableStage4, inputParams)
```

Example 1: 1 GB buffer, 64 KB chunks, 3 stages:

```
const i32 chunkSize = 64 * 1024

fun arr<u8> DecodePipeStage(arr<u8> block) {
  arr<u8> result = arr<u8>[block.len]
  for var index in 0..block.len {
    result[index] = block[index] ^ 0x5A
  }
  return result
}

fun arr<u8> FilterPipeStage(arr<u8> block) {
  arr<u8> result = arr<u8>[block.len]
  for var index in 0..block.len {
    result[index] = block[index] > 200 ? 200 : block[index]
  }
  return result
}

fun arr<u8> EncodePipeStage(arr<u8> block) {
  arr<u8> result = arr<u8>[block.len]
  for var index in 0..block.len {
    result[index] = ~block[index]
  }
  return result
}

fun main() {
  arr<u8> buff = loadfile("input.bin")   // 1 GB
  arr<u8> res = pipe(DecodePipeStage, FilterPipeStage, EncodePipeStage, buff, chunkSize) {
    u64 start = 0
    split: fun arr<u8>(arr<u8> buff) {
      while start < buff.len {
        feedpipe buff.view(start, chunkSize)
        start += chunkSize
      }
    }
  }
  savefile("output.bin", res)
}
```

Example 2: raw video compression (all types different, the join accumulates):

```
fun RawFrame      LoadFrame(PngImage png)       { ... }
fun FilteredFrame Denoise(RawFrame frame)       { ... }
fun EncodedFrame  Encode(FilteredFrame frame)   { ... }   // I, P or B frame

VideoFile video = pipe(LoadFrame, Denoise, Encode, framesFolder) {
  split: ...    // yields one PngImage per call
  joininit: fun VideoWriter() { return VideoWriter("out.mp4") }
  join:     fun (VideoWriter writer, EncodedFrame frame) { writer.write(frame) }
  joinend:  fun VideoFile(VideoWriter writer) { return writer.close() }
}
```

## 20.7 Target architectures and libraries

- Some parts of the language may be missing depending on the target (e.g. a C64 cannot have multitasking).
- The compiler handles it: no `if target.has(...)` construct in the source. An architecture has to define what it can provide, and the compiler checks each use against it.
- Granularity is probably finer than all-or-nothing, to be defined. It also covers type implementations (e.g. a C64 may provide only short strings, without the rope model).
- **Libraries are architecture-bound.** A library declares which architecture capabilities it requires. If a library uses threads, it requires threads — it does not compile for targets that lack threading. No conditional fallbacks, no silent degradation. If it compiles for your target, it works fully. The ecosystem naturally stratifies: some libraries are universal, some require specific capabilities.

## 20.8 Checkpoints and timers

- Checkpoints are every point where the running code can stop or hand over:
  - a call to the `wait` primitive, in any of its forms: a wait on a target (`wait x timeout N`), a timed wait, a bare `wait`, `Root.Time.wait`;
  - an `enforce`;
  - a `return` of any kind (`return`, `return!`, `return?`).
- The checkpoints are the only places where the calls through a task handle (section 20.1) run. Between two checkpoints the running code is never interrupted.
- `Root.Time.wait` is the same call as a timed `wait`.
- A bare `wait` and `wait 0` do not stop: they only act as a checkpoint.
- While a loop with no checkpoint inside runs, no call through the handle is served. This is why an infinite loop without a single checkpoint gets a level 1 compiler warning.

```
wait lapse(10)
wait 250                       // int, milliseconds
Root.Time.wait(250)            // the same call
```

## 20.9 Runnable (trait applied to Process, Task and Thread)

- Independent kinds, no containment; the program main is a Runnable too, the root of the tree.
- name: process = full path of the executable; task = class name; thread = function name (a lambda: its signature).
- No `Hung` status: it is a detection problem (a method later, maybe a ping with a timeout; it only answers at a checkpoint, so a long busy loop would look hung). A send method on Runnable: not sure.
- Status `Killed`: in all cases of kill, also when the kill signal was sent and the task ended by itself.
- children: how it is implemented is left to the compiler, probably a `vec<%Runnable>`.
- Return signature: `Runnable` keeps the return signature of what it runs as a type, `ReturnType`. For several results it is the tuple: `fun i32, string taskRun()` gives `(i32, string)`.
  - The compiler fills it at creation: `Task(MyTask, ...)` takes the result of `MyTask.taskRun()`, `Thread(runThis, ...)` the result of `runThis`, `Process(...)` is `RunResult`.
  - With the creation on the same line nothing is written: `Task task = Task(MyTask, 123)` and `var task = Task(MyTask, 123)` both know it, and `var n = wait task timeout 500` has the right type.
  - A top-level `Task` or `Thread` variable is known by name also in the functions that use it (14.1): a plain one knows its task when its declaration and every assignment of the program (at top level and in functions) give a task of the same class with the same results; with two different ones it knows nothing, as a local given different tasks. A top-level `Task<...>` says it, and every assignment to it, in functions too, is checked.
- Class of the task: the handle also keeps the class of its task, filled at creation like `ReturnType` and kept at run time. The compiler uses it for the calls through the handle. With the creation on the same line nothing is written, and the task's own methods are reachable through the handle.
- Where there is no creation to read them from (a parameter, a field), the handle is written with its class first, then its result types:

| Form | Class | Result |
|---|---|---|
| `Task t` | any task | not known: `var x = wait t timeout 500` is a compile error |
| `Task<MyTask> t` | `MyTask` or a subclass | the result of `MyTask.taskRun()` |
| `Task<MyTask, i32, string> t` | `MyTask` or a subclass | `(i32, string)`, checked against `MyTask.taskRun()` |
| `Task<*, i32, string> t` | any task | `(i32, string)`; the task's own methods are not reachable |

  - The first parameter is always the class: `Task<Dog>` is a task of class `Dog`, never a task that gives a `Dog` (that one is `Task<*, Dog>`).
  - `*` alone, followed by a comma or `>`, stands for any class. It is not a pointer: a pointer is `*T`, with its type after the star.
  - Result types that do not match the `taskRun()` of the class are a compile error.
  - A plain `Task t` can be started, killed, asked for its status and waited for without taking a value.
  - `if t is Task<MyTask> mt { }` is always possible on a `Task t`: `mt` is the same handle seen with its class. The type switch works too: `t is ? { Task<MyTask> a: ..., Task<Logger> b: ..., default: ... }`. It is chosen at run time, and `default` is required: a `Task` can be of any class.
- `Thread<T>` keeps only the result type: a thread is a function, there is no class to name.

```
enum RunKind { Process, Task, Thread }
enum RunStatus { Ready, Running, Completed, Failed, Killed }

trait Runnable<ReturnType> {
  RunKind kind
  RunStatus status
  string name
  date startTime
  Runnable parent                 // objects are nullable by default
  vec<%Runnable> children         // probably
  fun Runnable<ReturnType> start()
  fun ReturnType wait()
  fun signal(Signal s)              // sends s to this runnable (20.3.1)
  fun bool kill(lapse timeout)
  fun bool kill(uns milliseconds)
  fun hardKill()
}

class Task<TaskClass, ReturnType> : Runnable<ReturnType> { }   // written as in the table above
class Thread<ReturnType> : Runnable<ReturnType> { }
```

## 20.10 Kill and cancellation

Two kinds of kill: the soft kill (`kill`), cooperative, and the hard kill (`hardKill()`), explicit only.

- A runnable can kill only its descendants: its children and their children, at any depth. Never its parent or anything above it.

### Soft kill: `kill(timeout)`

- `kill` sends the cancel signal to the runnable with `signal(Signal(KnownSignals.Cancel))` (20.3.1) and waits. The cancel signal is ExclusiveSafe: it is never lost, and at its next checkpoint the runnable starts ending: its `atEnd` block runs and the `enforce` scopes unwind normally.
- The timeout of `kill` is mandatory, as for `wait`: `task.kill(500)`.
- Result: `true` if the runnable (and its descendants) ended within the timeout, `false` otherwise. A soft kill never escalates by itself: what has not ended keeps running.
- It works on processes, tasks and threads.
- The cancel signal goes down the children in cascade, level by level. The runtime takes the max length of the chain below the runnable (N levels) and starts from the deepest level: all the runnables of one level get the cancel signal together and share one window of `T / N`, then the level above starts. The call returns within `T`.

### Hard kill: `hardKill()`

- Only by an explicit call. No signal, no `atEnd`, no cleanup code: the stack is unreliable and memory may already be released.
- The heap of a task is freed in one piece (section 20.12).
- It takes the whole subtree: all the descendants are hard-killed with it, with no soft round first. The order does not matter, nothing runs.
- No guarantees: nothing is promised about what was lent read-write to the killed runnable.
- The locks held by the killed runnables (mutexes, global locks, refcount locks, semaphore permits) are released: all the ones the runtime can find. The data they protect may be half-written.
- Thread: depends on the OS (open point).

### End of the main program

1. Every runnable that has not ended gets the soft kill, all at once, in one window: 50 ms per level of the tree (`N × 50` ms).
2. The runnables that end are cleaned up as they end.
3. When the window closes, whatever has not ended gets `hardKill()`.
4. The process exits.

Until `hardKill()` exists: after the window, what has not ended stops with the process, without `atEnd`.

```
Signal  →  kill(T)  →  "please stop"  →  cooperates  →  clean exit + atEnd   (true)
                                      →  no answer   →  keeps running        (false)
hardKill()  →  the whole subtree ends at once  →  no atEnd, no cleanup
```

## 20.11 Parent, children, asparent

- Same mechanism as "as parent" in the spec: a parent destroys its children when it ends.
- `asparent` is a visibility keyword (with internal, public, unrestricted): the method is callable only by the children. A thread can call its task's asparent methods.
- An `asparent` method of a task can be used by its sub tasks and by their threads (a thread has access to whatever its parent gives). It goes one level of tasks only: a task created by the sub task cannot use it.

```
process (main task) -> sub task -> thread          YES
process (main task) -> sub task -> sub sub task    NO
```

- An `asparent` call runs at once in the sub task (or in its thread), on the memory of the parent: it is not queued to a checkpoint. If there are writes, they need to be protected by the developer (`mutex` and `enforce`).
- `asparent` is for methods only. Data is shared by lending it (section 20.12).

```
class MyTaskClass {
  asparent fun log(string text) { ... }
  fun internalWork() { ... }
}
```

## 20.12 Memory

- Each task has its own heap. Everything the task allocates comes from it: its object, its strings and collections, the partitions of its threads. The main program is a task like the others, with its own heap.
- First implementation: one shared, thread-safe heap for all the tasks. The per-task heaps, and freeing them in one piece, come later.
- The heap of a task is freed in one piece when the task ends or is hard-killed. This is what makes the forced kill safe: no walk through the objects, no `atEnd`, the whole heap is released.
- Globals and mutex-marked refcounts live outside the heap of any task.
- Each thread allocates from its own partition: no shared allocator, no lock. Results cross to the task with the normal passing modes. The partition is freed when the thread ends.
- Passing to a task (constructor parameters, arguments of a call through the handle, results): the normal passing modes apply, for every type.
  - Plain: borrowed read-only. `&`: borrowed read-write. No copy: the task works on the data where it is.
  - `->` gives, `!` sends a clone.
  - With a read-write lend, the lender makes no assumptions on the content until the task terminates.
  - With a read-only lend the lender can still write: the task reads with no assumptions on the content.

```
arr<u8> buff[4096]
Task t = Task(Filler, &buff).start()    // lent read-write, no copy
```

- A borrow does not change the ownership: when the task makes a borrowed object grow, it grows on the heap of its actual owner.
- Latent ownership transfer (inheritance): when the lender ends before the task, the ownership of what was lent passes to the task, and all continues. Otherwise the task would access freed memory.
  - The memory does not move: only the owner changes, and it is freed with the task.
  - What is lent to a task is never placed on the stack.
  - Level 3 warning where the compiler can see it.
  - When several tasks hold the same lend (never of a `Task`, 20.2.6), the last one still running inherits it.
- No thread-local or task-local storage added for now: the task class fields are task-local, the thread function locals are thread-local.
- Refcounts: a mutex-marked `@` refcount is protected and safe to share between tasks. Open: atomic cost of the count, cycles, a shared mutable object still needs a lock, a handle passed to a task is shared memory.
- Threads share memory and variables. The threads of a task work on different partitions of the memory owned by the task; the language can be extended where this needs it.
- Each task has its own memory. What crosses a boundary uses the normal passing modes: lent read-only (plain), lent read-write (`&`), given (`->`) or cloned (`!`). The rules are in section 20.12.
- Without a lend, tasks share memory only through mutex-protected constructs: globals and refcounts are considered safe. Refcount handles can be passed.
- Of the top-level variables of the program and the static fields of the classes, a task sees only: constants, refcounted objects, weak references, `mutex` variables (20.13) and globals (18). All of them are safe to share: they cannot change, or they have a lock. The other top-level variables and static fields are not reachable from a task: a compile error.
  - The code of a task is the methods of the class given to `Task(...)` and of its parents (not its constructor, which runs on the creator's side), the functions they call at any depth, and the functions they start as threads. Also part of it: the lambdas they write; through a function value, any lambda of the program with that function type (which one runs is known only when the program runs); the methods that replace the ones they call, in the subclasses and in the classes of a trait; the accessors of the properties they use; the functions of compiled libraries, whose interface marks the ones that use top-level variables or static fields of the library (15.8).
  - The main program and its threads see all of them: they are its own.

## 20.13 Mutex

- A mutex is native: `mutex <type> <name> = <value> timeout <milliseconds>`. The value can be a constructor: `mutex Inventory stock = Inventory() timeout 500`. The timeout is required and greater than 0.
- Scoped use only, with `enforce` (`lock` is the same). There is no manual acquire or release, and no atomics: the mutex is enough. It can be a global.
- Among threads and tasks of one process, never between processes.
- A full lock, reads included, unlike `&@T` (12.7), where reads stay free and only writes need the lock.
- A busy mutex follows the `enforce` rules (7.2.2): the wait is the `timeout` of the `enforce`, else the timeout of the mutex. `enforce m timeout 0 { }` tries once. A failure goes to `lockfail` or `default`; with neither, the block is skipped and the code goes on.
- The mutex is recursive: a function called inside `enforce m` that takes `m` again, on the same thread, goes on at once. An `enforce m` written inside `enforce m` is a compile error.
- Rules: a reference to mutex data that escapes the `enforce` block is a compile error; a blocking call inside `enforce` is a level 1 warning; locks are always taken in the same order (`enforce a, b, c` and `enforce b, a, c` is a compile error).

```
mutex i32 counter = 0 timeout 1000
enforce counter {
  counter++
}

mutex Inventory stock = Inventory() timeout 500
enforce stock timeout 0 {
  stock.add("apple")
} lockfail {
  Console.log("busy, try later")
}
```
## 20.14 Semaphore

- Declaration: `semaphore name [= init] [timeout lapse]`. Type `uns`. Default init 1. Init 0 is a compiler error (deadlock).
  - `init` is a whole number written in the declaration.
  - The timeout of a top-level semaphore is a number of milliseconds; a local one can be computed.
  - A local semaphore has one counter for every call of its function, as a local mutex.
- Read by its name, a semaphore is the number of permits free now (`uns`). It is never assigned: `pool = 5` is a compile error.
- Scoped use only with enforce: the permit is taken at the start of the block and returned at its end. Busy: the regular enforce timeout rules.
- `enforce name.take(count) { }` takes (or waits for) several units. Inside an `enforce` of the same semaphore it is allowed: it may wait for itself until its timeout.
- Not linked to signals. The permits held by a hard-killed task are released (20.10).
- Read/write lock: only if needed, defined as `r only` or `rw`.

```
semaphore pool = 12 timeout 1500
semaphore gate                  // 1 permit
semaphore broken = 0            // compiler error
enforce pool { ... }
enforce pool.take(10) { ... }
```

# 21 Multi-Process messaging (Root.Messaging)

Everything here is preliminary, syntax included.

## 21.0 Usage

Messaging is not included by default in DFlat programs. An `import Root.Messaging` is required: the full namespace path, as every import (16). Namespaces are case-insensitive, so `import root.messaging` is the same.

Importing `Root.Messaging` also imports `Root.Tasks` (chapter 20): Process, PostOffice and MailBox use the Runnable trait, `wait` and kill from there.

## 21.1 Process

- A process is one stdlib class, `Root.Messaging.Process`, a Runnable like Task and Thread. It behaves like a task but runs from an executable file.
- It is available just by importing `Root.Messaging` (21.0).
- **Process**: started through stdlib functions only (no fork). Processes talk to each other through mailboxes (chapter 21), never through shared memory.
- No processId in the trait (only in Process). Tasks and threads have none.
- `RunResult` has read-only fields: `exitCode`, `output`, `errors`, `timedOut`, `error`.
- `Root.Process.run(...)` is a different thing, part of the stdlib (stdlib spec): it launches an executable, waits for its end and gives a `RunResult`. It produces no `Process` object.
- A process is created like a thread, then started and waited for. `wait` gives the `RunResult`; the timeout is the one of the `wait`.

```
fun Process(string fullPath, arr<string> args, workDir = ".", input = null)
```

- `input` is the text sent to the standard input of the program; `null`: none.

```
Process p = Process("C:/tools/git.exe", ["status"])      // Ready
p.start()                                                // Running
RunResult res = wait p timeout 5000
```

- Same `start()` and `wait()` pattern as Task and Thread.
- result inside the Process: no big pro or con, undecided.

```
class Process : Runnable {
  uns processID
  arr<string> args
  RunResult? result      // null until it finishes
}
```

Kill (the general rules are in 20.10):

- A process run through the OS cannot get signals or direct control. The soft kill is a "please go away" message, only if it runs the `postOffice` global; otherwise `kill` cannot reach it and returns `false`.
- `hardKill()` is the OS kill, through its pid.

## 21.2 PostOffice

Messages go between tasks, between processes, and between machines on the same LAN. A message goes to a **mailbox**: a specific address for a specific receiver. A mailbox has one receiver and any number of senders. A mailbox is one direction only: the data goes from the senders that `find()` it to the receiver that `register()`ed it. For data going back, another mailbox has to be created, registered on the other side (example in 21.3).

### The registry

`PostOffice` is a class of the runtime. The program declares its global in the root file, as every global (Specs/18):

```
global PostOffice postOffice = PostOffice()
```

- A library that uses mailboxes declares its own `postOffice` global in its `lib.df`.
- All the `PostOffice` objects of a process share one registry inside the runtime: each global has its own lock, the registry under them is the same. A name registered through one is found through all the others.

Three operations:

- **`register(name, mode)`**: creates a mailbox. Exception (or panic) if the name is already registered, at any level: a mailbox name is unique across the three scopes, the same name cannot exist on different levels.
- **`find(name, mode?)`**: looks up an existing mailbox. Returns `null` if not found. The scope is optional; without it the search goes Process → Machine → LAN. With a scope, the mailbox is returned only if it is registered at that level, else `null`.
- **`remove(mailBox)`**: removes a mailbox. It takes a `MailBox`, not a name: only what is held can be removed. Returns `bool` (false if not registered or already removed).

```
// Receiver side: register
MailBox myBox = postOffice.register("cakes", MailBoxMode.Process)

// Sender side: find
MailBox dstBox = postOffice.find("cakes")
MailBox dstBox = postOffice.find("cakes", MailBoxMode.Process)   // explicit scope
```

MailBoxes are waitables (20.2): they have no timeout of their own, the timeout is the one of the `wait`. `MailBox myBox = postOffice.register("cakes", MailBoxMode.Process)`


Internal design:

```
class PostOffice {
  struct PortId {
    string name
    MailBoxMode mode
    endpoint, pipe, etc
  }
  map<PortId, something> mailBoxes
  collection<endpoint> knownPartners

  public fun register(string name, MailBoxMode mode) { ... }
  public fun MailBox find(string name, MailBoxMode mode) { ... }
  public fun bool remove(MailBox mailBox) { ... }
}
```

- The owner of a mailbox is its receiver, the runnable that calls `register`. When it ends, the mailbox is removed, its unread messages disappear and the senders get their exception (21.3.6). When a sender ends, the messages it sent stay until they are read.

- **`PortId`**: the registry key. It bundles the name, the mode and the connection details (endpoint, pipe, socket, etc.).
- **`mailBoxes`**: the central map of all known mailboxes, whatever their scope.
- **`knownPartners`**: the known LAN process endpoints (WebSocket connections). Used for targeted removal notifications.

### Scopes

Three scopes, explicit at registration:

- **`MailBoxMode.Process`**: in memory, private to the process.
- **`MailBoxMode.Machine`**: visible across the processes of the same machine.
- **`MailBoxMode.LAN`**: visible across the machines of the local network.

The scopes are nested layers. Registration goes down through them:

- `register(x, MailBoxMode.LAN)`: Process registry + Machine registry + LAN broadcast.
- `register(x, MailBoxMode.Machine)`: Process registry + Machine registry.
- `register(x, MailBoxMode.Process)`: Process registry only.

`find` without a scope searches upward: Process → Machine → LAN. The name is unique, so the order only says where the lookup looks first.

| Register mode | Process knows | Machine knows | LAN knows |
|---|---|---|---|
| `Process` | ✓ | — | — |
| `Machine` | ✓ | ✓ | — |
| `LAN` | ✓ | ✓ | ✓ |

A task can talk to a mailbox in the same process and to another in a different process or machine, all through the same `find`.

### Registry by scope

**Process: an internal shared object.** Part of the runtime: a thread-safe in-memory hashmap. `register` inserts, `find` looks up. No IPC, no files, no sockets.

**Machine: the OS is the registry.** `register` creates an OS-named resource at a well-known path, `find` checks if it exists.

- Linux: Unix domain socket (e.g. `/tmp/dflat/mailboxes/cakes`).
- Windows: named pipe (e.g. `\\.\pipe\dflat.cakes`).

The OS handles most of the cleanup when a process dies. A stale check may be needed (try to connect; if refused, it is dead, clean it up).

**LAN: UDP broadcast, event-driven.** No servers. The registration itself triggers the broadcast. The protocol converges by gossip.

A UDP broadcast happens only when a mailbox is registered, and as a reply to a broadcast that taught something new. There are no periodic broadcasts, no heartbeats and no polling: a machine that has nothing new to say stays silent.

The rule: when you register, tell everyone what you know. When you learn something new, tell everyone what you know. When you know everything, stay silent.

1. Machine A registers "cakes" → broadcasts `I_KNOW ["cakes@A:9100"]`.
2. Machine B (has "orders") receives → adds "cakes", replies `I_KNOW ["cakes@A:9100", "orders@B:9200"]`.
3. Machine A receives → adds "orders". It already knows everything B sent → silent.
4. Convergence reached.

A new machine joining:

1. Machine C registers "reports" → broadcasts `I_KNOW ["reports@C:9300"]`.
2. A and B receive → add "reports", reply with their full lists.
3. C learns everything in two rounds.

### LAN removal and death detection

No heartbeats. A mailbox is dead only when a connection to it fails. A removal is not broadcast: "mailbox gone" goes only to the `knownPartners`, through the existing WebSocket connections.

| Event | Action |
|---|---|
| `register` | UDP broadcast to everyone (discovery) |
| A broadcast is received | Add to `mailBoxes`, add the sender to `knownPartners` |
| WebSocket established | Add to `knownPartners` if not already there |
| `remove` | Send "mailbox gone" only to `knownPartners`, through the existing connections |
| A connection fails | Remove the dead mailboxes, remove from `knownPartners` |

## 21.3 MailBox

### 21.3.1 Sending

A message is created on its own and sent to a destination mailbox. The message knows where it is going. The send is waited for.

```
Message post = Message("Some content")
wait post.sendTo(dstBox)
```

- The payload can only be native or streamable objects. Streamable: an object that can be turned into a sequence of bytes and converted back. A `struct { i32, string, (uns, char) }` is streamable, an `@` refcount is not.
- Wire format: `sendTo` takes the payload, computes its `sizeof`, sends the size header, then the payload bytes. A message is a block; on the wire everything is bytes.

```
[sizeof payload][payload bytes]
```

### 21.3.2 Going back and forth

Each mailbox carries data one way, from whoever `find()`s it to whoever `register()`ed it. A back-and-forth needs two mailboxes, one registered on each side:

```
// Process A: client
MailBox replies  = postOffice.register("orders.replies", MailBoxMode.LAN)   // A receives here
MailBox toServer = postOffice.find("orders")                                // A sends here

wait Message(OrderRequest(42, "cake")).sendTo(toServer)
Message answer = wait replies.receive()

// Process B: server
MailBox requests = postOffice.register("orders", MailBoxMode.LAN)           // B receives here
MailBox toClient = postOffice.find("orders.replies")                        // B sends here

Message req = wait requests.receive()
wait Message(OrderAnswer(42, true)).sendTo(toClient)
```

When A and B are on different machines, both mailboxes travel on the one WebSocket between process A and process B (Transport by scope, below).

### 21.3.3 Receiving

Two ways of receiving from the same mailbox. They can be mixed.

**Block reading, `receive()`**: reads one complete message as a single unit. It casts from bytes to the expected type; exception on a type mismatch. On timeout it gives `null` with a silent exception.

```
Message msg = wait myBox.receive() timeout 2500
```

**Stream reading, `read()`**: reads the current message in chunks with the standard stream interface. EOF marks the end of the current message; the next read starts the next message. On timeout `amountRead` is `null`, with a silent exception.

```
MessageStream stream = myBox.getStream()
i32? amountRead, bool eof = wait stream.read(&buff, 4096) timeout 1500
```

| `amountRead` | `eof`   | Meaning                    |
|--------------|---------|----------------------------|
| `null`       | —       | Timeout                    |
| `> 0`        | `false` | Got data, more coming      |
| `> 0`        | `true`  | Got data, message complete |
| `0`          | `true`  | Empty message (edge case)  |

Mixing: switching from stream to block reading in the middle of a message loses the unread part of that message. `receive()` picks up at the next complete message.

### 21.3.4 MessageStream

a stream class for MailBox.

- `uns read(&buff, max)` engages as soon as anything is there: at least one byte, at most n. as count says how many. This is how sockets and pipes normally behave (POSIX read), and it's the right default for interactive data, where you want to react to whatever came in.
- `uns readExactly(&buff, max)` engages only when the buffer is full: exactly n bytes, or the stream ended. Use it for fixed-size records and headers.
- `uns readUntil(&buff, max, delimiter)` / readLine() engages when a delimiter arrives: for text and line protocols.


### 21.3.5 Timeouts

- A mailbox has no timeout of its own: every `wait` on it writes its timeout (20.2.8).
- `receive()` timeout: silent exception (returns null). A receive timeout is normal: nothing arrived yet.
- `sendTo` timeout: regular exception. A send timeout means the other side cannot keep up or is gone.

### 21.3.6 Reliability and backpressure

- Guaranteed delivery while both ends exist. If the other side is gone, the sender gets an exception. No "maybe delivered".
- A full buffer stops the sender until there is space or the timeout expires. No dropped messages.

### 21.3.7 Transport by scope

The same API works in all three scopes. The runtime selects the transport:

- **Process**: in-memory queue. Values are moved or copied by the normal DFlat rules. No serialization.
- **Machine**: OS primitives, named pipe on Windows, Unix domain socket on Linux, wrapped behind one abstraction.
- **LAN**: WebSockets. One connection per pair of communicating processes (a process cannot share a WebSocket with another process, on any OS), multiplexed: all the mailboxes between two processes share a single WebSocket connection in both directions. Each message on the wire carries a mailbox identifier for routing. Trust is delegated to WebSockets (WSS for encryption and authentication).
