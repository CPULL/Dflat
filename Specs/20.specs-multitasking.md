## 1. Execution units

- Three kinds: **Process**, **Task**, **Thread**. Weight: process > task > thread. They are independent kinds (">" means heavier, no containment).
- **Process**: started through stdlib functions only (no fork). How processes talk to each other is not specified yet, but never through shared memory.
- **Task**: a class that runs on its own. Any class can become a task by implementing `taskRun()`.
- **Thread**: a function (lambdas too) that runs on its own.
- Functions can be defined anywhere, not only in classes (implicit main object).
- Process, Task and Thread share a trait/superclass (**Runnable**) with common properties and methods, including:

```
fun <ReturnType> wait()
```

- A thread started directly belongs to the task that starts it (or the implicit main task).
- **All Runnables use deferred start**: creation puts the runnable in `Ready` status, then `.start()` begins execution.
- `wait` collects the next value the runnable hands out with one of the `return` forms (below, and section 3).

### Process (stdlib)

- A process is one stdlib class, `Root.Multitasking.Process`.
- It is available just by importing multitasking (section 0).
- `RunResult` has read-only fields: `exitCode`, `output`, `errors`, `timedOut`, `error`.
- The `Root.ExecProcess` part of the stdlib can stay for now, but it does not produce a `Process` object. It is not sure it is still needed.
- A process is created like a thread, then started and waited for. `wait` gives the `RunResult`; the timeout is the one of the `wait`.

```
fun Process(string fullPath, arr<string> args, workDir = ".", input = null)
```

- `input` is the text sent to the standard input of the program; `null`: none.

```
Process p = Process("C:/tools/git.exe", ["status"])      // Ready
p.start()                                                // Running
RunResult res = wait p timeout 5000
```

### Task

The `Task()` constructor takes the class itself followed by its constructor parameters. The object is built inside the task's memory space; the parameters cross the boundary with the normal passing modes (section 16). Then `taskRun()` starts after `.start()` is called.

```
class MyTask {
  public i32 val
  internal string txt
  arr<u64> data[256]

  fun taskRun() {
    data.fill(val)
    ...
  }
  fun method1() { ... }
  fun method2() { ... }
}

Task task = Task(MyTask, 123, "blah")   // Ready: object built inside the task
task.start()                            // Running: taskRun() begins
wait task timeout 5000                  // waits up to 5000 ms
```

- After `Task(MyTask, ...)` the creator holds only the handle. The object belongs to the task: `method1()` and `method2()` are the task's own code.
- A task cannot be started more than once from the same handle: a second `start()` raises a real exception, not a silent one.
- `taskRun()` can also be called directly, as a normal method of a normal object, without `start()`. Then every execution of `return!` or `return?` raises an exception.
- The methods of the task can be called through the handle (`ticker.stop()` in the sketch below): the public ones and the `unrestricted` ones, and also the internal ones from the same namespace.
- A call through the handle runs inside the task, at its next checkpoint (a `wait`, an `enforce`, a `return` of any kind: section 11), never on the caller's side. The calls share the queue of the event callbacks (section 5): one at a time, in arrival order.
  - The arguments and the result cross with the normal passing modes (section 16), as the constructor parameters do.
  - A method that returns nothing is posted and the caller goes on: `ticker.stop()`.
  - A method that returns a value is waited for: `var n = wait ticker.getCount() timeout 500`.
  - A task in a loop with no checkpoint never serves its calls (the warning of section 11).
- `wait task` collect the next produced item from the task, returned by `return` (task waits for the waiter to collect, then ends), `return!` (task waits for the waiter to collect), or `return?` (task does not wait and continue also if nobody is waiting right now.)
- `wait` on a task that is no more running returns a zero or null value (also composite) and produces a silent `TaskAlreadyTerminatedException`.
- `wait` on a task that was not started: the normal timeout, then a zero or null result and a silent `TaskWasNotStartedException`.
- A task is still an object: when it goes out of scope and is no more running, it is removed like any other object. It does not matter if the result was collected or not.
- No leaks: when the task has ended, nobody is waiting and nobody references its handle anymore, it terminates and all its memory is released.
- A task that is running remains alive, also when its handle goes out of scope. It is killed when the main process exits, with the chain cancellation of section 14.


Sketch of a task that returns many times: `return` sits inside the loop of `taskRun()`, and a public method is there to stop it.

```
class MyTask(i32 delay) {
  bool alive = true
  u64 count = 0
  fun u64 taskRun() {
    while alive {
      Root.Time.wait(delay)
      count++
      return? count
    }
  }
  public fun stop() {
    alive = false
  }
}

Task ticker = Task(MyTask, 100).start()
var n = wait ticker timeout 5000   // the next count
ticker.stop()
```

- `return` in `taskRun()` ends the task.
- When `taskRun()` ends without a `return` and it is not void, it returns the usual 0 or null. An exception comes only when the task is waited again after it has terminated.
- Three forms of `return`:
  - `return val`: wait until somebody collects the value, then exit the task/thread.
  - `return! val`: block and wait until somebody reads the value, then continues.
  - `return? val`: post the value to whoever is reading (if anybody is) and continue without waiting (it is an `async return`).

### Thread

The function comes first, its arguments follow. They are taken when the thread is created.

```
fun lapse runThis(u32 time = 1234) { ... }

Thread tr1 = Thread(runThis)          // Ready, default arguments
Thread tr2 = Thread(runThis, 567)     // Ready
tr1.start()                           // Running
tr2.start()                           // Running

var res1 = wait tr1 timeout 5000     // what runThis returned
var res2 = wait tr2 timeout 5000
```

- A thread is a simple function that is run in parallel. Threads do not have a `taskRun()` method.
- A thread is a function of its parent runnable, run in parallel: it has access to whatever the parent gives.
- A thread cannot live without a task: it needs the parent context to use data.
- The three forms of `return` work in a thread function as in `taskRun()`: a thread can hand out many values.

```
fun u64 aThread(u32 d) {
  while d > 0 {
     wait 1000 // 1 sec
     return d?
  }
}

Thread t = Thread(aThread, 10).start()
```

The handle can be written with its result type: `Thread<lapse>` for `runThis`, `Thread<u64>` for `aThread` (sections 12 and 19).

## 2. Memory and mutex

- Threads share memory and variables. The threads of a task work on different partitions of the memory owned by the task; the language can be extended where this needs it.
- Each task has its own memory. What crosses a boundary uses the normal passing modes: lent read-only (plain), lent read-write (`&`), given (`->`) or cloned (`!`). The rules are in section 16.
- Without a lend, tasks share memory only through mutex-protected constructs: globals and refcounts are considered safe. Refcount handles can be passed.
- Mutex: scoped use only (no manual acquire/release). Works among threads and tasks of one process, never between processes.
- A variable or object marked `mutex` can be locked, and used atomically, with the `enforce` construct. Atomics are not a separate thing: the mutex should be enough.
- `enforce guard { }` is the same as `lock guard { }`.
- A mutex can be declared as a global and used by threads.
- A mutex is a full lock: it blocks the whole object, reads included. It is not a `&@T` (12.7), where reads stay free and only writes need the lock.
- A busy mutex follows the `enforce` rules (7.2.2): the wait is the `timeout` of the `enforce`, else the default of the mutex, else 0 (one try); a failure goes to `lockfail` or `default`, and with neither the block is skipped and the code goes on.
- The default timeout is written at the definition of the mutex, as for `&@T` (form to be confirmed).

```
mutex i32 counter = 0 timeout 1000
enforce counter {
  counter++
}

mutex bool guard
enforce guard {
  ...
}
```

## 3. Wait

```
wait somesignal timeout 1000
wait task timeout 5000
wait function timeout 2000

var res = wait t timeout 500
```

There is one keyword, `wait`, for everything that is waited for: a thread, a task, a signal, a post box. A second keyword is not needed.

**Timeout is always required.** Omitting the timeout is a compiler error. This forces the programmer to always be intentional about how long to wait. `enforce` can set a scoped default.

On timeout, the behavior is **uniform for all wait targets**:
- Returns **zero or null**.
- Throws a silent `WaitTimeoutException` (silent as in 15.4): it is seen only by the code that catches it.

`enforce` in its expression form (7.2.6) gives the value for a timeout:

```
var res = enforce wait tr1 timeout 1000 default { 123 }   // 123 when it runs out
```

```
var a = enforce wait tr1 timeout 1000 default { 123 }               // waits up to 1000 ms
var b = enforce wait tr1 timeout 500 default { 123 }                 // this wait: 500 ms
```

Several waiters on the same runnable are served FIFO: only one at a time can get the result. Same for all Runnables.

Exceptions propagate when they are not caught: one that leaves the function or `taskRun()` reaches the waiter. As all exceptions, it follows the Rust `Result` model: `wait` gives the actual return values plus an extra error value with the exception, if any.

Waiting a fixed time: the OS has it (`Sleep`, `nanosleep`). A timeout on a signal wait can be a timed OS wait or a runtime timer; undecided. Open: waiting on several targets.

## 4. Signals

Communication has three levels, all important: **signals** (a bare go, section 4), **events** (a well defined payload, inside one process, section 5) and **messages** (variable data, also between processes, section 6).

- What a signal is for: "I need to wait for a go, I do not care about anything else".
- A signal is only an alert. It can be shared by many waiters or belong to one. It is sent, consumed and then gone. Underneath it is little more than a counter.
- Generic system with one uniform interface in the language. Each source (OS, window, runnable, user code) defines its own signals and decides how they are intercepted per OS.
- A signal has no payload and may have no sender. It is a bare notification. Messages are a separate thing and carry content.
- A signal is identified by an unsigned number or by a string. The two are separate namespaces: `Signal(20000)` and `Signal("myapp.go")` never meet.
- Numbers below 16384 are reserved. `KnownSignals` gives names to them.
- Number 666 is reserved as the cancellation signal (no OS uses it).
- Mode is set at creation, never at send, because waiters with different modes cannot live together. The mode is optional. Default is **Single**.
- Polymorphic constructors: an enum `KnownSignals` for the classic ones, strings for custom ones.
- Also used as cancellation signals.
- Signal modes:
  - **Broadcast**: any number of subscribers, all notified. Lost if nobody is waiting.
  - **Exclusive**: only one subscriber allowed (a second subscribe is an error). Lost if nobody is waiting.
  - **Single**: any number of subscribers, one woken per fire (FIFO). Lost if nobody is waiting.
  - **Stable**: any number of subscribers, one woken per fire (FIFO). If nobody is waiting, the send count is stored as a counter and each `wait` consumes one. (Single + persistence.)
- Combined wait: first signal to fire wins, only for wait. The result is a `SignalType`.
- Registry (starting point, not final): the entry is created on first use by whichever side comes first; Stable needs the creator to create it (it keeps the counter); same name with a different mode is an error. Open: creator side or receiver side.
- Signals use the same counting logic as a semaphore but need no enforce.

Life of a signal: created, waited for (the subscription), sent.

```
Signal wakeMeUp = Signal("wakemeup")
...
wait wakeMeUp timeout 5000     // the subscription
...
wakeMeUp.send                  // the emit
```

```
Signal s = Signal("Window.resize")
Signal s = myTask.subscribe("Runnable.end").subscribe("Runnable.kill")
Signal s = Signal("Process.Kill")
Signal closure = subscribe(TASKKILL)
```

Constructor syntax: mode first (optional, defaults to Single), then name/number.

```
enum SignalMode { Broadcast, Exclusive, Single, Stable }

Signal go     = Signal("myapp.go")                              // default Single
Signal job    = Signal(SignalMode.Single, 20000)                 // explicit mode, number
Signal done   = Signal(SignalMode.Broadcast, "myapp.done")      // explicit mode, string
Signal kill   = Signal(KnownSignals.Kill)
Signal cancel = Signal(KnownSignals.Cancel)                     // 666

go.send
go.wait timeout 1000
Signal.send("myapp.go")                                        // static, no mode
Signal.send("blah")
Signal any = Signal(SignalMode.Single, 1, 356, "bump")
```

```
struct SignalType {
  uns? number
  string name        // empty when the signal was a number
}
SignalType res = wait Signal(1, 356, "bump", 77777, "foo") timeout 5000
```

## 5. Events

- A registry. Identified by a name only, never a number (the id is probably a hash of the name). The payload is a struct, defined by code or libraries.
- **No wait for events: callbacks only.** Events are not part of the `wait` keyword's scope.
- No automatic sender. If a handler needs provenance, the payload struct carries it explicitly.
- The payload is passed readonly.
- Callbacks of an event run in registration order, never two at once for the same event.
- A callback runs on the task where it was registered, JavaScript style: it never interrupts running code, it runs at checkpoints (section 11).
- **Bubbling**:
  - `setProcessed()` **marks** the event as processed but does **not** stop propagation — remaining callbacks still fire.
  - `stopPropagation()` is a separate, explicit call to **halt** the callback chain.
  - A callback can check the `processed` flag to decide whether to act, but it is not forced to skip.

```
Event.register("resize", Size)
Event.on("resize", mycall)
Event.send("resize", Size(800, 600))

fun mycall(Size newSize) {
  if newSize.processed { ... }
  newSize.setProcessed()
  // newSize.stopPropagation()    // would halt the chain
}
```

## 6. Messages

- Messages carry content (signals do not).
- They should respect a message-passing architecture: either the OS provides something (pipes, sockets) or an internal system allows them.
- Messages can go between processes.
- They need a way to find their target.
- Their data can have a variable size.
- Consider them as pipes or sockets.
- As in a message-passing architecture: always one to many, never bidirectional.

Sketch: the receiver opens a named `PostBox` and waits on it; the sender builds a `Message` and broadcasts it to that name.

```
PostBox cakes = PostBox("Send cakes here")
var cake = wait cakes timeout 5000       // probably a stream, not known yet

Message myCake = Message(CarrotCake, par1, par2, par3)
myCake.broadcast("Send cakes here")
```

For efficiency the target can be found once and used for all the sendings:

```
PostBox? dst = myMsg.findTarget("Send cakes here")
```

This is only a sketch, details come later. Consider it some sort of loose UDP connection.

Answers and confirmations do not come back on the same path: who needs them opens a callback post box (as a callback socket) and the other side sends to it. What `broadcast` returns is not decided.

Sketch ideas (not decided):

- A message arrives whole or not at all: one send is one `wait` on the other side, never half a message.
- The message packs its arguments in order; the receiver reads them back in the same order from the stream. Both sides agree on the order and the types.

```
var cake = wait cakes timeout 5000
var kind = cake.read<CakeKind>()
var p1   = cake.read<i32>()
```

- Only values travel (numbers, strings, structs, arrays of them), copied into the message. Objects with owners, counted objects and borrows cannot cross a process border.
- A target found with `findTarget` is a snapshot of the post boxes open under the name at that moment: one opened later is not reached, and a send to one that closed is lost. `broadcast("name")` looks them up again each time.

## 7. Cancellation and kill protocol

Two-phase escalation: cooperative first, forced second.

A thread cannot be killed: it ends only by cooperating (Phase 1), so its `atEnd` always runs normally. The forced kill (Phase 2) applies to tasks only.

### Phase 1: Cancellation signal

Send a cancellation **signal** (not a token) to the thread or the task through DFlat's signal system. It can catch it, finish its current work, and exit gracefully. If it cooperates, it exits normally: its `atEnd` block runs with full guarantees, `enforce` scopes unwind normally.

### Phase 2: Forced kill (tasks only)

If the task does not respond within the timeout of the `kill` (section 14), escalate to TaskKill or OS equivalent. The OS kills the task. Its stacks are destroyed and cannot be relied upon. **No `atEnd` runs.** The stack is not reliable after a forced kill, and memory may already be released — running cleanup code would be undefined behavior.

### Summary

```
Signal  →  "please stop"  →  thread or task cooperates  →  clean exit + normal atEnd
  ↓ (task only: timeout, no response)
Kill    →  OS kills the task  →  stacks are garbage  →  no atEnd, no cleanup
```

## 8. Farm (data-parallel construct)

- Name: **farm**. Blocking call: starts N threads and waits for them.
- **Split**: a function (or code inline in the block) that takes the farm params and returns one param tuple per thread. Splits can be uneven (0-15, 15-39, 39-46). No automatic split.
- **Join**: same contract, takes the array of thread results and returns the farm result.
- Without a Join the return type is `arr<threadreturntype>`. Farm is void if the thread function returns nothing (e.g. Mandelbrot writing its screen band in place).
- Farm is thread-level parallelism. SIMD is separate.

```
fun sum(arr<i32> data) {
  i32 total = 0
  for var item in data {
    total += item
  }
  return total
}

arr<i32> buff = ...
var res = farm(4, sum, buff)
```

Block form:

```
res = farm(4, thrfn, params) {
  Split: fun paramstuple(params) { code for the split }
  Join:  fun farmresult(arr<thrresult> results) { ... }
}
```

## 9. Pipe (stage-parallel construct)

- Each stage is a plain function that defines its input and output. Input and output types can be completely different.
- The pipe partitions the data, feeds the stages and collects the results. It is pull-based: the split runs each time the first stage needs more data.
- The pipe is the main task, its stages run in threads.
- Join is incremental (init, one call per result, end).
- Stateful stages (e.g. a P-frame needs the previous frame) must see data in order.

First skeleton:

```
fun <outStream1> PipableStage1(<inputParams>)
fun <outStream2> PipableStage2(<outStream1>)
fun <outStream3> PipableStage3(<outStream2>)
fun <Result>     PipableStage4(<outStream3>)
Result res = pipe(PipableStage1, PipableStage2, PipableStage3, PipableStage4, inputParams)
```

Example 1: 1 GB buffer, 64 KB chunks, 3 stages:

```
const i32 chunkSize = 64 * 1024

fun arr<u8> DecodePipeStage(arr<u8> block) {
  arr<u8> result = arr<u8>[block.len]
  for var index in 0..block.len {
    result[index] = block[index] ^ 0x5A
  }
  return result
}

fun arr<u8> FilterPipeStage(arr<u8> block) {
  arr<u8> result = arr<u8>[block.len]
  for var index in 0..block.len {
    result[index] = block[index] > 200 ? 200 : block[index]
  }
  return result
}

fun arr<u8> EncodePipeStage(arr<u8> block) {
  arr<u8> result = arr<u8>[block.len]
  for var index in 0..block.len {
    result[index] = ~block[index]
  }
  return result
}

fun main() {
  arr<u8> buff = loadfile("input.bin")   // 1 GB
  arr<u8> res = pipe(DecodePipeStage, FilterPipeStage, EncodePipeStage, buff, chunkSize) {
    u64 start = 0
    split: fun arr<u8>(arr<u8> buff) {
      while start < buff.len {
        feedpipe buff.view(start, chunkSize)
        start += chunkSize
      }
    }
  }
  savefile("output.bin", res)
}
```

Example 2: raw video compression (all types different, the join accumulates):

```
fun RawFrame      LoadFrame(PngImage png)       { ... }
fun FilteredFrame Denoise(RawFrame frame)       { ... }
fun EncodedFrame  Encode(FilteredFrame frame)   { ... }   // I, P or B frame

VideoFile video = pipe(LoadFrame, Denoise, Encode, framesFolder) {
  split: ...    // yields one PngImage per call
  joininit: fun VideoWriter() { return VideoWriter("out.mp4") }
  join:     fun (VideoWriter writer, EncodedFrame frame) { writer.write(frame) }
  joinend:  fun VideoFile(VideoWriter writer) { return writer.close() }
}
```

## 10. Target architectures and libraries

- Some parts of the language may be missing depending on the target (e.g. a C64 cannot have multitasking).
- The compiler handles it: no `if target.has(...)` construct in the source. An architecture has to define what it can provide, and the compiler checks each use against it.
- Granularity is probably finer than all-or-nothing, to be defined. It also covers type implementations (e.g. a C64 may provide only short strings, without the rope model).
- **Libraries are architecture-bound.** A library declares which architecture capabilities it requires. If a library uses threads, it requires threads — it does not compile for targets that lack threading. No conditional fallbacks, no silent degradation. If it compiles for your target, it works fully. The ecosystem naturally stratifies: some libraries are universal, some require specific capabilities.

## 11. Checkpoints and timers

- Checkpoints are every point where the running code can stop or hand over:
  - a call to the `wait` primitive, in any of its forms: a wait on a target (`wait x timeout N`), a timed wait, a bare `wait`, `Root.Time.wait`;
  - an `enforce`;
  - a `return` of any kind (`return`, `return!`, `return?`).
- The checkpoints are the only places where the callbacks of the events (section 5) and the calls through a task handle (section 1) run. Between two checkpoints the running code is never interrupted.
- `Root.Time.wait` is the same call as a timed `wait`.
- A bare `wait` and `wait 0` do not stop: they only act as a checkpoint.
- While a loop with no checkpoint inside runs, no callback and no call through the handle is served. This is why an infinite loop without a single checkpoint gets a level 1 compiler warning.

```
wait lapse(10)
wait 250                       // int, milliseconds
Root.Time.wait(250)            // the same call
```

## 12. Runnable (trait applied to Process, Task and Thread)

- Independent kinds, no containment; the program main is a Runnable too, the root of the tree.
- No processId in the trait (only in Process). Tasks and threads have none.
- name: process = full path of the executable; task = class name; thread = function name (a lambda: its signature).
- No `Hung` status: it is a detection problem (a method later, maybe a ping with a timeout; it only answers at a checkpoint, so a long busy loop would look hung). A send method on Runnable: not sure.
- Status `Killed`: in all cases of kill, also when the kill signal was sent and the task ended by itself.
- children: how it is implemented is left to the compiler, probably a `vec<%Runnable>`.
- Return signature: `Runnable` keeps the return signature of what it runs as a type, `ReturnType`. For several results it is the tuple: `fun i32, string taskRun()` gives `(i32, string)`.
  - The compiler fills it at creation: `Task(MyTask, ...)` takes the result of `MyTask.taskRun()`, `Thread(runThis, ...)` the result of `runThis`, `Process(...)` is `RunResult`.
  - With the creation on the same line nothing is written: `Task task = Task(MyTask, 123)` and `var task = Task(MyTask, 123)` both know it, and `var n = wait task timeout 500` has the right type.
  - Where there is no creation to read it from (a parameter, a field) it is written: `Task<i32> t`, `Task<(i32, string)> t`.
  - A plain `Task t` in those places can be started, killed, asked for its status and waited for without taking a value. `var x = wait t timeout 500` is a compile error there: the type is not known.
- Class of the task: the handle also keeps the class of its task, filled at creation like `ReturnType` and kept at run time. The compiler uses it for the calls through the handle.
  - With the creation on the same line nothing is written, and the task's own methods are reachable through the handle.
  - `Task<MyTask> t`: only this kind of task (or a subclass), checked at compile time. It gives the methods and the return signature.
  - `Task<i32> t`: any task that gives an `i32`. Its value can be waited for, its own methods are not reachable.
  - Plain `Task t`: any task.
  - `if t is Task<MyTask> mt { }` is always possible on a `Task t`: `mt` is the same handle seen with its class. The type switch works too: `t is ? { Task<MyTask> a: ..., Task<Logger> b: ..., default: ... }`.

```
enum RunKind { Process, Task, Thread }
enum RunStatus { Ready, Running, Completed, Failed, Killed }

trait Runnable<T> {
  RunKind kind
  RunStatus status
  string name
  date startTime
  Runnable parent                 // objects are nullable by default
  vec<%Runnable> children         // probably
  fun Runnable<T> start()
  fun ExpectedResult wait()
  fun bool kill(lapse timeout)
  fun bool kill(uns milliseconds)
}

class Task<ExpectedResult> : Runnable<ExpectedResult> { }
class Thread<ExpectedResult> : Runnable<ExpectedResult> { }
```

## 13. Process

- Same `start()` and `wait()` pattern as Task and Thread.
- Stdlib class: `Root.Multitasking.Process`, available just by importing multitasking.
- result inside the Process: no big pro or con, undecided.

```
class Process : Runnable {
  uns processID
  arr<string> args
  RunResult? result      // null until it finishes
}
```

## 14. Kill and cancellation

- `kill` picks the right way for the runnable kind and returns a bool.
- The timeout of `kill` is mandatory, as for `wait`: `task.kill(500)`. It is how long to wait before the hard kill.
- Steps:
    1. Send the kill-yourself (cancel) signal.
    2. Wait for the timeout: ended in time = true.
    3. No answer: strong kill and forget = false.
- Threads cannot be killed: only the cancel signal (cooperative).
- **Soft kill**: `atEnd` runs, best effort. **Forced kill**: no `atEnd`, no runtime cleanup. The stack is unreliable and memory may already be released.
- A hard kill makes no guarantees: nothing is promised about what was lent read-write to the killed task.
- The cancel signal goes down the children list in cascade, depth first (deepest children first). Killing a runnable kills all its children.
- The cascade goes level by level. The runtime takes the max length of the chain below the runnable (N levels) and starts from the deepest level: all the runnables of one level get the cancel signal together and share one window; who has not ended when it closes is hard-killed (tasks), then the level above starts.
  - An explicit `kill(T)` splits its timeout over the levels: `T / N` each, so the call returns within `T`.
  - With no timeout written (the end of the main program) the window is 50 ms per level: at most `N × 50` ms.
- When the main program ends, its children get the usual kill strategy.

## 15. Parent, children, asparent

- Same mechanism as "as parent" in the spec: a parent destroys its children when it ends.
- `asparent` is a visibility keyword (with internal, public, unrestricted): the method is callable only by the children. A thread can call its task's asparent methods.
- An `asparent` method of a task can be used by its sub tasks and by their threads (a thread has access to whatever its parent gives). It goes one level of tasks only: a task created by the sub task cannot use it.

```
process (main task) -> sub task -> thread          YES
process (main task) -> sub task -> sub sub task    NO
```

- An `asparent` call runs at once in the sub task (or in its thread), on the memory of the parent: it is not queued to a checkpoint. If there are writes, they need to be protected by the developer (`mutex` and `enforce`).
- `asparent` is for methods only. Data is shared by lending it (section 16).

```
class MyTaskClass {
  asparent fun log(string text) { ... }
  fun internalWork() { ... }
}
```

## 16. Memory

- Each task has its own heap. Everything the task allocates comes from it: its object, its strings and collections, the partitions of its threads. The main program is a task like the others, with its own heap.
- The heap of a task is freed in one piece when the task ends or is hard-killed. This is what makes the forced kill safe: no walk through the objects, no `atEnd`, the whole heap is released.
- Globals and mutex-marked refcounts live outside the heap of any task.
- Each thread allocates from its own partition: no shared allocator, no lock. Results cross to the task with the normal passing modes. The partition is freed when the thread ends.
- Passing to a task (constructor parameters, arguments of a call through the handle, results): the normal passing modes apply, for every type.
  - Plain: borrowed read-only. `&`: borrowed read-write. No copy: the task works on the data where it is.
  - `->` gives, `!` sends a clone.
  - With a read-write lend, the lender makes no assumptions on the content until the task terminates.

```
arr<u8> buff[4096]
Task t = Task(Filler, &buff).start()    // lent read-write, no copy
```

- A borrow does not change the ownership: when the task makes a borrowed object grow, it grows on the heap of its actual owner.
- Latent ownership transfer (inheritance): when the lender ends before the task, the ownership of what was lent passes to the task, and all continues. Otherwise the task would access freed memory.
  - The memory does not move: only the owner changes, and it is freed with the task.
  - What is lent to a task is never placed on the stack.
  - Level 3 warning where the compiler can see it.
  - When several tasks hold the same lend, the last one still running inherits it.
- No thread-local or task-local storage added for now: the task class fields are task-local, the thread function locals are thread-local.
- Refcounts: a mutex-marked `@` refcount is protected and safe to share between tasks. Open: atomic cost of the count, cycles, a shared mutable object still needs a lock, a handle passed to a task is shared memory.

## 17. Mutex

- Scoped use only, no manual acquire or release. A variable or object marked `mutex` is locked with `enforce` (`enforce guard { }` is the same as `lock guard { }`). There are no atomics: the mutex is enough. Can be a global.
- Among threads and tasks of one process, never between processes.
- Full lock (reads included), unlike `&@T`.
- Busy mutex: wait = enforce timeout, else mutex default, else 0 (one try); a failure goes to `lockfail` or `default`; with neither, the block is skipped and the code goes on. Default timeout at the definition.
- Native mutex or a class Mutex: undecided.
- Rules: a reference to mutex data escaping the enforce block is a compile error if possible, otherwise revisit; a blocking call inside enforce is a level 1 warning; locks are always taken in the same order, `enforce a, b, c` and `enforce b, a, c` is a compile error; a mutex object calling itself is probably reentrant (not confirmed); several variables under one enforce is already in the compiler.

```
mutex i32 counter = 0 timeout 1000
enforce counter { counter++ }
mutex bool guard
enforce guard { ... }
```

## 18. Semaphore

- Declaration: `semaphore name [= init] [timeout lapse]`. Type `uns`. Default init 1. Init 0 is a compiler error (deadlock).
- Scoped use only with enforce: the permit is taken at the start of the block and returned at its end. Busy: the regular enforce timeout rules.
- `enforce name.take(count) { }` takes (or waits for) several units.
- Not linked to signals. A force-killed task holding a permit: same open point as the mutex locks.
- Read/write lock: only if needed, defined as `r only` or `rw`.

```
semaphore pool = 12 timeout 1500
semaphore gate                  // 1 permit
semaphore broken = 0            // compiler error
enforce pool { ... }
enforce pool.take(10) { ... }
```
