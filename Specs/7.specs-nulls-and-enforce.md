# 7. Nulls

## 7.1 Nulls
- `date`, `time`, `clock` and `lapse` are already nullable and a variable of these types without a value starts as null. A `clock` prints as its number, a `lapse` as its number in its own unit, and null as `null`.

- Basic native types (integers, reals, `dec`, `bool`, `char`, enums, bitfields) are not nullable by default: nullable only as `type?`.
- Other native types (`string`, `date`, `time`, `clock`, `lapse`, `addr`), pointers and all objects (classes, collections) are nullable by default; `type?` on them is a compile error.
- Strings: for a `string`, `""` and null are the same.
- `string?` is a string where null is not `""` (null `!=` `""`), mostly for C interop (`string? name = string(p)`, 4.4.6):

```
string? a = null
string? b = ""
a == null            // true
b == null            // false
string s = a         // "": a null string? is "" in a string
a ?? "none"          // "none"; b ?? "none" is ""
$"{a}"               // "null"
```

  - It converts to `string` implicitly (null becomes `""`); a `string` converts to `string?` implicitly and is never null.
  - `==`, `!=`, `??`, `??=`, `?.` and `enforce` work as for the other nullable types. `+=` and the changes in place are not defined on a `string?`.
  - A `string?` variable, field or item owns its string: a borrowed string assigned to it is copied, and the string ends with the variable, the object or the collection. A `string?` parameter or loop variable borrows it and is read-only; a function returns a `string?` its caller owns (`fun ->string? find()`). A clone (12.6) copies it.
  - Built: local variables (declared with their type, not with `var`), parameters, results, fields, and the items of `arr`, `vec` and `list` (with their members, `filter` and `map<string?>`). Tuple items hold a `string?` as they hold a `string`. Not yet: the keys and values of maps and the items of sets, `&string?` and `->string?` parameters.
- Null propagates in arithmetic; equals only null; sorts first.
- Null object access raises `NullPointerException`; no `x!` force-unwrap.
- `?.` `??` `??=`; `i8 b = maybe ?? 0` unwraps into a non-nullable target.
- `a == null` may call an overloaded `==`; `a is null` always checks the reference.
- Tuples are not nullable

## 7.2 `enforce`

`enforce` runs a block only when its variables are safe to use, and collects in one place the handling of what can fail: null or gone objects, locks that cannot be taken, and the exceptions generated by those objects. It narrows the catches to the objects that raise.

```
enforce ref, stream, lockedResource {
  lockedResource.update(ref.data)
  stream.write(lockedResource.payload)
}
null on ref {
  log("Weak reference expired")
}
lockfail on lockedResource {
  log("Could not acquire lock on resource")
}
atEnd {
  log("written")                                   // only when nothing is pending
}
catch AccessToAClosedStreamException ex on stream {
  log($"Stream was closed during write: {ex.message}")
}
catch SeekBeforeBeginException on stream {         // silent: seen because it is caught here (15.4)
  log("Stream attempted to seek past boundary")
}
atEnd {
  stream.flush()                                   // always
}
```

### 7.2.1 Form

```
enforce <var> [timeout <ms>][, <var> [timeout <ms>] ...] { ... }
null      [on <var>[, <var> ...]] { }
lockfail  [on <var>[, <var> ...]] { }
catch <Exception> [<name>] [on <var>[, <var> ...]] { }
atEnd { }
default { }
```

- The clauses follow the block, in any number. `null` and `lockfail` can be written anywhere among them; the order of the catches and of the `atEnd` clauses matters (7.2.3).
- `on` limits a clause to the listed variables; without `on` the clause covers all of them. `catch` keeps its usual parts (15.1): the exception type, an optional variable, `catch all`.
- `default` is the catch-all, the last resort: when it is written, it handles every problem that no other clause handles, a failed check without its clause (7.2.2) and an exception that no catch matches (7.2.3). There is at most one.
- `timeout <ms>` sets how long the `enforce` waits at most for the lock of the variable written just before it, in milliseconds (7.2.2). It is valid only after a `&@T` or `&%T` variable (compile error otherwise). `enforce a, b timeout 500` waits up to 500 ms for `b` only; `a` uses its own default; `enforce a timeout 100, b timeout 500` gives both.
- `else` is the short form: `enforce a, b { } else { }` runs the else branch when any check fails. It is valid only when no other clause is written.
- Strings cannot be enforced.

```
i32? count = readCount()
enforce count {
  total += count                    // count is an i32 here
} else {
  total = 0
}

enforce a, b, c {
  a.mix(b, c)
}
null on a { log("no a") }           // a is null
null on b, c { log("no b or c") }   // b or c is null (only the first clause that matches runs)
null { log("something is null") }   // any other case: here none is left, it never runs
```

### 7.2.2 The checks

- Before the block, each variable is checked in the order written:
  - not null: `T?`, objects, null pointers;
  - still alive: a weak reference whose object is gone (12.7), an orphaned child (12.5);
  - for a `&@T` or a `&%T`, its lock is taken. The locks are taken in the order of the variables.
- Waiting for a lock: when the lock is free it is taken at once. When it is busy, the `enforce` waits, in the queue of the object's waiters, at most for its timeout: the `timeout` written in the `enforce` for that variable; when none is written, the default timeout of the object (12.7); when the object has none either, 0. A timeout of 0 tries the lock once and does not wait. There is no infinite wait.
- The waiting `enforce` checks its own timeout. When the lock is released, it goes to the first waiter of the queue. When the timeout runs out first, the waiter leaves the queue and the lock check fails: the lock failure goes to its `lockfail` clause, or to `default` (as below). A release and a timeout at the same moment are decided atomically: either the waiter gets the lock (and does not time out) or it times out (and the lock goes to the next waiter); the lock is never lost or held twice.
- There are no other checks: `enforce` knows only nullability, liveness and locks (it does not know whether a stream is "ready").
- When a check fails, every lock already taken is released, then the first `null` / `lockfail` clause that matches the failing variable runs; when none matches, `default` runs if it is written. When neither is written, nothing runs and the execution goes on after the `enforce`. In both cases the block, the catches and the `atEnd` clauses do not run: the `enforce` never started.

```
%Dog watcher = %first
&@Account account = Account()

enforce watcher, account {
  account.owner = watcher.name
}
lockfail on account { log("account busy") }
// watcher gone: no clause for it, the enforce is skipped and the code goes on
// account busy: "account busy" is logged, nothing else of the enforce runs

&@Item first = Item()
&@Item second = Item()
enforce first, second {             // first is locked, then second
  first.swapWith(second)
}
lockfail on first { }               // first is busy: nothing was locked
lockfail on second { }              // second is busy: the lock of first is released before this runs

&@Player player = @Player() timeout 100   // the default wait for its lock: 100 ms
enforce player { }                  // waits up to 100 ms
enforce player timeout 500 { }      // waits up to 500 ms: the timeout of the enforce wins
enforce first, player timeout 0 { } // first waits its default; player is tried once
lockfail on player { log("player busy") }
```

### 7.2.3 The block and the clauses after it

- Inside the block every variable has passed its checks: a weak reference holds a temporary usage of its object (12.7) and a `&@T` holds its lock.
- An exception raised in the block stops it and becomes pending. The clauses after the block are read from top to bottom:
  - `catch`: the first catch that matches handles the pending exception, which is no longer pending. `catch E on x` matches only the exceptions generated by `x` (raised by a member of `x`); a catch without `on` matches the exceptions of anything in the block and of the `atEnd` clauses above it.
  - `atEnd`: it runs when nothing is pending and is skipped while an exception is pending. An exception it raises becomes pending, and the catches below it can handle it.
  - The last `atEnd`, after the last catch, always runs, like a `finally`.
- An exception that no catch handles goes to `default` when it is written (then the last `atEnd` runs and the exception ends there); otherwise it bubbles up after the last `atEnd`, also one raised in a catch body. The last `atEnd` raising while another exception is pending is a `Panic` (as in 14.2).
- A silent exception that no catch of the `enforce` names is not created: its fallback applies (15.4).

```
enforce a {
  ...
}
atEnd { }          // 1
catch E1 { }       // 2
atEnd { }          // 3
catch E2 { }       // 4
atEnd { }          // 5
catch E3 { }       // 6
atEnd { }          // 7
```

| What happens | Runs |
|---|---|
| nothing fails | 1, 3, 5, 7 |
| 1 raises E2 | 4, 5, 7 (3 is skipped) |
| 3 raises E2 | 1, 4, 5, 7 |
| the block raises an exception that no catch matches | 7, then the exception bubbles up |

```
enforce file, log {
  file.write(data)                       // may raise AccessToAClosedStreamException
  log.append("saved")
}
catch AccessToAClosedStreamException on file {
  log.append("file closed")              // only the exceptions of file; the same exception from log goes on
}
catch Exception ex {
  report(ex.message)                     // anything else from the block
}
atEnd {
  log.flush()                            // always
}
```

### 7.2.4 Leaving the block

- `return` is allowed: the value is computed first, then the `atEnd` clauses run (nothing is pending, so all of them), then the locks and the usages are released.
- `break`, `continue` and `jump` that leave the block are a compile error. A loop inside the block keeps its own `break` and `continue`.

```
fun i32 balance(%Account weakAccount) {
  enforce weakAccount {
    return weakAccount.total             // computed, then the atEnd, then the usage is released
  }
  atEnd { log("read") }
  return 0                               // the account is gone
}

for var item in items {
  enforce item {
    if item.done {
      continue                           // compile error: continue leaves the enforce
    }
  }
}
```

### 7.2.5 Releases

- The locks and the temporary usages taken by the `enforce` are released at its very end, after the last `atEnd` and after `default`, on every way out: the normal end, `return`, an exception that bubbles up.

```
enforce account {
  account.total += 10                    // the lock is held
}
atEnd {
  log($"new total {account.total}")      // still held: the lock ends after the last atEnd
}
```

### 7.2.6 Expression form

`enforce` before an expression makes every variable of the expression an enforced variable, with the usual clauses: the expression defines the scope instead of a list of variables.

```
i32 r = enforce a + b.tryGet() + f.size() null on a { 1 } catch XException { -1 } default { 42 }
```

is the same as:

```
i32 r
enforce a, b, f {
  r = a + b.tryGet() + f.size()
}
null on a { r = 1 }
catch XException { r = -1 }
default { r = 42 }
```

- Every variable usage within the expression is treated as if it appeared in an enforce statement. Receiver objects, arguments, field accesses, property accesses, and other variable reads are checked according to 7.2.2.
- The clauses are those of the statement form: `null [on ...]`, `lockfail [on ...]`, `catch E [ex] [on ...]`, `default`. A failed null check raises nothing: it goes to its `null` clause, or to a `catch NullPointerException`, or to `default`.
- When everything works, the result is the value of the expression. When a clause handles a condition, the result is the value of that clause. An unhandled exception propagates normally. Unhandled null checks and lock failures follow the usual enforce rules and yield the zero or null value of the target type.
- The value of a clause follows the rule of the function bodies (13): a single expression is the value; a longer block gives it with `return`, which ends the clause, not the function. The local variables are visible in the clauses.
- Every path that gives a value (an expression or a `return`) must have a type compatible with the target: `i32 res = enforce f.size() default { "not good" }` is a compile error.
- The locks and the usages are held while the expression runs and released after the clause that ran, as after the last `atEnd` (7.2.5).

```
i32 size = enforce cache.count()                     // 0 when cache is null, gone or busy, or when count raises
string name = enforce weakUser.name() ?? "unknown"   // ?? acts on the result, as written

i32 res = enforce f.test()
  catch NullPointerException { return -1234 }        // f is null
  catch IllegalFileException { count++; return count }
  default { -1 }                                     // anything else

i32 r = enforce account.whatever() lockfail { -1 } default { 0 }
i32 hp = enforce timeout 500 player.health() lockfail { -1 }   // waits up to 500 ms for every lock
```

- `timeout <ms>` written right after `enforce` sets the wait for every lock the expression takes. Without it each object waits its own default (`@Player() timeout 100`, 7.2.2).
