You are helping me design how the collections `vec`, `list`, `map`/`bmap`, `hmap`, `set`/`bset` and `hset` are built in Dflat. You cannot see my files, so everything you need is below. Every point below carries one of three marks:

## 1. The project
Dflat is a statically typed language I am designing, with a Rust-like ownership model and C#/Rust-like syntax. The compiler is written in C# (.NET 10), generates C, and compiles it with clang. The compiler is at version 0.0.11alpha and the specification at 0.0.11 (the two versions are independent). There is a specification (dflat-spec.md), a standard library specification (dflat-stdlib.md), and 155 passing tests. Built collections: `arr<T>` and a first slice of `vec<T>` (see section 5).

## 2. Language facts you need
- Types: i8..i64, u8..u64, r32, r64, bool, char, string, date, time, classes, traits, enums, tuples. Lengths and indexes are `u64` everywhere. `uns` is a type of the spec but is not built in the compiler yet.
- Classes: `public class Name(i32 a, string b) : Parent, Trait { fields and methods }`. Fields are written in the body, primary constructor parameters become fields. No `new`: `Circle c = Circle(2.0)`. **All methods are camelCase** (`getIterator()`, not `GetIterator()`).
- Fields and properties are one concept (spec 11.1.4): `R:` / `W:` blocks, `field`, `value`, defaults, visibility per accessor; trait properties are access contracts with an optional default implementation (11.2). The compiler does not build this yet: it treats a read-only property of a library class as a method `get_name()`.
- Ownership (spec 12): single owner, freed at the end of the owner's scope. `->a` moves ownership (`list.add(->a)`), parameters borrow, returning moves to the caller, `b = a` is the same object without changing ownership, `a!` makes a copy, `.clone()` duplicates. Weak references `b _= a`, used with `enforce`. Collections own their elements: adding moves in, removing moves out, reading borrows. A destroyed object keeps its memory but points to a "dead" class, so a double free is detected.
- Objects are nullable by default; `T?` is not allowed on objects.
- Exceptions (spec 15), as rewritten on 2026/10/19-20: a function that can raise returns `(result, error)`; the compiler marks provably safe functions, and they return only the result. The caller owns and releases every returned error. A SILENT exception (a class with the `SilentException` trait) is returned like any other (a silent `throw` leaves its function like any `throw`), but only the immediate caller sees it, and only if a catch around the call handles it; otherwise the caller discards it and goes on with the value the function returned (the zero value). Operations of the language that raise silent exceptions (overflow of `+ - *`, a cast that does not fit) are seen only by a catch in the same function. A non-silent exception left unhandled inside an `atEnd` block is a Panic. The catch variable belongs to its catch and cannot be stored, returned or moved out.
- **SETTLED** (changed in the spec 0.0.11): the three silent exceptions of the collections (`NaNUsedAsKeyException`, `InvalidMapKeyException`, `EmptyVectorAccessException`, IDs 21 to 23) were removed and the IDs retired. The fallbacks apply (a NaN key is not stored or retrieved, a missing key reads as the null or zero value, `pop` returns `false`).
- Strings are never freed yet (known limitation); how a `string` is stored in the generated C (empty and null strings, occupancy flag of hash tables) is a separate session.

## 3. Generics (spec 11.3) as they are built today
The model is monomorphization like Rust: a generic function or class is a template and each distinct list of type arguments makes a separate copy, compiled as an ordinary class or function.
- Generic functions and classes: `class Stack<Item> { ... }`, `fun Item smaller<Item : Numeric>(Item a, Item b)`. Constraints with `&&`, and `where` clauses on functions and class headers. Named compile-time type sets: `Generic Strings { char, string }`, predefined `Signed`, `Unsigned`, `Integers`, `Reals`, `Numeric`.
- Value parameters: `class Grid<u64 Width, u64 Height, Cell>`, usable in array sizes.
- Type switch: `item is ? { Numeric: (r64)item, string: ..., default: ... }`. Only the matching case is compiled in each copy.
- Generic traits (`trait Container<Item>`), and placeholders (`placeholder Item`, `with (Item is u32)`, `where Source.Item : Numeric`). A generic PARENT trait (`trait A<T> : B<T>`) is not in the language.
- Conversion to a set member: `Box<Num>(5.5)` picks the member of the set `Num` from the argument.
- Not in the language: default type arguments, specialization, `T?` in generic code. A set is never the type of a value.
- Limits of generated copies (spec 11.3.12): chain depth 16, copies per user generic 16, copies per library collection 64 (counted per collection), `arr<T>` has no limit because it is a primitive.

## 4. What the specification says about collections (spec 6, version 0.0.11)
There are seven: `arr`, `vec`, `list`, `map` (alias `bmap`), `hmap`, `set` (alias `bset`), `hset`.
- `arr<T>`: fixed size set at initialization, contiguous, a primitive. `vec<T>`: contiguous and growable, capacity form `vec<T>[n]`. `list<T>`: a counted B-tree used by position, O(log n) insert and remove, no capacity. `map<K,V>`: sorted (B-tree). `hmap<K,V>`: hash map. `set<T>`: sorted (B-tree). `hset<T>`: hash set. `hmap` and `hset` have a capacity form.
- Collections are objects: nullable by default, they own their items, `==` compares identity only (`c!` or `.clone()` copies).
- **SETTLED** (spec 6.1): the seven collections are generated by the compiler as C code (speed first); users can write their own collection classes in Dflat (6.12).
- Index outside a collection: compile error when detectable; otherwise checked at runtime in every build. **SETTLED**: Debug raises `IndexOutOfRangeException` (not silent, catchable); Release is a `Panic` and a `catch` for it is ignored with a level 3 warning.
- Keys: hashed collections need `==` and a hash; sorted collections need an ordering. `.hash` and `.order` exist on all types. Orders: numbers, char, bool, date, time by value; strings by bytes; tuples item by item. Reals can be keys except NaN (never stored). **SETTLED**: maps and sets do not allow null keys or null set items; `""` is a valid string key.
- Literals: `[1,2,3]` can be assigned to arr, vec, list, set, hset; `{k: v}` to map and hmap; literals are `arr` unless declared otherwise; empty literals need a declared type.
- **SETTLED** (6.4): `for Item x in c` is read-only; `for (&)Item x in c` is a read/write borrow of the item (the marker is written `(&)Type variable` everywhere); set items and map keys are always read-only; a basic value without `(&)` is a copy and assigning to it gives a level 3 warning. A `for` loop only borrows (no consuming loop). A collection cannot be changed while it is iterated.
- **SETTLED** (6.6): `pop((&)out)` returns a `bool`, moves the last item of a `vec` into `out`, and on an empty `vec` returns `false` and gives `out` the default value (the only form of `pop`). `bool tryGet(k, (&)out[, default])` returns `true` when the key exists. `swap`: `Item old = sequence.swap(position, Item new)`; `Item old = map.swap(Key key, Item new)` (a missing key adds the pair and returns a null item); `sequence.swap(i, j)`; `map.swap(key1, key2)` (both present: exchange; one present: its value moves to the missing key and the original key is removed; both missing: nothing). `->c[k]` moves an item out: the slot is zeroed in `arr` and `vec`, and the item is removed in `list`, `map`, `hmap`, `set` and `hset`. A result that is not assigned is destroyed at the end of the statement; `c[k] = v` drops the previous item.
- Members (6.6): `.len`, `.capacity`, `reserve`, `shrinkToFit`, `.keys`, `.values`, `c[k]` read, `c[k] = v`, `add(v)`, `add(k, v)` (bool), `add(collection)`, `insert(index, v)`, `pop((&)out)`, `has`, `hasKey`, `indexOf`, `keyOf`, `remove`, `removeAll`, `removeAt`, `tryGet`, `swap`, `clear`, `fill`, `fillAtCapacity`, `resize`, `truncate`, `sort`/`sortUnstable` (a custom comparer is a lambda), `reverse`, `copyFrom`, and for sets `union`, `intersection`, `difference`, `symmetricDifference`, `|=`, `&=`, `-=`, `^=`, `isSubsetOf`, `isSupersetOf`, `isDisjointFrom`.
- Views (6.5), **PROPOSAL** (first session, preliminary): views are read-only only (no writable views), and can only be local variables or parameters, never fields, collection items or results. The full Rust borrow model stays an option.
- Custom collections (6.12, partial). **SETTLED**: the traits `Collection` (all seven), `IndexCollection` (`arr`, `vec`, `list`), `MapCollection` (`map`, `hmap`) and `SetCollection` (`set`, `hset`) impose the signatures; they take the item type as a generic argument (`class MyCollection<Item> : IndexCollection<Item>`; there is no reserved type name); `Collection` requires a read-only `len` and `fun Iterator getIterator()`; `for x in c` on a custom collection asks `getIterator()` once and calls `next()` until `isValid` is false; `next()` returns a tuple ending with `isValid`: `(Item value, bool isValid)` for sequences, `(Key key, Value value, bool isValid)` for maps (the shape for sets is open). **SETTLED** (2026/10/20): for `vec` and `arr` the iterator is simply a `uns cursor` (u64 in the compiler for now) and `next()` increases it; the specification is finished when the other iterators are needed. For the collections of the compiler no iterator object is built in a `for`: it is a direct C loop.

## 5. What the compiler can and cannot do today
**Built**: classes, inheritance, traits, enums, tuples, exceptions and silent exceptions (as in section 2), ownership with owners and borrows and `->`, reference parameters, `arr<T>` with its members, all the generics of section 3, `File` and `FileStream` written in Dflat as preludes, and the first slice of `vec`:
- `vec<T>` literals (`vec<i32> a = [1, 2, 3]`, bare `vec w = [...]`), the capacity form `vec<T>[n]`, `c[i]` read and write, `.len`, `.capacity`, `for`, `add(->v)`, `insert`, `pop((&)x)`, `remove`, `removeAll`, `removeAt`, `clear`, `reserve`, `shrinkToFit`, `fillAtCapacity`, `resize`, `truncate`, `swap(i, j)`, `has`, `indexOf`, `fill`, `reverse`, `sort`, `sortUnstable`, `getIterator()`.
- Items are owned (moved in, moved out, dropped when removed or replaced; the vec ends its items and frees its block).
- Traits `Iterator` (a marker), `IndexIterator<Item>` (a `u64 cursor` and `next()`), `IndexCollection<Item>` (`get_len()` and `getIterator()`); `arr.getIterator()`; `for x in c` over a class of the program that implements `IndexCollection<T>`.
- Tests: `vec`, `vecown`, `customcollection` and six error cases; a 20-million-item loop works.

**Not built (the compiler answers "feature not supported")**: pointers, lambdas and function types (so `sort(lambda)`), secondary constructors, `atEnd` in a class body (a destructor), imports and libraries, indexer or operator overloading for user classes (open), `T?` in generic code, conversion of `Box<Dog>` to `Box<Animal>`, trait properties (11.1.4), `uns`, `Collection<Item>` (needs a generic parent trait), `add(collection)`, `copyFrom` on `vec`, views `v[a..b]`, `v!` (clone), `removeAt(range)`, `swap(position, new)`, `fill` of objects (needs cloning), the sized declaration `vec<T>[n] name`, `for (&)Item x in c`, the compile error for changing a collection while it is iterated, the Debug / Release index rule (needs the options `--debug` and `--release`), and `list`, `map`, `hmap`, `set`, `hset`.

**How `vec` is implemented today (to review, see question 1)**: a generic class `vec<T>` written in Dflat over `arr<T>`, embedded in the compiler and added when a program mentions `vec`. The hot paths are not calls but C emitted by the compiler: `c[i]`, `c[i] = v`, `.len`, the `for` loop, `has`, `indexOf`, `fill`, `reverse`, `sort`, `sortUnstable`, `pop` and the literals. This contradicts the settled decision "generated as C code", and I accepted it only for the first slice because ownership, drops, traits and exceptions then work without new machinery. A hand-written C version can replace it without changing the language.

## 6. The first questions, with their state
1. **Where the collections are written.**
   - SETTLED: the seven collections are generated by the compiler as C code; users can write their own collection classes in Dflat; mandatory traits fix the signatures (`Collection`, `IndexCollection`, `MapCollection`, `SetCollection`).
   - NOT DECIDED: whether the current `vec` (Dflat class over `arr`, section 5) stays for now or is replaced by C templates before the next collection is built; and the same for `list`.
2. **What the language must gain first.**
   - SETTLED: for the compiler's own collections nothing is needed (it emits C). For custom collections: `len` is a read-only property of the trait; `getIterator()` is required; `for x in c` uses an iterator with `next()` returning a tuple ending with `isValid`; fields and properties are one concept (11.1.4).
   - NOT DECIDED: the indexer (`c[k]` read and write) and the literal construction for custom classes; which other members the collection traits require and which they supply by default.
3. **Order of work.** SETTLED: the order does not matter, everything will be implemented. (Built: `vec`. The next one is probably `list`.)
4. **Ownership of the items.**
   - SETTLED: the Rust model; the drop code is generated per item type; the rules of `->c[k]`, `pop`, `swap`, `tryGet`, `c[k] = v` and the unassigned result (section 4).
   - NOT DECIDED: `swap` and `->c[k]` on sets (a set has no `c[k]` read).
5. **Exceptions and cost.**
   - SETTLED: the index check in every build (Debug: `IndexOutOfRangeException`; Release: `Panic`); the three silent exceptions of the collections are removed.
   - NOT DECIDED: whether the index rule also covers `arr` indexing and the other non-silent exceptions of operations; the cost of `c[i]` as a failing operation (the error part). Today `vec` indexing is inlined C that raises `IndexOutOfRangeException` in every build.
6. **Borrow rules.**
   - SETTLED: a collection cannot be changed while it is iterated; `for` read-only and `for (&)` read/write (section 4).
   - PROPOSAL: enforcement as a compile error when the compiler can prove the loop body changes the collection (Rust style), otherwise a version check at runtime (C# style); views read-only, only local variables or parameters.
   - NOT DECIDED: what the runtime check raises; how an iterator refers to its collection without a borrow stored in a field (today `vecIterator` and `arrIterator` hold a snapshot of the items and the count); how `next()` returns a read-only or a writable borrow of the item.
7. **Hashing and ordering.**
   - SETTLED: NaN keys are never stored; null keys are not allowed.
   - PROPOSAL: `hmap` and `hset` can have several implementations, chosen by target architecture or compiler option (the iteration order of hashed collections is already unspecified); `reserve` gives the initial size.
   - NOT DECIDED: the hash function, the table design (open addressing, robin hood, chaining), the B-tree node size, the cursor type of each iterator (a position for `arr` / `vec` / `list`, a slot for hash tables, a node or a key for trees), and whether `Iterator` has two or three sub-traits.
8. **Code size** (a copy of the class per element type, limit 64). NOT DECIDED: copies per element type against shared non-generic C helpers working on byte sizes.
9. **Literals and inference.** The typing rules of 6.3 stay. For `vec` the compiler lowers a literal to an empty vec plus a block of items. NOT DECIDED: the lowering for the other collections, and how a custom class receives the items of a literal.

## 7. What I want to refine for `list` (spec 6.9 is only a short section today)
1. **Structure.** Is the counted B-tree required, or just the O(log n) insert and remove by position? The node size is open: a fixed number of items per node, or a size chosen from the item size? PROPOSAL: a fixed node size to start, with the structure private so it can change later.
2. **Position semantics.** `insert(index, v)` with `index == len` appends, as in `vec`; is that the same for `list`? What does `list[i]` cost (O(log n) per access)?
3. **Iterator cursor.** For `vec` the cursor is a position. For `list` it could stay a position (simple, O(log n) per `next()`) or be a leaf pointer plus an offset (faster, but a different cursor type from `IndexIterator`). Which one for the first version?
4. **Members.** The list column of 6.6 has no `pop`, `fill`, `resize`, `truncate`, `reserve` or `.capacity`. Is `sort` on a list required in the first slice (it needs a different algorithm over nodes)? Views on a list: same rules as `vec`?
5. **Ownership.** PROPOSAL: the same Rust model as `vec` (`add(->T)`, `->list[i]` removes the item, items dropped on removal, node memory freed when the list ends). Please confirm there is no difference for `list`.
