# Collections: what is left to decide and to build (updated 2026/10/28, Specs0.0.18, compiler 0.0.34alpha)

You are helping me finish the design of the collections of Dflat. You have access to the approved specification: it is quoted as Specs<section> (for example Specs6.8.3 is section 6.8.3 of dflat-spec.md). The compiler is written in C# and generates C (clang). It builds `arr<T>`, `vec<T>`, `list<T>`, `map<K, V>` and `hmap<K, V>` (native and string keys and values); `set` and `hset` do not exist yet. Every point below has a tag that says whether it is open, decided, built or left for later, with its context. Please answer by point number.

The points tagged INSPECS are decided and written in the specification (Specs0.0.16, 0.0.17 and 0.0.18, 2026/10/26 to 2026/10/28): each keeps only a line with the sections of the spec, and its COMPILERSTATE line when something is not built. The points still tagged DECIDED are decided but not (fully) in the specification, for the reason written in them. The discussion continues with the TOBEDISCUSSED points.

Tags (one per point):
- TOBEDISCUSSED: open, needed shortly. This is what I want to discuss.
- DECIDED: decided, not built or only partly built (a COMPILERSTATE line says what is missing). Do not reopen it unless you find a real contradiction.
- IMPLEMENTED: decided and fully built by the compiler.
- INSPECS: decided and written in the specification; only a pointer to the spec sections is left here (plus the COMPILERSTATE line when something is not built).
- FUTUREVERSION: not for now, left on purpose for a later version of the specification.
- REMOVED: no longer a point.

Labels inside a point:
- PROPOSAL: an idea (mine, of the design side or of the compiler side), not confirmed. Please judge it.
- COMPILERSTATE: a fact about what the compiler does or does not do today. Not a decision.
- EXPLORED: discussed on 2026/10/26 as a possible direction, explicitly not decided.

How the compiler implements the collections today (so you can judge the proposals): `vec` and `list` are generic classes written in Dflat over `arr<T>`, embedded in the compiler. The hot paths (index, length, `for`, the literal, `has`, `sort`, printing, the drop) are C that the compiler emits. The items are owned: moving an existing object in needs `->x`, a new object needs no marker, a replaced or removed item ends; a string item is always its own copy in its smallest form. The counter of open iterators and views (the private field `iteratorCounter` of the trait `Collection`) makes a changing operation raise `ModifyingIteratedCollectionException` (ID 46). In Release builds an index outside a collection and that exception are a `Panic`. Traits: `Collection<Item>` (the parent), `IndexCollection<Item>`, `IndexIterator<Item>` and `Iterator`. The language has generic traits with a generic parent trait, placeholders, a type switch, value parameters, ownership with moves, silent exceptions, a preprocessor and `uns`. `map` and `hmap` are generic classes written in Dflat too, over a C runtime each (the B+ tree and the extendible hash table); they share the class methods and the code at the call sites. `.hash` is built for every type (point 86). A printed collection shows only its first 3 items, then `, ...] (N items)` (Specs6.1).

5. Smaller ones: 36 (lambdas and `sort(lambda)`), 45 (code size of the generic maps), 66 (variadic parameters and an existing collection).

## PART A - Traits, iterators and the rules every collection shares

The traits are in Specs6.7 and Specs6.9, the iteration rules in Specs6.4. The compiler has `Iterator` (a marker trait), `IndexIterator<Item>` (`next()`; the cursor is private to each iterator), `Collection<Item>` (`len`, `has`, `clear`, the iterator counter) and `IndexCollection<Item>` (`getIterator()`), implemented by `vec` and `list`; `arr.getIterator()` also works.

### 1. [INSPECS] The Iterator trait hierarchy

Specs6.7: `Iterator` marker trait with `IndexIterator`, `MapIterator`, `SetIterator`.
COMPILERSTATE: `Iterator` is an empty marker trait, `IndexIterator<Item> : Iterator` with `next()`. Missing: `MapIterator`, `SetIterator` (decided, Specs6.7.3) and `writableNext()`.

### 2. [INSPECS] getIterator() in the Collection sub-traits

Specs6.7: each sub-trait declares its own typed `getIterator()`.
COMPILERSTATE: `IndexCollection<Item>` with its `getIterator()` is built. `MapCollection` and `SetCollection` wait for maps and sets.

### 3. [INSPECS] The cursor of the iterators

Specs6.7, 6.7.1, 6.8.3: the cursor is private to each iterator.
COMPILERSTATE: the cursor is private to each iterator; the `vec` iterator keeps a position, the `list` iterator keeps a node.

### 4. [INSPECS] How the iterator refers to its collection

Specs6.7, 6.8.3: the reference to the collection lives in the concrete iterator, declared `as parent`.
COMPILERSTATE: the iterator of `vec` and `list` is a child object of its collection (it holds the counter of point 6); the pointer kind waits for pointers.

### 5. [INSPECS] writableNext() and for (&)

Specs3.2, 6.4, 6.7: `(&)` inside a tuple, `writableNext()`.
COMPILERSTATE: neither `writableNext()` nor `for (&)Item x in c` is built. A borrow inside a tuple is not a type the compiler has.

### 6. [INSPECS] The collection is read-only (in size) while it has open iterators or views

Specs6.4: the counter of open iterators and views; Debug catchable, Release `Panic`.
- Note 2026/10/26: whether `ModifyingIteratedCollectionException` should be an immediate `Panic` in Release is questioned ("maybe yes, maybe no"). Not reopened; nothing is written in stone. Not all exceptions in Release are panics: some are normal bubbling exceptions that must be handled (like a Rust `Result`).
COMPILERSTATE: built for `vec` and `list` (iterators and views). Missing: the counter on `arr` (an `arr` has no header yet).

### 7. [INSPECS] Which operations count as a change

Specs6.4, 6.6: forbidden and allowed operations; `clear()` keeps the size.
COMPILERSTATE: built for `vec` and `list`, including `clear()` keeping the size and `truncate` on `list`. Missing: the checks on `arr` (no counter, point 6).

### 8. [INSPECS] The compile-time proof of a change inside a loop

Specs6.4: only the direct case is proved.
COMPILERSTATE: only the runtime check is built.

### 9. [INSPECS] Change detection in custom collections: executeAfter and executeBefore

Specs11.2, 6.9: `executeAfter` (after a success, reads `<method>.result`; the iterator counter, `Keyable`) and `executeBefore` (before the implementation, can stop it; `checkUnlocked()` on the methods that change the size). Both are needed (2026/10/26).
COMPILERSTATE: `executeAfter`, the private `iteratorCounter`, `acquireIterator()` and `releaseIterator()` are built. Missing: the chain has one link only (a sub-trait cannot redeclare the method), and the changing methods (`add`, `remove`, ...) are not trait methods, so they carry no check in custom collections.

### 10. [INSPECS] .sizeof of a collection

Specs6.6: header plus the allocated block.
COMPILERSTATE: built on `arr`, `vec` and `list`.

### 11. [INSPECS] The methods behind the properties and the operators

Specs6.7: the snake_case methods table.
COMPILERSTATE: `get_len()` is built. Missing: `get_view` and `read_pos` for custom collections.

### 20. [INSPECS] arr is a class

Specs6.1, 6.8.1: `arr` is a class with ownership.

## PART F - map (bmap): the sorted map

Specs6.8.4, Specs6.7.2. Nothing is built. The settled rules: sorted by key (B-tree), alias `bmap`, no capacity, `MapCollection<Key, Value>`, a missing key reads as the null or zero value, `add(k, v)` returns `false` when it replaced a value, `add(map)` merges (the new value wins), `tryGet(k, (&)out[, default])` returns `true` when the key exists, `swap` forms, `->c[k]` removes the entry, `has(v)`/`remove(v)`/`removeAll(v)` work on values. (2026/10/26: a null key is no longer excluded, see point 15.)

### 38. [INSPECS] The B-tree design

Specs6.8.4.1. The multi-type parts are reserved there (open, Specs99).
- Decided 2026/10/26 (string values, NOT yet in the spec): 64 bytes is only the size limit for keeping a string value inside the leaf: a string of up to 59 bytes of text sits in the slot (class 0 or 1), a longer one is pointed to (class 13). Because a string in the slot moves with its leaf (insert, split, merge, share), the read rule is: a read inside a statement (`print(m[k])`, `m[k] == "x"`, `m[k].len`) or in a `for` loop over the map (which locks its size) is done in place; a value that is kept (`string s = m[k]`, `s = m[k]`, a field, a parameter written to, `tryGet`) is a copy; `->m[k]` takes the string out.
COMPILERSTATE: built for native and string keys and values (compiler 0.0.23alpha to 0.0.27alpha): exact sort keys and string keys (16-byte slot, separators that point to the leaf keys), string values inline with the read rule above, relaxed deletion, one rebuild for removeAll, the null key in the header, the iterator of the for loop. Missing: keys and values that are objects, tuples or wide natives, multi-type keys, clock and lapse keys (their null is 0).

## PART G - hmap: the hash map

Specs6.8.5, 6.8.5.1. Built (steps 1 to 6 of point 46, compilers 0.0.30alpha to 0.0.34alpha) for native and string keys and values. The settled rules: hash map, same members as `map` (Specs6.7.2), iteration in an unspecified order (the same for the same content and history), capacity members `.capacity`, `reserve`, `shrinkToFit` and the capacity form `hmap<K, V>[n]`, keys need `equals` and a hash.

### 46. [INSPECS] The hash table design

Specs6.8.5.1 (extendible hashing: directory, buckets of 16 with chains of extensions, two Fibonacci scrambles, layouts, merges, directory shrink, stuck buckets, capacity, `shrinkToFit()`, iterator), 6.2.1 (identity, null), 6.8.7 (`hset` from `hmap`). The old proposal (open addressing with robin hood probing) is dropped.
Note 2026/10/26 (still valid): the hash is stable across runs for value types, so a saved map stores keys and values, never the hashes or the table (the table is rebuilt on load).
COMPILERSTATE: steps 1 and 2 built 2026/10/27 (compilers 0.0.30alpha and 0.0.31alpha, tests hmap, hmapstrings): native keys and values, strings, `.keys` and `.values` (step 4, 0.0.32alpha, test hmapviews), capacity (step 5, 0.0.33alpha, test hmapcapacity), literals with the types from the entries (step 6, 0.0.34alpha, test hmapliterals); also removal and shrinking (step 3), `for (k, v)`. `.hash` is built (point 86).
Build order (the compiler side decides), after point 86:
  1. native keys and values - DONE (0.0.30alpha, test hmap)
  2. strings - DONE (0.0.31alpha, test hmapstrings)
  3. removal and shrinking - DONE with step 1
  4. `for (k, v)`, `.keys`, `.values` - DONE (0.0.32alpha, test hmapviews)
  5. capacity - DONE (0.0.33alpha, test hmapcapacity)
  6. literals - DONE (0.0.34alpha, test hmapliterals)
  7. `hset` - the basic part can be built now; the set operations wait for points 52 to 61 (see the AGENDA)
  8. object keys, after `Keyable` (point 79)
Compiler choices (CompilerImplementation.txt): the key slot of a native is 8 bytes also with a 32-bit `uns`; C(d) and C(d-1) are kept for every d; the directory stops at 48 bits (28 with a 32-bit `uns`).
Open (Specs99): widening of the stuck buckets (later).

### 52. [INSPECS] The operations that return a new set

### 53. [INSPECS] The in-place operators += and -=

Specs6.6, 6.7.2, 6.8.6: only `+=` and `-=`, on every map and set; they call the members (no special case of the compiler, one implementation; a custom collection gets them from its members, Specs6.9). Maps: `m += (key, value)` (`add(k, v)`), `m += other` (`add(map)`), `m -= key` (`removeAt`), `m -= s` (a `set` or `hset` of the key type: every key removed with its value). Sets: `s += v` / `s += other` (`add`), `s -= v` (`remove`), `s -= other` (in-place difference). `|=`, `&=` and `^=` are removed.
COMPILERSTATE: built for maps 2026/10/28 (compiler 0.0.35alpha, test mapoperators): `add(map)`, `m += (k, v)`, `m += pair`, `m += other`, `m -= key` on `map` and `hmap`. Built 2026/10/28 (0.0.38alpha / 0.0.39alpha): the sets and `m -= set` (test mapminusset). ### 83. [TOBEDISCUSSED] Lifetime of borrows of items

Context: a borrow of an item taken outside a `for` loop (`(*)i32 p = (&)m[k]`, `f((&)m[k])`, `(&)v[3]`) points into the collection. An insert or delete in a `map` shifts or moves the inline values of a leaf (point 38), and an `add` that reallocates a `vec` moves its items, so the borrow points to the wrong place. Inside `for (&)` it is safe (the counter blocks changes, point 6); `tryGet(k, (&)out)` is safe (`out` is the caller's own variable). The spec has no rule for it.
PROPOSAL: a borrow of an item (`(&)c[k]`, `&c[k]`) increments the counter of the collection, like an iterator, as long as the borrow lives; meanwhile a change raises `ModifyingIteratedCollectionException`. The borrow lives at most to the end of its scope, like the iterators, views and tuples holding a `(&)` (Specs3.2, Specs6.5).
Open: this needs the compiler to track the lifetime of borrows in general, which is wider than the collections. Prerequisite of step 5 of point 78.

### 85. [TOBEDISCUSSED] Temporary objects that never end

Context: found 2026/10/26 while building step 4 of point 78. A new object that is not kept in a variable and not returned (a temporary inside an expression) is never ended by the compiler (a known limit of the ownership code: "temporaries inside an expression are never destroyed"). For a view this means its counter is never given back, so its collection stays locked for good:
```
vec<i32> v = [1, 2, 3, 4]
r.Console.log(v[1..3])          // the view is never ended
v.add(5)                        // ModifyingIteratedCollectionException (a Panic in Release)
```
The same happens with `v[1..3].len`, a view passed to a function, and a new map view used in another expression (for the maps the common forms avoid the view object).
COMPILERSTATE: not fixed. The view of a map given only to printing is printed and then ended.
Question: when does a temporary object end? PROPOSAL: at the end of the statement that made it, like the temporary strings (df_tmp), unless it is kept (a variable, a field, an item, a returned value, an argument moved with ->).

### 86. [INSPECS] Building .hash before hmap
