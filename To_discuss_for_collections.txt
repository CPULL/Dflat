# Collections: what is left to decide and to build (updated 2026/10/26, Specs0.0.16, compiler 0.0.22alpha)

You are helping me finish the design of the collections of Dflat. You have access to the approved specification: it is quoted as Specs<section> (for example Specs6.8.3 is section 6.8.3 of dflat-spec.md). The compiler is written in C# and generates C (clang). It builds `arr<T>`, `vec<T>` and `list<T>`; `map`, `hmap`, `set` and `hset` do not exist yet. Every point below has a tag that says whether it is open, decided, built or left for later, with its context. Please answer by point number.

The points tagged INSPECS are decided and written in the specification (Specs0.0.16, 2026/10/26): each keeps only a line with the sections of the spec, and its COMPILERSTATE line when something is not built. The points still tagged DECIDED are decided but not (fully) in the specification, for the reason written in them. The discussion continues with the TOBEDISCUSSED points.

Tags (one per point):
- TOBEDISCUSSED: open, needed shortly. This is what I want to discuss.
- DECIDED: decided, not built or only partly built (a COMPILERSTATE line says what is missing). Do not reopen it unless you find a real contradiction.
- IMPLEMENTED: decided and fully built by the compiler.
- INSPECS: decided and written in the specification; only a pointer to the spec sections is left here (plus the COMPILERSTATE line when something is not built).
- FUTUREVERSION: not for now, left on purpose for a later version of the specification.
- REMOVED: no longer a point.

Labels inside a point:
- PROPOSAL: an idea (mine, of the design side or of the compiler side), not confirmed. Please judge it.
- COMPILERSTATE: a fact about what the compiler does or does not do today. Not a decision.
- EXPLORED: discussed on 2026/10/26 as a possible direction, explicitly not decided.

How the compiler implements the collections today (so you can judge the proposals): `vec` and `list` are generic classes written in Dflat over `arr<T>`, embedded in the compiler. The hot paths (index, length, `for`, the literal, `has`, `sort`, printing, the drop) are C that the compiler emits. The items are owned: moving an existing object in needs `->x`, a new object needs no marker, a replaced or removed item ends; a string item is always its own copy in its smallest form. The counter of open iterators and views (the private field `iteratorCounter` of the trait `Collection`) makes a changing operation raise `ModifyingIteratedCollectionException` (ID 46). In Release builds an index outside a collection and that exception are a `Panic`. Traits: `Collection<Item>` (the parent), `IndexCollection<Item>`, `IndexIterator<Item>` and `Iterator`. The language has generic traits with a generic parent trait, placeholders, a type switch, value parameters, ownership with moves, silent exceptions, a preprocessor and `uns`.

## PART A - Traits, iterators and the rules every collection shares

The traits are in Specs6.7 and Specs6.9, the iteration rules in Specs6.4. The compiler has `Iterator` (a marker trait), `IndexIterator<Item>` (`next()`; the cursor is private to each iterator), `Collection<Item>` (`len`, `has`, `clear`, the iterator counter) and `IndexCollection<Item>` (`getIterator()`), implemented by `vec` and `list`; `arr.getIterator()` also works.

### 1. [INSPECS] The Iterator trait hierarchy

Specs6.7: `Iterator` marker trait with `IndexIterator`, `MapIterator`, `SetIterator`.
COMPILERSTATE: `Iterator` is an empty marker trait, `IndexIterator<Item> : Iterator` with `next()`. Missing: `MapIterator`, `SetIterator` and `writableNext()`.

### 2. [INSPECS] getIterator() in the Collection sub-traits

Specs6.7: each sub-trait declares its own typed `getIterator()`.
COMPILERSTATE: `IndexCollection<Item>` with its `getIterator()` is built. `MapCollection` and `SetCollection` wait for maps and sets.

### 3. [INSPECS] The cursor of the iterators

Specs6.7, 6.7.1, 6.8.3: the cursor is private to each iterator.
COMPILERSTATE: the cursor is private to each iterator; the `vec` iterator keeps a position, the `list` iterator keeps a node.

### 4. [INSPECS] How the iterator refers to its collection

Specs6.7, 6.8.3: the reference to the collection lives in the concrete iterator, declared `as parent`.
COMPILERSTATE: the iterator of `vec` and `list` is a child object of its collection (it holds the counter of point 6); the pointer kind waits for pointers.

### 5. [INSPECS] writableNext() and for (&)

Specs3.2, 6.4, 6.7: `(&)` inside a tuple, `writableNext()`.
COMPILERSTATE: neither `writableNext()` nor `for (&)Item x in c` is built. A borrow inside a tuple is not a type the compiler has.

### 6. [INSPECS] The collection is read-only (in size) while it has open iterators or views

Specs6.4: the counter of open iterators and views; Debug catchable, Release `Panic`.
- Note 2026/10/26: whether `ModifyingIteratedCollectionException` should be an immediate `Panic` in Release is questioned ("maybe yes, maybe no"). Not reopened; nothing is written in stone. Not all exceptions in Release are panics: some are normal bubbling exceptions that must be handled (like a Rust `Result`).
COMPILERSTATE: built for `vec` and `list` (iterators and views). Missing: the counter on `arr` (an `arr` has no header yet).

### 7. [INSPECS] Which operations count as a change

Specs6.4, 6.6: forbidden and allowed operations; `clear()` keeps the size.
COMPILERSTATE: built for `vec` and `list`, including `clear()` keeping the size and `truncate` on `list`. Missing: the checks on `arr` (no counter, point 6).

### 8. [INSPECS] The compile-time proof of a change inside a loop

Specs6.4: only the direct case is proved.
COMPILERSTATE: only the runtime check is built.

### 9. [INSPECS] Change detection in custom collections: executeAfter and executeBefore

Specs11.2, 6.9: `executeAfter` (after a success, reads `<method>.result`; the iterator counter, `Keyable`) and `executeBefore` (before the implementation, can stop it; `checkUnlocked()` on the methods that change the size). Both are needed (2026/10/26).
COMPILERSTATE: `executeAfter`, the private `iteratorCounter`, `acquireIterator()` and `releaseIterator()` are built. Missing: the chain has one link only (a sub-trait cannot redeclare the method), and the changing methods (`add`, `remove`, ...) are not trait methods, so they carry no check in custom collections.

### 10. [INSPECS] .sizeof of a collection

Specs6.6: header plus the allocated block.
COMPILERSTATE: built on `arr`, `vec` and `list`.

### 11. [INSPECS] The methods behind the properties and the operators

Specs6.7: the snake_case methods table.
COMPILERSTATE: `get_len()` is built. Missing: `get_view` and `read_pos` for custom collections.

## PART B - What is missing on arr

Specs6.8.1. Built: literals, `arr<T>[n]`, the sized declaration `arr<T>[n] name`, `c[i]`, `.len`, `for`, `has`, `indexOf`, `fill`, `clear`, `reverse`, `sort`, `sortUnstable`, `copyFrom` (from an `arr`, a `vec` or a `list`, without objects), `swap(i, j)`, `replace`, `->a[i]`, `getIterator()`, views `a[x..y]`, `.sizeof`, `transformTo<Kind>()`, the ownership rules of the items when they are moved in or replaced.

### 20. [INSPECS] arr is a class

Specs6.1, 6.8.1: `arr` is a class with ownership.
COMPILERSTATE: an `arr` is a value `{pointer, length}` that is copied freely (`b = a` shares the block). Its block is never freed and its items are not dropped when the array ends; only the items that are replaced end (`a[i] = x`, `fill(null)`, `swap`). Arrays held in objects or variables leak until the program ends.

### 21. [INSPECS] clear() and fill() on arrays of objects

Specs6.1: a dropped owned object ends.

### 22. [INSPECS] swap(i, j) and replace(pos, value)

Specs6.6.

### 23. [INSPECS] Reading an element before it is filled

Specs6.8.1, 19.3: level 1 warning.
COMPILERSTATE: the warning is not built (arrays start as zeros).

Specs6.6.

### 26. [INSPECS] removeAt(range)

Specs6.6.
COMPILERSTATE: built for `vec` and `list`.

### 27. [INSPECS] Sized declarations vec<T>[n] name

Specs6.3.

### 28. [INSPECS] Growth policy and capacity

Specs6.8.2.
COMPILERSTATE: built 2026/10/25: 16 items on the first allocation, doubling up to a 4mb block, then growing by half, never less than what is needed (also for `add(collection)`); `reserve(n)` and `shrinkToFit()` are exact. Missing: the compiler parameters `double-grow-limit` and `further-grow-factor` (fixed at 4mb and 1.5), and the fixed-increment option for small targets.

## PART D - What is missing on list

### 36. [TOBEDISCUSSED] sort(lambda) and lambdas

Context: Specs6.6: `sort(lambda)` uses a temporary custom sorter; the lambda returns a bool (true is -1) or a number. Lambdas and function types are in Specs13.
COMPILERSTATE: lambdas and function types are not built, so `sort(lambda)` and every functional member are "feature not supported". Sorting objects and tuples with the default comparer is also missing (point 14).
Question: the order of the lambda work against the collections work.

Note 2026/10/26: not settled. The implementation order of point 78 is the one to follow, and lambdas are not in it. Open gaps of the lambda semantics: what a bool lambda returns for false (0 or 1), and whether a numeric lambda is judged only by its sign.

## PART F - map (bmap): the sorted map

Specs6.8.4, Specs6.7.2. Nothing is built. The settled rules: sorted by key (B-tree), alias `bmap`, no capacity, `MapCollection<Key, Value>`, a missing key reads as the null or zero value, `add(k, v)` returns `false` when it replaced a value, `add(map)` merges (the new value wins), `tryGet(k, (&)out[, default])` returns `true` when the key exists, `swap` forms, `->c[k]` removes the entry, `has(v)`/`remove(v)`/`removeAll(v)` work on values. (2026/10/26: a null key is no longer excluded, see point 15.)

### 38. [INSPECS] The B-tree design

Specs6.8.4.1. The multi-type parts are reserved there (open, Specs99).
- Decided 2026/10/26 (string values, NOT yet in the spec): 64 bytes is only the size limit for keeping a string value inside the leaf: a string of up to 59 bytes of text sits in the slot (class 0 or 1), a longer one is pointed to (class 13). Because a string in the slot moves with its leaf (insert, split, merge, share), the read rule is: a read inside a statement (`print(m[k])`, `m[k] == "x"`, `m[k].len`) or in a `for` loop over the map (which locks its size) is done in place; a value that is kept (`string s = m[k]`, `s = m[k]`, a field, a parameter written to, `tryGet`) is a copy; `->m[k]` takes the string out.
COMPILERSTATE: built for native and string keys and values (compiler 0.0.23alpha to 0.0.27alpha): exact sort keys and string keys (16-byte slot, separators that point to the leaf keys), string values inline with the read rule above, relaxed deletion, one rebuild for removeAll, the null key in the header, the iterator of the for loop. Missing: keys and values that are objects, tuples or wide natives, multi-type keys, clock and lapse keys (their null is 0).

## PART G - hmap: the hash map

Specs6.8.5. Nothing is built. The settled rules: hash map, same members as `map` (Specs6.7.2), iteration in an unspecified order, capacity members `.capacity`, `reserve`, `shrinkToFit` and the capacity form `hmap<K, V>[n]`, keys need `==` and a hash.

### 46. [FUTUREVERSION] The hash table design

Context: Specs6.1 and Specs99: open addressing, robin hood or chaining is not chosen; several implementations may exist, chosen by target architecture or compiler option (first design, preliminary). The iteration order is unspecified.
Question: the table design, the load factor, the growth, how deletion works (tombstones or backward shift), whether the order is reproducible between runs (it helps tests), and what the capacity form `[n]` guarantees.
PROPOSAL: open addressing with robin hood probing and backward-shift deletion, a power-of-two table, a maximum load of 7/8; a fixed seed so the order is reproducible; a small-table variant for architectures with little memory (point 74).
Note 2026/10/26: hash tables are not under discussion yet (including NaN as a key of `hmap` and `hset`; in `map` and `set` every NaN is one key that sorts last, Specs6.2). The hash is stable across runs for value types, so a saved map stores keys and values, never the hashes or the table (the table is rebuilt on load).

### 49. [TOBEDISCUSSED] String keys

Context: Specs6.2: `""` is a valid key; a null string and `""` are the same value.

## PART H - set (bset): the sorted set

Specs6.8.6, Specs6.7.3. Nothing is built, and the spec says "the sets are defined later; what follows is the first design". The settled rules: sorted (B-tree), alias `bset`, `SetCollection<Item>`, a value is held once, no capacity, items are read-only in loops, iteration sorted. (2026/10/26: a null item is no longer excluded, same rules as the keys, point 15.)

### 52. [TOBEDISCUSSED] The operations that return a new set

Context: Specs6.8.6: `union(other)`, `intersection(other)`, `difference(other)`, `symmetricDifference(other)` return new sets; the two sets must be of the same kind (`set` with `set`, `hset` with `hset`).
Question: ownership. The new set holds items of the two sets; items are objects that the originals own. Cloned (point 35)? A compile error for sets of objects? Moved (which leaves the originals empty)?
PROPOSAL: basic items, strings and other value types are copied; for objects the operation is a compile error until cloning exists.

### 53. [TOBEDISCUSSED] The in-place operators |=, &=, -=, ^= and +=

Context: Specs6.8.6: `|=` (union), `&=` (intersection), `-=` (difference), `^=` (symmetric difference), `+=` as `|=`; with a single value `|=`/`+=` add it and `-=` removes it; no operator returns a new set (`set1 | set2` is not defined).
COMPILERSTATE: compound operators on collections are not built; the compiler has operators only for numbers, strings and their kinds.
Question: are these operators defined by the traits (operator overloading for `SetCollection`) or special cases of the compiler for the default sets? A custom set class: can it provide them? Which of `|=` with a single value and with a collection is chosen when the item type is itself a set?
PROPOSAL: special cases of the compiler for the default sets in this version; operator overloading with the custom collections (point 63).

### 54. [INSPECS] isSubsetOf, isSupersetOf, isDisjointFrom

Specs6.8.6.

### 55. [TOBEDISCUSSED] add(collection) and has on sets

Context: Specs6.8.6: `add(val)` returns `true` if the value was added; `add(collection)` returns the number of items actually added; a duplicate is ignored.
Question: the source of `add(collection)` (any collection of the right item type? a `vec`, an `arr`?) and the ownership of its items (point 24, point 35).

### 56. [TOBEDISCUSSED] The iterator of a set

Context: Specs6.7.3 and Specs99: the shape of `next()` for sets is open (`(Item value, bool isValid)`?), and so are the cursor types. See point 1, point 3. Items are read-only in a loop (`(&)` is a compile error).

### 57. [TOBEDISCUSSED] ->c[k] and swap on sets

Context: Specs6.6 and Specs6.7.3: a set has no `c[k]` read; `->c[k]` is "probably valid, the key being the item"; `swap` is not defined for sets.
Question: the form (`->set[item]` removes the item and gives it; or `set.take(item)`?). The reason is that `has` tells whether an item is present and `remove(v)` ends it, so a way to take an object out is needed.

### 58. [TOBEDISCUSSED] Set literals

Context: Specs6.3: `[...]` can be assigned to `set` and `hset`; a duplicate value in a set literal is a compile error; the empty literal needs a declared type (`set<string> tags = []`).
Question: the lowering (an empty set plus the adds) and the type of a bare `set tags = [...]`.

### 59. [INSPECS] Sets and maps as items

Specs6.2: set items follow the key rules.

## PART I - hset: the hash set

Specs6.8.7. Nothing is built. The settled rules: `SetCollection<Item>`, a hash set, the same members and operations as `set`, capacity members and the capacity form `hset<T>[n]`, iteration in an unspecified order. Only the points that are different from `set` are listed.

### 60. [TOBEDISCUSSED] set against hset

Context: Specs6.8.6: the operations take two sets of the same kind; mixing `set` and `hset` is a compile error.
Question: is there a conversion (`hset<T> h = s.toHash()`)? Would you rather allow the operation and choose the result's kind from the left operand?
PROPOSAL: an explicit conversion member in a later version; mixing stays an error.

### 61. [TOBEDISCUSSED] Order of the result of set operations on an hset

Context: Specs6.8.7: unspecified order. The result of `union` of two hash sets has an unspecified order too.
PROPOSAL: nothing to specify; documented as unspecified.

### 62. [TOBEDISCUSSED] Sharing the code of set and hset with map and hmap

Context: a set is a map without values; an `hset` is an `hmap` without values.
PROPOSAL: the compiler generates `set` and `hset` from the `map` and `hmap` code (the value type is empty), so the designs of point 38 and point 46 are decided once.

## PART J - Custom collections and related language points

Specs6.9 (custom collections, partial). A custom collection implements the traits of Specs6.7 or subclasses a default collection. Built: a class that implements `IndexCollection<T>` (which brings `Collection<T>`) gets `for x in c` through `getIterator()` and `next()`.

### 63. [FUTUREVERSION] The indexer, literals and operators of custom classes

Context: Specs6.9: how a custom class provides `c[k]` (read and write) and the literals `[...]` and `{ ... }` is open (Specs99); `c[k]` is not an operator the language lets a class define.
COMPILERSTATE: not built; a custom class cannot be indexed, cannot receive a literal, and cannot define `|=` or `+=`.
Already decided: `c[k]` and `c[k] = v` are implemented by the non-public methods `read_pos` and `set_pos` of the trait (point 11).
Question: how a custom class receives the literals `[...]` and `{ ... }` and defines `|=` and `+=`.

### 64. [FUTUREVERSION] Subclassing the default collections

Context: Specs6.9: a custom collection can subclass `vec`, `list`, `map`, `hmap`, `set` or `hset`; how the overridden methods are dispatched is open; `arr` cannot be subclassed (a primitive).
Question: the compiler's direct code for `c[i]`, `for` and the hot paths does not call methods; if a class overrides `add`, which one runs?
PROPOSAL: a subclass of a default collection loses the direct paths and goes through the virtual calls.

### 65. [INSPECS] The traits for maps and sets in custom classes

Specs6.7.
COMPILERSTATE: neither trait exists in the compiler.

### 66. [TOBEDISCUSSED] Variadic parameters and existing collections

Context: Specs99: the position of a variadic parameter and passing an existing collection (`f(...v)`). A `vec` as the variadic argument is the natural case.

### 67. [FUTUREVERSION] Structs in collections

Context: Specs11.1.5: structs are generic non-heap value types, to be defined; they differ from `dfoot` (Specs5). A `vec<Point>` of structs would hold values inline, which changes the ownership and the drop code.

### 68. [FUTUREVERSION] Lists of pointers and references

### 83. [TOBEDISCUSSED] Lifetime of borrows of items

Context: a borrow of an item taken outside a `for` loop (`(*)i32 p = (&)m[k]`, `f((&)m[k])`, `(&)v[3]`) points into the collection. An insert or delete in a `map` shifts or moves the inline values of a leaf (point 38), and an `add` that reallocates a `vec` moves its items, so the borrow points to the wrong place. Inside `for (&)` it is safe (the counter blocks changes, point 6); `tryGet(k, (&)out)` is safe (`out` is the caller's own variable). The spec has no rule for it.
PROPOSAL: a borrow of an item (`(&)c[k]`, `&c[k]`) increments the counter of the collection, like an iterator, as long as the borrow lives; meanwhile a change raises `ModifyingIteratedCollectionException`. The borrow lives at most to the end of its scope, like the iterators, views and tuples holding a `(&)` (Specs3.2, Specs6.5).
Open: this needs the compiler to track the lifetime of borrows in general, which is wider than the collections. Prerequisite of step 5 of point 78.

### 85. [TOBEDISCUSSED] Temporary objects that never end

Context: found 2026/10/26 while building step 4 of point 78. A new object that is not kept in a variable and not returned (a temporary inside an expression) is never ended by the compiler (a known limit of the ownership code: "temporaries inside an expression are never destroyed"). For a view this means its counter is never given back, so its collection stays locked for good:
```
vec<i32> v = [1, 2, 3, 4]
r.Console.log(v[1..3])          // the view is never ended
v.add(5)                        // ModifyingIteratedCollectionException (a Panic in Release)
```
The same happens with `v[1..3].len`, a view passed to a function, and a new map view used in another expression (for the maps the common forms avoid the view object).
COMPILERSTATE: not fixed. The view of a map given only to printing is printed and then ended.
Question: when does a temporary object end? PROPOSAL: at the end of the statement that made it, like the temporary strings (df_tmp), unless it is kept (a variable, a field, an item, a returned value, an argument moved with ->).
