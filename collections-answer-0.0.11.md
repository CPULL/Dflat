# Collections: partial answer to the briefing

Answer to `To_discuss_for_collections.txt`, written after the design session of 2026/10/20. The language rules are in `dflat-spec.md` 0.0.11 (sections 6, 10.3, 11.1.4, 11.2, 12.4, 15). This document follows the numbers of the briefing and says, for each question, what is decided, what is preliminary and what is still open. **Decided** means the user stated it as a decision; **preliminary** means a first reaction that can still change.

## Decisions

### 1. Where the collections are written
- Decided: the seven collections are generated by the compiler as C code. Performance comes first, and it cannot be guaranteed that Dflat code would be as fast as C.
- Decided: users can write their own collection classes in Dflat (6.12).
- Decided: mandatory traits fix the signatures: `Collection` (all seven), `IndexCollection` (`arr`, `vec`, `list`), `MapCollection` (`map`, `hmap`), `SetCollection` (`set`, `hset`).

### 2. What the language must gain first
For the compiler's own collections nothing is needed, because the compiler emits C directly. For custom collections:
- Decided: `.len` is a read-only property of the trait; a collection trait also requires `fun Iterator GetIterator()`.
- Decided: `for x in c` on a custom collection uses an iterator holding the cursor; `next()` returns a tuple ending with `isValid`: `(Item value, bool isValid)` for sequences, `(Key key, Value value, bool isValid)` for maps (the shape for sets is open). `isValid == false` means the other items are not valid, so null keys, values and items do not clash with the end of the iteration. It replaces `Item? Next()` of the old `Sequence` example.
- Decided: the collection traits take the item type as a generic argument (`class MyCollection<Item> : IndexCollection<Item>`); there is no reserved type name.
- Decided: fields and properties are one concept (11.1.4). `R:` / `W:` blocks, `field`, `value`, defaults, visibility per accessor; trait properties are access contracts with optional default implementation (11.2). This is the language support the traits need for `len`.
- Open: the indexer (`c[k]` read and write) and literal construction for custom classes; which other members the traits require and which they supply by default. The compiler does not build indexer or operator overloading for user classes yet.

### 3. Order of work
Closed by the user: the order does not matter, everything will be implemented.

### 4. Ownership of elements
- Decided: the Rust model. A collection owns its items; the drop code is generated per item type.
- Decided: a result that is not assigned is destroyed at the end of the statement; `c[k] = v` drops the previous item; a `for` loop only borrows the items (no consuming loop).
- Decided: `->c[k]` moves the item out. The slot is zeroed in `arr` and `vec`; the item is removed in `list`, `map`, `hmap`, `set` and `hset`.
- Decided: `pop((&)out)` returns a `bool`, moves the item into `out`, and on an empty `vec` returns `false` and gives `out` the default value. It is the only form (no `tryPop`, no null special case).
- Decided: `swap`: `Item old = sequence.swap(position, Item new)`, `Item old = map.swap(Key key, Item new)` (a missing key adds the pair and returns a null item), `sequence.swap(i, j)`, `map.swap(key1, key2)` (both present: exchange; one present: its value moves to the missing key and the original key is removed; both missing: nothing).
- Decided: `bool tryGet(k, (&)out[, default])` returns `true` when the key exists.
- Open: `swap` and `->c[k]` on sets (a set has no `c[k]` read).

### 5. Exceptions and cost
- Decided: an index outside a collection is checked in every build (like Go, C#, Java and Rust). Debug: `IndexOutOfRangeException`, catchable. Release: `Panic`; a `catch` for it is ignored with a level 3 warning.
- Decided: the three silent exceptions of the collections (`NaNUsedAsKeyException`, `InvalidMapKeyException`, `EmptyVectorAccessException`) are removed, and their IDs 21 to 23 retired. The fallbacks apply: a NaN key is not stored or retrieved, a missing key reads as the null or zero value (`hasKey` and `tryGet` tell the difference), `pop` returns `false`.
- Decided: maps and sets do not allow null keys (or null set items). `""` is a valid string key.
- Open: whether the index rule also covers `arr` indexing and the other non-silent operation exceptions; the cost of `c[i]` as a failing operation (the error part).

### 6. Borrow rules
- Decided: a collection cannot be changed while it is iterated.
- Preliminary: enforcement is a compile error when the compiler can prove the loop body does not change the collection (Rust style); otherwise a version check at runtime (C# style). What the runtime check raises is open.
- Decided: `for Item x in c` is read-only; `for (&)Item x in c` is a read/write borrow of the item; the marker is written `(&)Type variable` everywhere. Set items and map keys are always read-only. A basic value without `(&)` is a copy; assigning to it gives a level 3 warning.
- Preliminary: views are read-only only (no writable views) and can only be local variables or parameters, never fields, collection items or results. The full Rust borrow model stays an option if tasks need it.
- Open: how an iterator refers to its collection without a borrow stored in a field (it is a borrow in an object, which the view rules do not allow); how `next()` returns a read-only or a writable borrow of the item.

### 7. Hashing and ordering
- Preliminary: `hmap` and `hset` can have several implementations, chosen by target architecture or compiler option; the iteration order of the hashed collections is already unspecified in the spec, so implementations may differ. `reserve` already gives the initial size.
- Decided: NaN keys are never stored; null keys are not allowed.
- Open: the hash function, the table design (open addressing, robin hood, chaining) and the B-tree node size; the cursor type of each iterator (a position for `arr` / `vec` / `list`, a slot for the hash tables, a node or a key for the trees); whether `Iterator` has two or three sub-traits.
- For the compiler chat: how a `string` is stored in the generated C (empty and null strings, occupancy flag of hash tables) is outside the collections and gets its own session; the current temporary implementation stays until then.

### 8. Code size
Not discussed yet. Open: copies per element type against shared non-generic C helpers working on byte sizes (11.3.12 gives the limit of 64 copies per collection).

### 9. Literals and inference
Not discussed yet. The typing rules of 6.3 stay as they are; open: how `vec values = [1, 2, 3]` and `map ages = { one: 1 }` are lowered, and how a custom class receives the items of a literal.

## Still open (to decide later, one at a time)
- Indexer and literal construction for custom classes; the other members of the collection traits
- Iterator sub-traits, cursor types, how an iterator refers to its collection, borrow returned by `next()`, `next()` for sets
- What the runtime check raises when a collection is changed during an iteration
- Cost of `c[i]` as a failing operation; whether the index rule covers `arr` and the other non-silent operation exceptions
- `swap` and `->c[k]` on sets
- Hash and B-tree designs, code size, literal typing and lowering
- String storage in the generated C (separate session)
